§1

Why replicate, and what it costs

Core idea. Replication gives fault tolerance, availability and performance. Latency improves much less than other metrics, and the speed of light is a hard limit, so data must be close to users. The main problem is consistency between replicas. A consistency model is a contract between the processes and the data store: strong guarantees are easy to program but expensive.

Q1Exercise

(a) Give the three reasons to replicate data, with one example each. (b) From 1983 to 2024, network bandwidth improved more than 3000×, but round-trip latency improved less than 30× (2.54 ms → 0.1 ms in a LAN). Why does this matter for replication? (c) A data store has one replica in Milan and one in New York, about 6,500 km apart. Light in optical fiber travels at about 200,000 km/s. What is the minimum time of a write that waits synchronously for the remote replica?

Model answer

  1. Fault tolerance: redundancy hides failures (replicated state machines with consensus give the illusion of one machine). Availability: a local replica on a mobile device supports disconnected operation; replicas also absorb load peaks (for example, the release of a new operating system). Performance: share the load to increase throughput (a replicated web server), and put data close to users to cut latency (processor caches, local copies on phones, CDNs, geo-replicated data stores).
  2. When other metrics improve much faster, latency becomes the limiting factor. A protocol that waits for remote replicas pays latency on every operation. More bandwidth or faster CPUs do not help. So designers replicate data close to the clients and try to avoid synchronous coordination.
  3. One way: 6,500 / 200,000 s = 32.5 ms. A synchronous write needs at least one round trip: about 65 ms, before any processing or queuing. A client that does 100 dependent writes waits at least 6.5 s.

Why

No technology removes the propagation delay: it is physics. This is the root of the whole chapter. Strong models need synchronous coordination, so they pay this delay. Weak models (causal, FIFO, eventual) answer from the local replica and propagate later.

Exam tip

When a question asks you to compare designs "in terms of response time", always say which interactions are synchronous and how far apart the replicas are.

Q2Describe

Give real examples of replicated systems. What are the main challenges of replication? What is a consistency model, and which kinds of guarantees can it give?

Model answer

Examples. Collaboration platforms (Google Docs, Microsoft 365, Dropbox): files are replicated on user devices, support disconnected work, and are reconciled at reconnection. They assume that conflicts are infrequent. Distributed file systems, which may support simultaneous changes. CDNs (for example, used by Netflix) replicate content near the users.

Challenges.

  • Consistency: a change to one replica must reach all the others. Concurrent updates create write-write and read-write conflicts. We must define the behavior in case of conflicts.
  • Cost: replication can degrade performance. Waiting until every replica has a write can be very expensive.
  • Different applications need different guarantees: data-centric vs client-centric.
  • "Read returns the last write" is the ideal, but "last" is not defined without a global clock.

Consistency model: a contract between the processes and the data store. Stricter guarantees simplify development but cost more; weaker ones are cheaper but make development harder. Kinds of guarantees: on content (maximum difference between versions at different replicas), on staleness (maximum time before a change reaches all replicas), on the order of updates (which behaviors are allowed with conflicts). Models are data-centric or client-centric. Consistency protocols implement the models.

Why

The "contract" view explains the whole chapter. The store promises a set of allowed results; the programmer writes code that is correct for every allowed result. The fewer results allowed, the easier the code, and the more coordination the store needs.

§2

Replication protocols: single leader, multi leader, leaderless

Core idea. The key question is "who decides the order of writes?". Single leader: the leader decides; followers are updated synchronously, asynchronously or semi-synchronously. Multi leader: nobody decides, so write-write conflicts happen; it fits geo-replication. Leaderless: clients contact quorums, with NR + NW > N and NW > N/2. A protocol is highly available if it needs no synchronous (blocking) communication; CAP says that with partitions you choose availability or consistency.

Q4Exercise

A single-leader store has one leader and four followers. The round-trip times from the leader to the followers are 2, 5, 9 and 40 ms. Ignore processing time. (a) What is the write latency with synchronous, asynchronous, and semi-synchronous replication with k = 2? (b) How many copies of a confirmed write exist in each case? (c) The store is asynchronous. The leader confirms W(x)7 and crashes before it sends the update. A follower becomes the new leader. What happens? (d) With asynchronous replication, a client writes x = 7 on the leader and immediately reads x from the 40 ms follower. What can it read?

Model answer

  1. Synchronous: wait for all followers → 40 ms (the slowest). Asynchronous: complete after the local write → about 0 ms. Semi-synchronous, k = 2: wait for the two fastest replies → 5 ms.
  2. Synchronous: 5 copies. Asynchronous: 1 copy is sure (the leader). Semi-synchronous: at least 3 copies (leader + 2 followers), so the write survives any 2 crashes.
  3. The write is lost: no follower has it, but the client got "ok". Failover can also create other problems: followers that are not up to date, and a partitioned network where two nodes think they are the leader. To make failover safe, you need a consensus protocol.
  4. It can read the old value. This is a read-write conflict: the client does not see its own write.

Why

Semi-synchronous replication is the practical compromise: the latency of the k-th fastest follower, not of the slowest one, and k + 1 durable copies. Synchronous replication is feasible inside one data center because there the round trips are short.

Q5CompareExam 13 Feb 2015 · 19 Sep 2013

What is a "primary-based consistency protocol"? How does it work, which variants exist, and what are their pros and cons?

Model answer

A primary-based protocol is a single leader protocol: each data item has one primary (leader). All writes go to the primary, which orders them and propagates them to the backups (followers). So there are no write-write conflicts.

Leader failure requires failover, done safely with consensus. A common optimization: partition the data and give each partition a different primary, to spread the write load.

Why

"Primary-based" is the older name (Tanenbaum) of what the current slides call single leader. All variants trade latency for safety: the more replicas the primary waits for, the slower the write and the smaller the risk of stale reads and lost writes.

Q6Scenario

A social network has data centers in Europe, the US and Asia. Users post and comment. Should you use one leader for the whole world or one leader per data center? Two users comment on the same post at the same moment in Europe and in Asia: what happens, and is it a problem?

Model answer

Use multi leader (one leader per data center). With one world leader, an Asian user pays an intercontinental round trip on every post: prohibitive latency, and no writes when the link to the leader fails.

The two comments are a write-write conflict: each data center accepts its comment and propagates it. Europe can show A then B; Asia can show B then A. In this application it is acceptable:

  • Writes (posts, comments) are not frequent.
  • The writes of a user or a group of users usually go to the same replica.
  • The order of concurrent comments is not critical.

If you need the same order everywhere, add a deterministic rule (for example, sort by timestamp, last-write-wins). If you need a reply to appear after its post, use causal consistency.

Why

Multi leader is harder in general, but in practice conflicts are rare and easy to solve in many applications. The choice depends on the cost of a conflict, not only on its probability.

Q7Exercise

A leaderless store has N = 5 replicas. Which (NR, NW) choices are correct: (2, 4), (3, 3), (1, 5), (3, 2), (4, 2)? What is ROWA?

Model answer

Rules: NR + NW > N (avoids read-write conflicts: every read quorum meets the last write quorum), and NW > N/2 (avoids write-write conflicts: two write quorums meet).

  • (2, 4): 6 > 5, 4 > 2.5 → correct.
  • (3, 3): 6 > 5, 3 > 2.5 → correct.
  • (1, 5): 6 > 5, 5 > 2.5 → correct. This is ROWA: read one, write all. Fast reads, but a write fails if any replica is down.
  • (3, 2): 5 is not > 5 → a read can miss the last write; and 2 < 2.5 → write-write conflicts. Wrong.
  • (4, 2): 6 > 5, but NW = 2 → two concurrent writes can use disjoint quorums. Wrong.

Why

It is the pigeonhole principle: two sets whose sizes add up to more than N must share an element. That shared replica carries the latest version number.

Q8Exercise

(a) N = 7. List all correct quorum pairs with the smallest NR for each NW. For (4, 4) and for ROWA, how many crashed replicas can reads and writes tolerate? (b) N = 5, NW = 3, NR = 3. A write of x with version 7 reached A, B, D. Now the versions are A:7, B:7, C:6, D:7, E:5. A client reads from C, D, E. What does it return, and what does read repair do? (c) What happens with NW = 2 if one client writes to {A, B} and another to {D, E} at the same time?

Model answer

  1. NW > 3.5 → NW ≥ 4, and NR ≥ 8 − NW: (4, 4), (3, 5), (2, 6), (1, 7). An operation with quorum Q still works with f crashes if 7 − f ≥ Q. (4, 4): reads and writes tolerate 3 crashes. ROWA (1, 7): reads tolerate 6 crashes; writes tolerate 0.
  2. Replies: C:6, D:7, E:5. The client returns the value with the highest version, 7. D is in both quorums ({A, B, D} ∩ {C, D, E} = {D}): this is the guarantee of NR + NW > N. Read repair: the client (or the coordinator) sends version 7 to the stale replicas C and E. A stays up to date through anti-entropy later, if needed.
  3. The two write quorums do not intersect. Both clients can get the same next version number with different values: a write-write conflict. Replicas disagree and no read can decide which value is "the" version. NW > N/2 forbids this.

Why

Quorum sizes move the cost between reads and writes. Big write quorums make writes slow and fragile, small read quorums make reads fast. Pick them by the read/write ratio and by which operation must stay available.

Q9Describe

What is a highly available protocol? State the CAP theorem. How do modern distributed databases position themselves with respect to CAP?

Model answer

A protocol is highly available if it needs no synchronous (blocking) communication: if a node or a link fails, a client still gets a reply from a correct replica.

CAP: C = consistency, A = availability, P = network partitions. In the presence of partitions you can have availability or consistency, not both. Partitions can always happen, so the real choice is between:

  • Strong guarantees (C) through blocking communication: higher latency, possibly no service during failures. Example: NewSQL (Spanner, Calvin, VoltDB), sequential or linearizable replication.
  • High availability (A) through non-blocking communication: lower latency, weaker guarantees. Example: NoSQL stores with asynchronous or multi-leader replication.

Some weak models (FIFO, causal with sticky clients, eventual) have highly available implementations. Sequential and linearizable do not.

Why

During a partition, a replica that answers without talking to the other side may return a value that the other side already overwrote. To refuse is to lose availability; to answer is to lose strong consistency.

§3

Sequential consistency and linearizability

Core idea. Sequential: all processes see the same interleaving, and each process's operations keep program order; there is no notion of time. Linearizable: in addition, each operation takes effect at one instant between its start and its end: a recency guarantee, the illusion of a single copy. Neither has a highly available implementation.

Q10Exercise

State the definition of sequential consistency. Then consider (all variables start at 0): P1: x = 1; print(y, z); P2: y = 1; print(x, z); P3: z = 1; print(x, y);. The output is the six digits printed in time order, as in the slides. Which outputs are possible under sequential consistency: 001011, 000000, 011011, 001001, 111111?

Model answer

Definition (Lamport): "The result is the same as if the operations by all processes were executed in some sequential order, and the operations by each process appear in this sequence in the order specified by its program." Operations of one process are not reordered, all processes see the same interleaving, and time plays no role.

Two facts follow from program order, because each print comes after the write of its own process:

  • The second print reads the variable of the process that printed first, and that process already wrote it. So the second pair contains at least one 1.
  • The third print happens after all three writes. So the last pair is always 11.

Why

Under sequential consistency you do not search for "which values can appear"; you search for one global order that respects program order. To prove that an output is impossible, find a property that every valid order has (here: the last print sees all the writes).

Q11ExerciseExam 27 Jun 2013

Two threads share volatile int x, y, tmp1, tmp2. Thread t0 runs x = 1; tmp1 = y; and thread t1 runs y = 1; tmp2 = x;. The main thread repeats: set all variables to 0, start t0 and t1, join both, and if (tmp1==0 && tmp2==0) break;. ("volatile" only stops compiler optimizations.) On a machine with a sequentially consistent memory model, does the program terminate? Then, related slide question: in Java, thread 1 runs x = 1; y = 1; and thread 2 reads y = 1 and then reads x. Which values of x are allowed?

Model answer

(The exam text file lost the thread bodies; this is the standard version of this exam question.)

It never terminates. Suppose tmp1 = 0. Then t0 read y before t1 wrote y. By program order, x = 1 happened before that read, and t1's read of x happens after t1's write of y. So t1 reads x after x = 1, and tmp2 = 1. The same argument works if tmp2 = 0. So no sequentially consistent interleaving gives tmp1 = tmp2 = 0, and the loop never breaks. (On a real multi-core CPU with store buffers, both reads can return 0, and the program can terminate: real hardware is not sequentially consistent.)

Java: x = 0 and x = 1 are both allowed. A thread can read from its local cache, and any old value is allowed. Exceptions: if the variables are volatile, or the accesses are inside synchronized blocks, the accesses are sequentially consistent, and only x = 1 is allowed. In practice, programs synchronize with synchronized blocks, so such races should never occur.

Why

Sequential consistency was born as a memory model for multiprocessors (Lamport, 1979). The C, C++ and Java memory models are not sequentially consistent for plain variables, because caches and reordering make programs faster. You get sequential behavior only where you ask for it.

Q12ScenarioMargara exercises

Describe a single-leader protocol that guarantees sequential consistency (assume no faulty links or processes) and state its assumptions. Show what goes wrong if (a) links are not FIFO; (b) clients are not sticky. How do you get sequential consistency with a leaderless protocol? Why does sequential consistency limit availability?

Model answer

Protocol. All writes go to the leader. The leader orders them, applies them, and sends them to all followers synchronously; the write completes when all followers reply. Reads go to any replica. Example from the slides: C reads x = 0 at follower 2, A writes x = 1, B reads 1 at follower 1. The sequence R(x)0 by C → W(x)1 by A → R(x)1 by B explains everything. (MySQL, PostgreSQL, MongoDB use this; failover is sometimes manual.)

Assumptions: links are FIFO (updates arrive in the order the leader sent them); clients are sticky (each client always uses the same replica).

  1. Without FIFO links: the leader sends W(x)1 then W(x)2. Follower 1 receives them in order, follower 2 receives W(x)2 then W(x)1. Follower 2 ends with x = 1, follower 1 with x = 2. Clients see two different orders of the same writes: not sequential (and replicas diverge).
  2. Without sticky clients: client B reads x = 1 at follower 1 (updated), then moves to follower 2 (not updated yet) and reads x = 0. B's own history R(x)1 R(x)0 with one write W(x)1 has no valid sequential order.

Leaderless: quorums with NR + NW > N and NW > N/2. A write needs a quorum to agree on its version number; a read needs a quorum to find the latest version.

Availability: no highly available implementation exists. Single leader: the client must reach the leader, and the leader must update replicas synchronously. Leaderless: the client must reach a quorum. Two problems follow: high latency from synchronous interactions, and blocked clients during network partitions.

Why

The leader creates a single order; FIFO links make every replica apply that order; sticky clients stop a client from "jumping back" to a replica that is behind. Remove any one of the three and two observers can see different orders.

Q13CompareMargara exercises

Define sequential consistency and linearizability. Write (or describe) a schedule that is sequentially consistent but not linearizable. Does the single-leader sequential protocol also guarantee linearizability? If not, how can you modify it?

Model answer

Sequential: "the result is the same as if all operations were executed in some sequential order, and the operations of each process appear in the order of its program". No time. Linearizable: "each operation should appear to take effect instantaneously at some moment between its start and its completion". It is a recency guarantee: the illusion of one copy. Also called strong, external or atomic consistency.

Example. A writes x = 1 on the leader. The leader updates follower 1, then follower 2. In real time: B reads x = 1 from follower 1; after that, C reads x = 0 from follower 2. The sequential order RC(x)0 → W(x)1 → RB(x)1 exists, so it is sequential. It is not linearizable: C's read starts after B's read ended and still returns the old value. There is no single instant at which x changes from 0 to 1.

Fix: the leader orders writes by timestamp and updates replicas synchronously and atomically. For example, the leader locks the followers, sends the write, and unlocks them when all have it. A locked follower does not answer reads. After the unlock, no read can return 0. With failures, you need consensus (Raft) to agree on the leader and on the partition state.

Why

If B and C talk on another channel (a phone call), C learns that it read a stale value: the single-copy illusion breaks. Linearizability forbids it; sequential consistency does not care about real time.

Q14Exercise

x starts at 0. Client A runs W(x)1 from t = 0 to t = 10 ms. Client B runs R(x) from t = 2 to t = 4 and gets 1. For each case, is the history linearizable? Is it sequentially consistent? (a) Client C runs R(x) from t = 5 to t = 7 and gets 0. (b) C runs R(x) from t = 3 to t = 6 and gets 0. (c) C runs R(x) from t = 12 to t = 13 and gets 0.

Model answer

B returns 1, so the write takes effect at some point p ≤ 4 (before B's read ends) and p ≥ 0.

  1. C's read starts at 5 > 4 ≥ p. It must see 1. Not linearizable. Sequential: yes (order RC(x)0, W(x)1, RB(x)1).
  2. C's read overlaps B's read and the write. Points: C at 3.0 (reads 0), write at 3.5, B at 3.8 (reads 1). Each point is inside its interval. Linearizable, and so sequential.
  3. The write ended at 10; C starts at 12. It must see 1. Not linearizable. Sequential: yes, with the same order as in (a).

Why

Method: give each operation a point inside its interval and check that the points form a legal sequential history. Overlapping operations can be put in any order; non-overlapping operations must keep their real-time order. Sequential consistency drops the real-time rule, so case (c), which looks absurd, is still sequential.

Q15Describe

Why is sequential consistency "not enough"? What does it mean that linearizability is composable? What is strict serializability? Why is linearizability hard to guarantee with failures?

Model answer

  • Not enough: sequential consistency has no notion of time. A write can be "done" for the writer and still invisible to others for an unbounded time. When clients also communicate outside the store, they can notice it.
  • Composable: if the operations on each single variable are linearizable, the whole schedule is linearizable. You can check (or implement) each object separately. Sequential consistency is not composable: two per-variable sequential histories can be impossible to merge.
  • Strict serializability: linearizability extended to transactions (groups of operations): transactions are serializable, and the serial order respects real time.
  • Failures: to decide if and how the network is partitioned and who is the leader is an agreement problem. You need a consensus protocol such as Raft (or Paxos).

Why

Composability is why linearizability is practical: a system made of independent linearizable registers (or partitions) is linearizable as a whole, with no global coordination between them.

§4

Causal, FIFO, synchronization variables

Core idea. Causal: writes that are potentially causally related are seen by all in the same order; concurrent writes in any order. Implementation: vector clocks, highly available with sticky clients. FIFO (PRAM): the writes of each single process are seen in issue order; implementation: sequence numbers. Synchronization variables make writes visible only when the program asks. Strength: linearizable ⇒ sequential ⇒ causal ⇒ FIFO.

Q16Exercise

(a) Use the group chat example to explain causal consistency and give the definition of causal order. (b) Replicas R1, R2, R3 implement causal consistency with vector clocks (one entry per replica, counting the writes it applied from each replica). R3 has V = [1, 0, 0]. It receives, in this order: m1 from R2 with timestamp [2, 1, 0]; m2 from R1 with [2, 0, 0]; m3 from R2 with [2, 2, 0]. When does R3 apply each update? What does a client at R3 read while m1 waits?

Model answer

(a) A writes "Distributed systems are the best!", B replies "No way! They are too complex…". If C sees B's message first, she cannot understand it: everybody must see A's message before B's. Two unrelated messages ("Apple released a new MacBook", "I'm having fun learning replication") can be seen in any order. Definition: "Writes that are potentially causally related must be seen by all processes in the same order. Concurrent writes may be seen in any order at different machines." Causal order: a write by P is after every previous operation of P (also on other variables); a read of x is after the write it reads (a process reads its own writes too); the order is transitive. It is not total: unordered operations are concurrent. It is Lamport's happened-before, applied to reads and writes.

(b) Rule: apply an update from Rj with timestamp T when T[j] = V[j] + 1 and T[k] ≤ V[k] for every k ≠ j (all its potential causes are applied).

Q17Exercise

(a) Define FIFO (PRAM) consistency and explain the name. (b) A replica uses sequence numbers to implement FIFO consistency. It has applied P1's writes up to number 1 and P2's up to 0. It receives: (P1, 3), (P2, 1), (P1, 2), (P1, 5), (P2, 2), (P1, 4). Give the order in which it applies the updates. (c) Why is FIFO consistency "very easy to implement", even with multiple leaders?

Model answer

(a) "Writes done by a single process are seen by all others in the order in which they were issued; writes from different processes may be seen in any order at different machines." Causality across processes is dropped. PRAM = Pipelined RAM: a process can fill a pipeline with writes without waiting for the earlier ones to complete.

(b) Rule: apply update S from P only after all of P's updates with smaller numbers.

  1. (P1, 3): expected 2 → buffer.
  2. (P2, 1): expected 1 → apply.
  3. (P1, 2): apply; then (P1, 3) from the buffer.
  4. (P1, 5): expected 4 → buffer.
  5. (P2, 2): apply.
  6. (P1, 4): apply; then (P1, 5).

Applied order: P2:1, P1:2, P1:3, P2:2, P1:4, P1:5.

(c) Each replica needs only one counter per writer and a hold-back buffer. No replica waits for another one to agree; concurrent writes from different processes need no coordination.

Why

FIFO consistency is FIFO multicast applied to a data store. Compare it with causal consistency: a vector clock says "wait for every write I depended on", a sequence number only says "wait for my own earlier writes".

Q19CompareExam 25 Feb 2015 · 23 Sep 2015

Why were consistency models with synchronization variables introduced? How do they work? Then place them in the summary of data-centric models (linearizable, sequential, causal, FIFO).

Model answer

FIFO consistency still makes every write visible to every process, even processes that do not care. Moreover, not all writes need to be seen by all processes, for example the writes inside a transaction or critical section. Models with synchronization variables make writes visible only when a process asks for it through the variable (constructs such as synchronize, acquire/release). The programmer forces consistency only where needed: at the end of a critical section (to distribute writes) and at the beginning of a "reading session" (to see others' writes).

Classic variants (Tanenbaum): weak consistency (one synchronize operation, accesses to sync variables are sequentially consistent); release consistency (acquire brings the local copy up to date, release propagates the writes); entry consistency (one lock per data item, so only the data protected by that lock is synchronized).

ModelDescription
LinearizableAll processes see all shared accesses in the same order; operations behave as if they took place at some point in wall-clock time
SequentialAll processes see all shared accesses in the same order; accesses are not ordered in time
CausalAll processes see causally related shared accesses in the same order
FIFOAll processes see the writes of each process in the order they were issued; writes of different processes may be seen in different orders
With sync variablesConsistency is enforced only at synchronization points chosen by the programmer

Why

Most programs already synchronize with locks. Tying propagation to synchronization points removes the useless traffic between them. The cost: the programmer is responsible for consistency.

§5

Schedule drill: FIFO, causal, sequential

Core idea. Use one method for every schedule. (1) FIFO pairs: the writes of each process, in program order. (2) Causal pairs: add "write w → write w′" when a process reads w and later writes w′ (plus transitivity). (3) For each process, list the order in which it observes values. (4) FIFO/causal: each process needs its own view that respects the pairs. Sequential: one order for everyone; look for two processes that observe two writes in opposite orders. Values start at 0.

(d) P0: W(x)1 R(y)2 W(x)3
    P1: W(y)2 R(x)3 W(y)4
    P2: R(x)1 R(y)4 R(x)1

Model answer

  1. FIFO only. P1 reads 1 before writing 2: W(x)1 → W(x)2 causally. P2 sees 2 then 1: not causal. FIFO holds, because the two writes come from different processes.
  2. FIFO and causal, not sequential. The writes are concurrent, so P2 and P3 can see them in opposite orders; one global order cannot.
  3. None. P0 writes x before y. P1 sees y = 1 and then x = 0: P0's order is broken. This is the smallest FIFO violation.
  4. FIFO only. P1 reads 3 before writing 4: W(x)3 → W(y)4 (and W(x)1 → W(x)3). P2 reads y = 4, so x = 3 is applied; then it reads x = 1: not causal. Removal of P1's R(x)3, P2's R(y)4 or P2's R(x)1 makes it sequential (and so causal).

Why

These four patterns are the building blocks of every exam schedule: (a) a broken causal chain through one variable, (b) concurrent writes seen in opposite orders, (c) a broken FIFO order, (d) a broken causal chain across two variables.

§6

Eventual consistency and client-centric models

Core idea. With few concurrent updates and mostly reads (web caches, DNS, social media), eventual consistency is often enough: updates reach all replicas eventually. CRDTs make concurrent updates converge. When a client moves between replicas, client-centric models protect that one client: monotonic reads, monotonic writes, read your writes, writes follow reads. Implementation: a read-set and a write-set per client.

Q36ScenarioExam 14 Feb 2024

Your application requires FIFO consistency, but the data store provides only eventual consistency. Assuming no failures, does the store satisfy the requirement? If not, can you implement FIFO on top of the eventually consistent store? How?

Model answer

No. Eventual consistency guarantees only that replicas converge when updates stop. A process can see P's second write before its first, or see a value and then an older one. Eventual does not imply FIFO (nor causal, nor sequential).

Yes, you can build it in a layer on top of the store:

  • Each process tags its writes with (process id, sequence number). For example, store the value together with the tag.
  • The reading layer keeps, for each writer, the last sequence number accepted. When it reads a value with tag (P, s), it accepts it only if all of P's writes with number < s were already seen. Otherwise it returns the previously accepted value (or waits and retries).
  • The store eventually delivers every write, so the missing ones arrive, and the layer makes progress.

Alternative: each process appends to its own append-only log in the store; readers apply each log in sequence-number order.

Why

FIFO is the same mechanism as FIFO multicast: sequence numbers per sender and a hold-back buffer. Eventual consistency gives "everything arrives eventually"; the sequence numbers add "in order".

Exam tip

Be careful with overwrites: if P writes x twice quickly, a reader may never see the first value. That is allowed under FIFO (the reader saw the writes "in order", and the first was simply overwritten). What is forbidden is seeing the second and then the first.

Q37ExerciseMargara exercises

(a) Does eventual consistency imply sequential, causal or FIFO consistency? When is it enough, and why is it so popular? (b) Describe CRDTs: why are they useful, and what are their limits? (c) A counter starts at 10 on replicas A, B, C. A does +5, B does −3, C does +2. Each replica receives the others' updates in a different order. Show the final value if replicas store the operations, and what can go wrong if each replica only sends its last value. (d) Comments on a post: (Ann, ts 5), (Bob, ts 3), (Cy, ts 8) arrive in different orders at two replicas. With last-write-wins on the timestamp, what is the final order?

Model answer

(a) No to all three: eventual consistency says nothing about the order of intermediate values, only that replicas converge. It is enough when there are no (or easily resolved) simultaneous updates and mostly reads: web caches, DNS, social media. Popular because it is very easy to implement, conflicts are rare in practice (a user often accesses and updates the same replica; networks propagate updates fast), and CRDTs exist. It is often used in geo-replicated stores. It can be hard to reason about: with concurrent updates a replica can temporarily hold a "wrong" result.

(b) CRDTs (conflict-free replicated data types) guarantee convergence even if updates arrive in different orders, because their operations have commutative semantics. Useful: no coordination, high availability, automatic convergence. Limits: only for types whose operations commute; temporary inconsistent values; they cannot enforce invariants that need coordination (for example, "the balance stays ≥ 0").

(c) Store the set of operations: every replica applies +5, −3, +2 in some order. Addition commutes: 10 + 5 − 3 + 2 = 14 everywhere. With "send the last value": A sends 15, B sends 7, C sends 12. A replica that keeps the last value it received ends with 15, 7 or 12, depending on the arrival order: replicas diverge or lose updates.

(d) Each append carries an identifier (timestamp); in case of conflict the larger identifier is considered the last one. Both replicas sort by timestamp: Bob (3), Ann (5), Cy (8), independently of the arrival order. All replicas converge to the same list.

Why

Convergence needs a result that does not depend on the delivery order. A counter gets it from commutative addition; a list gets it from a deterministic tie-break (the timestamp). Without one of the two, the order of arrival decides the result.

Q38DescribeMargara exercises

In which context are client-centric consistency models relevant? Describe the four client-centric properties and how a consistency protocol can enforce them.

Model answer

Context: mostly-read data, few concurrent updates, eventual consistency, and clients that connect to different replicas over time (mobile users). The models give guarantees from the point of view of a single client.

  • Monotonic reads: if a process reads x, later reads of x return the same or a more recent value.
  • Monotonic writes: a write on x completes before any later write on x by the same process (FIFO for one process; x can be a large part of the store, such as a code library).
  • Read your writes: a read sees the effect of the process's earlier writes (an updated web page, a changed password).
  • Writes follow reads: a write after a read of x takes place on the same or a newer value than the one read (a reply is shown only after the original post).

Protocol. Each write has a unique id (replica id + sequence number). Each client keeps a read-set (ids of writes relevant to its reads) and a write-set (ids of its writes), encodable as vector clocks (latest id from each replica).

  • Monotonic reads: before reading at L2, the client checks that L2 has applied all writes in the read-set.
  • Monotonic writes: the same, with the write-set.
  • Read your writes: the same as monotonic writes (check the write-set before reading).
  • Writes follow reads: first bring the server up to date with the read-set, then perform the write and add it to the write-set.

Why

The client carries its own history from replica to replica. A replica that is behind must catch up before it serves the client.

Q39Exercise

One client uses two local copies L1 and L2 of the store. For each case, which client-centric property is violated, if any? (a) The client reads x at L1, which has applied W1(x). It moves to L2, which has applied W1(x) and then W2(x), and reads x2. (b) Same as (a), but L2 has applied only W2(x), not W1(x). (c) The client writes W1(x) at L1, moves to L2, and writes W2(x) before W1(x) reaches L2. (d) The client changes its password at L1, moves to L2, and logs in with the new password before the change reaches L2. (e) The client reads post p (written by W1) at L1, then replies at L2, where W1 has not arrived yet.

Model answer

  1. None: monotonic reads holds. The set of writes at L2 contains the write the client already saw.
  2. Monotonic reads violated. The value x2 may look "newer", but L2's state does not include W1, which the client has already seen. In the slides, the read at L2 must reflect WS(x1; x2), not WS(x2) alone.
  3. Monotonic writes violated: W2 is performed at L2 before W1 completed there. If W1 arrives later, L2 may end with the older value.
  4. Read your writes violated: the login fails with the new password.
  5. Writes follow reads violated: at L2 the reply exists without the original post, so other users at L2 see a reply to nothing.

Why

All four models ask the same question at the new replica: "does it already contain the writes this client depends on?". They differ only in which writes count: the ones the client read (MR, WFR) or the ones it wrote (MW, RYW).

Q40Exercise

Replicas L1, L2, L3. Write ids are (replica, sequence number), and sets are encoded as vectors [L1, L2, L3]. A client has read-set RS = [3, 1, 0] and write-set WS = [0, 2, 0]. (a) It connects to L2, which has applied [2, 4, 5], and reads x with monotonic reads and read-your-writes. Can L2 answer at once? (b) It then connects to L3, which has applied [3, 1, 6], and writes x with monotonic writes and writes-follow-reads. What must happen first? The new write gets id (L3, 7): what is the new WS?

Model answer

Rule: a replica can serve the request if the relevant set is ≤ its applied vector, entry by entry.

  1. Monotonic reads: RS = [3, 1, 0] vs [2, 4, 5]: the L1 entry is 3 > 2. L2 misses write (L1, 3). L2 must first get it from L1 (or the client waits, or uses another replica). Read your writes: WS = [0, 2, 0] ≤ [2, 4, 5]: OK.
  2. Writes follow reads: RS = [3, 1, 0] ≤ [3, 1, 6]: OK. Monotonic writes: WS = [0, 2, 0] vs [3, 1, 6]: the L2 entry is 2 > 1. L3 must first apply (L2, 2), the client's own earlier write. Then L3 performs the write (L3, 7). New WS = [0, 2, 7].

Why

A vector compresses "all the writes I depend on" into one number per replica. This works because each replica numbers its own writes in order, so "up to 3 from L1" means writes 1, 2 and 3 from L1.

§7

Design strategies and case studies

Core idea. To design a replicated store, decide where to place replicas (permanent, server-initiated, client-initiated), what to propagate (notification, data, operation), and how (push, pull, leases; synchronous or asynchronous; read repair and anti-entropy). NoSQL systems chose availability; NewSQL systems (Spanner, Calvin, VoltDB) give strong guarantees with new techniques to limit the cost.

Q41CompareExam 13 Jul 2015 · 19 Feb 2013

Describe the strategies for propagating updates among replicas: what to propagate, push vs pull, and the propagation strategies in leader-based and leaderless protocols (anti-entropy, gossiping, epidemic algorithms). Why are they used?

Model answer

What: (1) a notification only, used with invalidation: small overhead, avoids propagating writes that will be overwritten; best when reads ≪ writes. (2) The modified data: best when reads ≫ writes. (3) The operation (active replication): very small messages, but each replica recomputes (costly for complex operations), and you must consider side effects.

Leases control the frequency of polling: during the lease the server pushes updates; after it expires the client must pull.

Leader-based: synchronous, asynchronous, semi-synchronous propagation. Leaderless: read repair (a client that reads several replicas detects stale ones and updates them) and anti-entropy (a background process that constantly compares replicas and copies missing data; push, pull or push-pull). Gossiping / epidemic algorithms are anti-entropy strategies: each replica periodically contacts a random peer and exchanges updates, so an update spreads like an infection, reaching all replicas in O(log N) rounds with no central coordinator.

Why

Every choice depends on the read/write ratio: send data where it will be read, and do not push data that will be overwritten before anyone reads it. Epidemic protocols are used because they scale and tolerate failures: no replica is special.

Q42Scenario

Choose replica placement, what to propagate, and push or pull. (a) A stock price is updated 50 times per second; client caches read it about once per minute. (b) A product catalog changes once a day and is read thousands of times per second at many replicas. (c) An update is "apply a 10% discount to all 2 million products". (d) A news site gets a sudden traffic peak from a new country. (e) Static DNS data and the content of a video service.

Model answer

  1. Reads ≪ writes: propagate only a notification (invalidation), or let clients pull on demand. Pushing every new price wastes traffic: most values are overwritten before anyone reads them. Leases can bound how often clients poll.
  2. Reads ≫ writes: push the modified data to all replicas. Each update is read many times, so the transfer pays off, and replicas answer immediately.
  3. Propagate the operation (active replication): one short message instead of 2 million new values. Each replica recomputes. The operation must be deterministic and free of side effects (no "now()", random numbers, or e-mails sent by each replica).
  4. Server-initiated replicas: create replicas dynamically near the new clients to cope with the load; this needs knowledge of the network topology.
  5. Permanent replicas: statically configured, as in DNS and CDNs. Browsers and proxies add client-initiated replicas (caches, possibly shared among clients).

Why

Ask two questions every time: "how often is each update read before it is overwritten?" and "who knows when the data is needed: the server or the client?". Push when the server knows and data is read often; pull when only the client knows.

Q43Scenario

Choose a consistency model and a protocol for each case, and justify. (a) Bank accounts whose balance must never go below zero, in one data center. (b) A shopping cart in a geo-replicated store that must accept items even during a partition. (c) A group chat across continents where replies must never appear before the message they answer. (d) A lock service that elects one master for a cluster. (e) A mobile e-mail client that connects to different servers during the day.

Model answer

  1. Sequential or linearizable (serializable transactions): single leader with synchronous (or semi-synchronous) replication, consensus for failover. Low latency inside the data center makes it affordable. The invariant needs coordination: a CRDT cannot enforce it.
  2. Eventual consistency with a CRDT (for example, a set of "add item" operations), multi leader. It stays available during partitions; concurrent adds merge without conflicts.
  3. Causal consistency, multi leader with vector clocks. It is highly available with sticky clients, and much cheaper than sequential across continents. Unrelated messages can appear in different orders.
  4. Linearizability: everybody must agree, in real time, on who holds the lock. Use a consensus-based replicated log (Raft or Paxos). It is not available during a partition on the minority side; that is the price.
  5. Client-centric models over an eventually consistent store: monotonic reads (a mail never "disappears"), read your writes (a sent mail appears in "Sent"), with read-sets and write-sets carried by the client.

Why

Start from the cost of an anomaly. If an anomaly breaks an invariant (money, locks), pay for strong consistency. If it only looks strange (comment order), choose the weakest model that hides it, because weaker models give latency and availability.

Q44Describe

NoSQL vs NewSQL: what are the two families, and how do Spanner, Calvin and VoltDB provide strong guarantees at reasonable cost?

Model answer

NoSQL (2000s): key-value stores, wide-column, document stores. Operations on single items, so no isolation and no atomic commit needed (no multi-item transactions). Asynchronous and/or multi-leader replication → high availability. NewSQL (2010s): relational, serializable isolation (locking, timestamps), blocking atomic commit, sequential or linearizable replication → strong guarantees, with new techniques to limit costs:

  • Spanner: very large databases, many partitions, each replicated. Standard parts: single leader with Paxos per partition, 2PC across partitions, timestamp concurrency control. Novelty: TrueTime (atomic clocks + GPS) returns an uncertainty interval that surely contains the real time. A read-write transaction commits only after its timestamp is surely past on every node, so timestamp order = real-time order → linearizable. Read-only transactions read the latest value at a TrueTime timestamp without locks.
  • Calvin: a sequencing layer (a replicated log based on Paxos) orders all transactions before execution. Transactions are deterministic and run everywhere in the log order → linearizable. Agreement happens before locks are taken (less contention), and no 2PC is needed: a failed participant does not cause an abort, because any replica of it can vote, and it recovers by replaying the log.
  • VoltDB: developers specify how to partition tables and transactions (for example, hotels and flights both by city). Single-partition transactions run sequentially on that partition with no coordination; other transactions use standard protocols.

Why

Each system removes one expensive piece: Spanner turns clock uncertainty into a short wait, Calvin removes 2PC through determinism, VoltDB avoids coordination through smart partitioning.

Q45Exercise

(a) Spanner: TrueTime has uncertainty ε = 4 ms, so TT.now() returns [t − 4, t + 4] around the real time t. A coordinator calls TT.now() and gets [1000, 1008] ms. It picks the commit timestamp s = 1008. Until when must it wait before it commits and releases its locks, and why? (b) VoltDB: hotels and flights are both partitioned by city. Classify: (1) book a hotel and a flight from Milan's airport, both in the Milan partition; (2) book a Milan hotel and a Rome hotel in one transaction. (c) Calvin: a participant crashes in the middle of a transaction. Why is there no abort?

Model answer

  1. It waits until TT.now() reports an earliest value > 1008, that is until the real time is surely past s. With ε = 4, this happens when t − 4 > 1008, so t > 1012. At the call, t was in [1000, 1008] (about 1004), so the commit wait is about 8 ms = 2ε. After that, every node's clock is past 1008, so any transaction that starts later gets a larger timestamp: timestamp order matches real-time order (linearizable).
  2. (1) Single-partition: it runs sequentially on the Milan partition with no coordination. (2) Multi-partition: it needs the standard (coordinated) protocols, so it is slower. A good partitioning makes case (1) the common case.
  3. The order of transactions was fixed in the replicated log before execution, and transactions are deterministic. Any replica of the failed participant can vote for it, and the crashed node returns to the right state by replaying the log. So there is no 2PC and no abort due to the failure.

Why

Spanner pays the uncertainty interval as latency on every read-write commit. This is why precise clocks matter: with ε = 4 ms the wait is about 8 ms; with NTP-like uncertainty (tens of ms) it would be too slow.
