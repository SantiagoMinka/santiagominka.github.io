§1

Why replicate, and how: protocols

Core idea. Replication gives fault tolerance, availability and performance (latency does not improve like other metrics; the speed of light is a hard limit). The cost is keeping replicas consistent. Three protocol families: single leader, multi leader, leaderless (quorums).

Q1Compare

Describe and compare single leader, multi leader and leaderless replication protocols.

Why

The question is always "who decides the order of writes?". One leader: the leader. Many leaders: nobody, so conflicts must be resolved. Leaderless: a quorum vote.

Q2Exercise

A leaderless store has N = 5 replicas. Which (NR, NW) choices are correct: (2, 4), (3, 3), (1, 5), (3, 2), (4, 2)? What is ROWA?

Model answer

Rules: NR + NW > N (avoids read-write conflicts: every read quorum meets the last write quorum), and NW > N/2 (avoids write-write conflicts: two write quorums meet).

  • (2, 4): 6 > 5, 4 > 2.5 → correct.
  • (3, 3): 6 > 5, 3 > 2.5 → correct.
  • (1, 5): 6 > 5, 5 > 2.5 → correct. This is ROWA: read one, write all. Fast reads, but a write fails if any replica is down.
  • (3, 2): 5 is not > 5 → a read can miss the last write; and 2 < 2.5 → write-write conflicts. Wrong.
  • (4, 2): 6 > 5, but NW = 2 → two concurrent writes can use disjoint quorums. Wrong.

Why

It is the pigeonhole principle: two sets whose sizes add up to more than N must share an element. That shared replica carries the latest version number.

§2

Data-centric consistency models

Core idea. From strongest to weakest: linearizable (one copy, real time) ⇒ sequential (one interleaving, no time) ⇒ causal (causally related writes in the same order) ⇒ FIFO (writes of one process in order). Eventual consistency only promises convergence.

Q3ExerciseExam 18 Jun 2024

P0: W(x)2 W(x)5 R(x)4 W(y)3 · P1: W(y)1 W(x)4 R(y)1 R(y)3 · P2: R(y)1 R(x)2 R(y)3 R(x)5 R(x)4. Is it FIFO, causal, sequential? How do the answers change without the last R(x)4 of P2?

Model answer

Constraints. FIFO: W(x)2 → W(x)5 → W(y)3 (P0); W(y)1 → W(x)4 (P1). Causal adds: P0 reads x = 4 before writing y = 3, so W(x)4 → W(y)3, and also W(y)1 → W(y)3.

Full schedule.

  • FIFO: yes. P2 sees y: 1 → 3, x: 2 → 5 → 4. P0's writes in order (2, 5, then y3), P1's in order (y1, then x4). A valid view for P2: W(y)1, W(x)2, R(y)1, R(x)2, W(x)5, W(y)3, R(y)3, R(x)5, W(x)4, R(x)4.
  • Causal: no. W(x)5 and W(x)4 both causally precede W(y)3 (W(x)5 by P0's program order; W(x)4 because P0 read 4 before writing y). So when P2 reads y = 3, both x writes are already in its view, and no other x write exists. All later reads of x must return the same value, but P2 reads 5 and then 4. Contradiction.
  • Sequential: no (not causal).

Without the last R(x)4: P2 sees y: 1 → 3 and x: 2 → 5. View: W(x)2, W(y)1, W(x)4, W(x)5, W(y)3 respects causality (4 before y3, 5 before y3) → causal: yes, FIFO: yes. Sequential: no. P0 reads 4 after writing 5, so the global order needs W(x)5 → W(x)4 → W(y)3. P2 reads y = 3 and then x = 5: but after W(y)3 the latest x is 4. No global order works. Remove P2's R(y)3 or R(x)5 (or P0's R(x)4) and it becomes sequential.

Why

Method: (1) write FIFO pairs; (2) add causal pairs created by reads followed by writes; (3) for each process, write the order in which it observes values; (4) look for an observation that contradicts a required order (causal) or two processes that observe two writes in opposite orders (sequential). Check every answer with the checker.

Q4ExerciseMargara, exercise 3

P0: W(x)1 R(x)2 W(x)3 · P1: R(x)1 W(x)2 R(x)3 · P2: R(x)K R(x)?. For K = 1, 2, 3, which values can the last read return under FIFO and under sequential consistency?

Model answer

The schedule itself forces W(x)1 → W(x)2 → W(x)3 globally (P1 reads 1 before writing 2; P0 reads 2 before writing 3).

KFIFOSequential
1{1, 2, 3}{1, 2, 3}
2{1, 2, 3}{2, 3}
3{2, 3}{3}

FIFO only keeps P0's order (1 before 3). So after seeing 2, P2 can still see 1 later (1 and 2 come from different processes). After seeing 3, it cannot see 1 (P0's order), but it can see 2. Sequential uses the global order 1 → 2 → 3, so values never go back.

Why

Under weak models, "going back" to an older value is allowed when the two writes have no required order. Ask for each candidate: does seeing it now break a required order?

Q5Compare

Define sequential consistency and linearizability. Write (or describe) a schedule that is sequentially consistent but not linearizable. How can a single-leader protocol give each of them?

Model answer

Sequential: "the result is the same as if all operations were executed in some sequential order, and the operations of each process appear in the order of its program". No time. Linearizable: each operation appears to take effect instantaneously at some moment between its start and its completion: a recency guarantee, the illusion of one copy. It is composable (per variable ⇒ global).

Example. A writes x = 1 on the leader. The leader updates follower 1, then follower 2. In real time: B reads x = 1 from follower 1; after that, C reads x = 0 from follower 2. Sequential order RC(x)0 → W(x)1 → RB(x)1 exists, so it is sequential. It is not linearizable: C's read starts after B's read ended and still returns the old value.

Single leader, sequential: writes go to the leader, FIFO links, sticky clients, synchronous propagation. Linearizable: in addition, make the update atomic across replicas, e.g. lock the followers while a write is in progress so no one reads the old value after anyone read the new one. With failures, you need consensus (Raft).

Why

If B and C talk on another channel, C can learn that it read a stale value: that breaks the single-copy illusion. Linearizability forbids it; sequential consistency does not care about real time.

Q6Describe

Define causal and FIFO consistency, and describe a protocol for each. Which models allow a highly available implementation (a client can read and write while disconnected from other replicas)?

Model answer

Causal: potentially causally related writes are seen by all in the same order; concurrent writes in any order. Causal order: a write is after every earlier operation of the same process; a read is after the write it reads; transitive. Protocol: multi-leader; writes carry vector clocks; a replica applies an update only after all its potential causes. FIFO (PRAM): writes of one process are seen by all in issue order. Protocol: per-process sequence numbers; apply update S from P only after all of P's updates with smaller numbers.

ModelHighly available?
FIFOYes (sticky clients): read the local replica, write locally, propagate later
CausalYes, only if clients are sticky; reads may return old values, never causally inconsistent ones
SequentialNo: needs synchronous coordination with the leader or a quorum
LinearizableNo

Why

Causal and FIFO constrain only the order of things a replica already knows. Sequential and linearizable need agreement with replicas you cannot reach during a partition (CAP).

Q7ScenarioExam 14 Feb 2024

Your application requires FIFO consistency, but the data store provides only eventual consistency. Assuming no failures, does the store satisfy the requirement? If not, can you implement FIFO on top of the eventually consistent store? How?

Model answer

No. Eventual consistency guarantees only that replicas converge when updates stop. A process can see P's second write before its first, or see a value and then an older one. Eventual does not imply FIFO (nor causal, nor sequential).

Yes, you can build it in a layer on top of the store:

  • Each process tags its writes with (process id, sequence number), e.g. store the value together with the tag, or keep per-process version counters.
  • The reading layer keeps, for each writer, the last sequence number applied. When it reads a value with tag (P, s), it accepts it only if all of P's writes with number < s were already seen; otherwise it returns the previously accepted value (or waits/retries).
  • Since the store eventually delivers every write, the missing ones arrive, so the layer progresses.

Alternative: append-only per-process logs in the store, read in sequence-number order.

Why

FIFO is the same mechanism as FIFO multicast: sequence numbers per sender and a hold-back buffer. Eventual consistency gives "everything arrives eventually"; the sequence numbers add "in order".

Q8Describe

Does eventual consistency imply sequential, causal or FIFO consistency? What are CRDTs, why are they useful, and what are their limits?

Model answer

No to all three: eventual consistency says nothing about the order of intermediate values, only that replicas converge.

CRDTs (conflict-free replicated data types) converge even when updates arrive in different orders, because operations commute. Example: a counter stores the set of increments/decrements, not the last value. An append-only list with last-write-wins on timestamps converges to the same order.

Useful: no coordination, high availability, automatic convergence. Limits: only for data types with commutative semantics; temporary "wrong" values; cannot express invariants that need coordination (e.g. a balance that must stay ≥ 0).

Why

Eventual consistency is popular because conflicts are rare in practice (users mostly write to one replica) and networks are fast. CRDTs make the rare conflicts harmless.

Q9CompareExam 25 Feb 2015 · 23 Sep 2015

Why were consistency models with synchronization variables introduced? How do they work?

Model answer

FIFO consistency still makes every write visible to every process, even processes that do not care, and even writes inside a critical section that nobody should see yet. Models with synchronization variables make writes visible only when a process asks for it through the variable (e.g. synchronize, acquire/release). The programmer forces consistency only where needed: at the end of a critical section (to distribute writes) and at the beginning of a reading session (to see others' writes).

(Classic variants in the literature: weak consistency with one synchronize operation; release consistency with acquire/release; entry consistency with one lock per data item.)

Why

Most programs already synchronize with locks. Tying propagation to synchronization points removes useless traffic between them, at the cost of putting the responsibility on the programmer.

§3

Client-centric models and design strategies

Core idea. When a client moves between replicas, client-centric models give guarantees for that client only: monotonic reads, monotonic writes, read your writes, writes follow reads. Design choices: where to place replicas, what to propagate, push or pull.

Q10Describe

In which context are client-centric models relevant? Describe the four properties and how a protocol can enforce them.

Model answer

Context: mostly-read data, few concurrent updates, eventual consistency, and clients that connect to different replicas over time (mobile users).

  • Monotonic reads: after reading x, later reads return the same or a newer value.
  • Monotonic writes: a write on x completes before any later write on x by the same process (FIFO for one process).
  • Read your writes: a read sees the effect of the process's earlier writes (e.g. a changed password, an updated web page).
  • Writes follow reads: a write after a read of x happens on the same or a newer value (a reply is shown only after the original post).

Protocol. Each write has an id (replica id + sequence number). Each client keeps a read-set (writes relevant to its reads) and a write-set (its writes), encodable as vector clocks. Monotonic reads: before reading at L2, L2 must have applied the read-set. Monotonic writes and read your writes: same with the write-set. Writes follow reads: bring the server up to date with the read-set, then add the write to the write-set.

Why

The client carries its own history from replica to replica. A replica that is behind must catch up before serving the client.

Leases combine them: push during the lease, then pull.

Leader-based: synchronous, asynchronous, semi-synchronous. Leaderless: read repair (a client that sees stale replicas updates them) and anti-entropy (background exchange; push, pull or both; gossip/epidemic strategies).

Replica placement: permanent (DNS, CDN), server-initiated (to follow load), client-initiated (caches).

Why

Every choice depends on the read/write ratio: send data where it will be read, and do not push data that will be overwritten before anyone reads it.

Q12Describe

NoSQL vs NewSQL: how do Spanner, Calvin and VoltDB provide strong guarantees at reasonable cost?

Model answer

NoSQL (2000s): single-item operations, no multi-item transactions, asynchronous or multi-leader replication → high availability. NewSQL (2010s): relational, serializable transactions, atomic commit, sequential/linearizable replication, with new techniques to cut cost:

  • Spanner: Paxos per partition, 2PC across partitions, timestamps. TrueTime (atomic clocks + GPS) returns an uncertainty interval; a transaction commits only after the interval has surely passed, so timestamp order = real-time order → linearizable. Read-only transactions read at a timestamp without locks.
  • Calvin: a replicated sequencing layer (Paxos log) orders all transactions before execution; transactions are deterministic and run in that order everywhere. No 2PC; less lock contention; a failed participant recovers by replaying the log.
  • VoltDB: developers partition tables and transactions (e.g. by city); single-partition transactions run sequentially without coordination.

Why

Each system removes one expensive piece: Spanner replaces clock uncertainty with waiting, Calvin removes 2PC with determinism, VoltDB avoids coordination with smart partitioning.
