§1

Why simulate: ways to study a system, emulation, models

Core idea. You can study a system by experiments on the actual system or on a model. A model is physical or mathematical; a mathematical model is solved analytically or by simulation. Network emulation sits in between: the real software runs on an imitated network. It is often important to analyze before building, and analysis needs a model.

Q1Describe

Describe the ways to study a system (Law and Kelton, Figure 1.1). Where does simulation sit in this classification?

Model answer

  • Experiment with the actual system: you change the real system and measure it. This is the most realistic option, but often it is too expensive, too risky, or the system does not exist yet.
  • Experiment with a model: you build a representation of the system.
    • Physical model: a real object at a smaller scale (a testbed, a scale model).
    • Mathematical model: logical and quantitative relations. If the model is simple, you get an analytical solution (a formula). If it is too complex, you use simulation: you execute the model and observe it.

Simulation is a mathematical model that you solve numerically by running it. Network emulation is between "actual system" and "model": the real software runs, but the network is imitated.

Why

Each step down the tree trades realism for cost and control. The common trap is to call emulation a kind of simulation. In emulation the system under test is the real code; only the environment is fake.

Q3Compare

Compare network emulation and simulation. Give examples of emulation tools and say what they can alter.

Model answer

Emulation: the real system runs on an emulated network. The network emulator appears to be a network to the OS. A component or device alters the packet flow to imitate the target environment, for example a WAN or a wireless network. It can introduce packet delay, loss, duplication and reordering. It is often coupled with node emulation (virtual machines such as UML, VMware, VirtualBox). Tools: Mininet, FreeBSD Dummynet (used in Emulab), Linux NetEm, and more user-friendly tools such as marionnet and netkit.

Simulation: a model of the whole system (nodes and network) runs inside a simulator. No real code and no real network run. Simulated time is not wall-clock time.

EmulationSimulation
What runsReal software, real OS stackA model of software and network
TimeReal timeSimulated time (the clock jumps)
ScaleLimited by the real machinesVery large (thousands of nodes)
Realism of the softwareHigh: it is the real codeOnly as good as the model
ReproducibilityPartial (real scheduling, real timing)Full, with the same seeds
WhenCode exists; test it in a hard environmentAnalyze before building

Why

Testing distributed systems in large or complex deployments is hard. Emulation keeps the real code and fakes the environment. Simulation fakes everything but gives scale and control. The key phrase from the slides is "appears to be a network to the OS".

Q4Scenario

Pick emulation or simulation for each case and justify: (a) you want to check that your Java chat server handles 200 ms delay and 5% packet loss between 4 machines; (b) you want to compare two gossip protocols on 100,000 peers before you write any code; (c) you want to check that your real Kafka client handles packet reordering; (d) you want to repeat exactly the same run to debug a rare race; (e) you want to estimate the mean waiting time of a token ring mutual exclusion protocol for 6, 50 and 500 nodes.

Model answer

  1. Emulation (for example NetEm or Mininet). The code exists and the scale is small. NetEm can add the delay and the loss.
  2. Simulation. The code does not exist (analyze before building) and 100,000 real nodes are too many to emulate.
  3. Emulation. You test the real client. The emulator can reorder packets.
  4. Simulation. A discrete event simulation with fixed seeds gives exactly the same history at every run. Emulation runs in real time with real scheduling, so a rare race may not repeat.
  5. Simulation. You need many configurations and large sizes. You change only the ini file.

Why

Choose emulation when the question is "does my real code work in this network?". Choose simulation when the question is "how does this design perform?", or when the scale or the need for reproducibility is high. The trap: emulation is not reproducible in general, because the real OS and the real clock are involved.

Q5Exercise

Why is it often important to "analyze before building"? Define the three pairs of model classes (analytical vs operational, discrete vs continuous, deterministic vs stochastic). Then classify: (a) the formula "round time = n · d" for a token ring; (b) an OMNeT++ token ring with uniform(300s,500s) request periods; (c) a set of differential equations for the temperature of a server room.

Model answer

Analyze before building: design errors found after the system is built cost much more. Analysis needs a model of the system. Simulation is a special form of analysis: you obtain a history of system execution and you analyze it.

  • Analytical: the model is a set of equations; you compute the result. Operational: the model describes the behavior step by step; you execute it.
  • Discrete: the state changes at separate instants (a message arrives). Continuous: the state changes continuously in time (a temperature, a fluid level).
  • Deterministic: the same inputs always give the same output. Stochastic: some inputs are random variables.
ModelClassification
(a) n · dAnalytical, discrete, deterministic
(b) OMNeT++ token ringOperational, discrete, stochastic (random inputs)
(c) differential equationsAnalytical, continuous, deterministic

Why

The slides say discrete event simulation uses a "discrete, deterministic, operational model". This looks strange when the model uses random numbers. The pseudo-random generator is deterministic: with the same seed you get the same history. Randomness is an input; the execution of the model stays deterministic.

§2

Discrete event simulation

Core idea. A discrete event simulation has a list of events (timestamped objects), a simulation clock, state variables and performance indicators, and an event processing function. The main loop removes the first event, advances the clock to its timestamp and passes the event to the function. The function updates state and indicators and creates new events. A discrete event simulator implements this loop for you.

Q6Describe

Describe the elements and the main loop of a discrete event simulation.

Model answer

  • List of events: timestamped objects, kept ordered by timestamp (a priority queue).
  • Simulation clock: the current simulated time.
  • State variables: describe the system now (queue length, "server busy", "who has the token").
  • Performance indicators: the values you want to measure (total waiting time, number of messages).
  • Event processing function: takes one event, updates the state variables and the indicators, and creates new events with timestamps ≥ the clock.
forever:
  e = take the first event from the list and remove it
  clock = e.timestamp          // advance the clock
  process(e)                   // update state and indicators, create new events

The loop stops when the list is empty or when a time limit is reached (in OMNeT++: sim-time-limit).

Why

Nothing happens between two events, so the clock jumps directly to the next event. One hour of network activity can run in seconds. A trap: an event must never get a timestamp smaller than the clock. That would change the past and break causality.

Q7Exercise

Hand-simulate a single server with a FIFO queue. Jobs arrive at t = 0, 1, 2, 11 with service times 3, 2, 4, 1. Events: ARR (arrival) and DEP (end of service). Rules: on ARR, if the server is idle, start service and schedule DEP at t + service; else put the job in the queue. On DEP, if the queue is not empty, take the first job, add its waiting time, and schedule its DEP; else the server becomes idle. Give the clock and the state after each event. Then give: total waiting time, mean waiting time, server utilization, maximum queue length, time-average queue length.

Model answer

ClockEventActionBusyQueueTotal wait
0ARR J1start J1, DEP J1 at 3yes00
1ARR J2queue J2yes10
2ARR J3queue J3yes20
3DEP J1start J2 (wait 3−1 = 2), DEP J2 at 5yes12
5DEP J2start J3 (wait 5−2 = 3), DEP J3 at 9yes05
9DEP J3queue empty → idleno05
11ARR J4start J4 (wait 0), DEP J4 at 12yes05
12DEP J4idle; list empty → stopno05
  • Total waiting time = 0 + 2 + 3 + 0 = 5; mean waiting time = 5 / 4 = 1.25.
  • Busy time = [0, 9] + [11, 12] = 10; utilization = 10 / 12 ≈ 0.83.
  • Maximum queue length = 2 (in [2, 3)).
  • Area under the queue-length curve = 1·1 + 2·1 + 1·2 = 5; time-average queue = 5 / 12 ≈ 0.42.

Why

The clock takes only the values 0, 1, 2, 3, 5, 9, 11, 12. It never visits 4, 6, 7, 8 or 10, because nothing happens there. To compute time-based indicators (utilization, mean queue), you accumulate "value × time since the last event" at each event. Note that the area under the queue curve equals the total waiting time (Little's law in a simple form).

Q9Describe

What is a discrete event simulator? What does it provide besides the main loop? Name some examples used for networks and distributed systems.

Model answer

A discrete event simulator is software that implements the event loop and simplifies the job of writing discrete event simulations. You write only the state and the event processing.

  • A library of basic, general-purpose elements: random number generators, containers, statistics.
  • A library of existing models: hosts, routers, switches, protocols.

Examples: OpNet, QualNet, JiST/SWANS, Parsec/GloMoSim, J-Sim, ns-2, OMNeT++.

Why

The loop itself is ten lines. The value of a simulator is in the libraries: correct random number streams, statistics, and validated models of real network elements that you do not have to write again.

§3

OMNeT++: component model and NED

Core idea. OMNeT++ gives a component model, a C++ class library (simulation kernel and utilities), an infrastructure to assemble and configure simulations (NED and ini files), runtime environments (Tkenv, Cmdenv) and an Eclipse-based IDE. Simple modules hold behavior in C++; compound modules contain submodules and connections. Modules exchange messages through gates. The whole simulation is an instance of the highest-level module (the network).

Q10Describe

What does OMNeT++ provide? Describe each part in one or two sentences, and name some simulation frameworks built on it.

Model answer

  • Component model: structures complex simulations as reusable modules connected through gates.
  • C++ class library: the simulation kernel (event list, clock, loop) and utility classes for random number generation, statistics collection, topology discovery.
  • Assembly and configuration: the NED language describes modules and wiring; omnetpp.ini gives the parameter values for each run.
  • Runtime environments: Tkenv is graphical (animation, inspection, step by step; Qtenv in recent versions). Cmdenv is command-line, for fast batch runs.
  • IDE: Eclipse-based, to design, run and evaluate simulations (NED editor, result analysis).

Frameworks developed separately: INET (Internet protocols), Mobility Framework, MiXiM, Castalia (wireless sensor networks).

Why

The split is the main idea: structure (NED), behavior (C++) and experiments (ini) are separate. You can change the experiment without recompiling, and reuse a module in many networks. Use Tkenv to understand and debug; use Cmdenv to collect results fast.

Q11Compare

Compare simple modules and compound modules. What are gates and connections? How is the module hierarchy built?

Model answer

Simple moduleCompound module
NED keywordsimplemodule (the top level is a network)
NED contentInterface only: parameters and gatesParameters, gates, submodules, connections
BehaviorA C++ class extending cSimpleModuleNo C++ code; behavior comes from its submodules
Position in hierarchyLeavesInner nodes

Gates are the input and output ports of a module. A module sends messages only through its output gates. Connections link an output gate to an input gate. A connection can carry channel properties: delay, datarate, ber, per. In a compound module, a connection can link a submodule gate to a gate of the parent (for example mac.phyOut --> out).

Compound modules contain simple or compound modules, so modules form a tree. The root is the network; the simulation is an instance of it.

Why

A compound module is only packaging: at run time, messages travel between simple modules. The gates of a compound module are pass-through points. This lets you build a "host" once and use it many times.

Q12Code

Read the EtherStation compound module from the slides. (a) Which submodules does it have, and which are simple modules? (b) List the gates that a message from app passes on its way to the station's out gate. (c) The slide has the line llc.macOout --> mac.llcIn;. What happens at build time, and how do you fix it?

module EtherStation {
  gates:
    input in;  output out;
  submodules:
    app: EtherTrafficGen;  llc: EtherLLC;  mac: EtherMAC;
  connections:
    app.out --> llc.hlIn;
    app.in <-- llc.hlOut;
    llc.macIn <-- mac.llcOut;
    llc.macOout --> mac.llcIn;
    mac.phyIn <-- in;
    mac.phyOut --> out;
}

Model answer

  1. Three submodules: app (EtherTrafficGen), llc (EtherLLC), mac (EtherMAC). EtherMAC is a simple module (its NED is simple EtherMAC with gates phyIn, phyOut, llcIn, llcOut). The other two are also leaves with C++ code.
  2. app.out → llc.hlIn; LLC processes it and sends on llc.macOut → mac.llcIn; MAC sends on mac.phyOut → EtherStation.out.
  3. The gate macOout does not exist in EtherLLC. NED checks gate names when the network is set up, so the simulation stops with an error such as "no such gate". Fix: llc.macOut --> mac.llcIn;.

Why

The arrow shows the direction of the messages. a --> b and b <-- a mean the same thing. The left side of --> must be an output gate and the right side an input gate. The parent gates in and out only forward messages to and from the inner modules.

Q14Code

Write the NED network of the token ring lab. The simple module TRNode has the parameters sendMsgOnInit (bool, default false), reqPeriod and usePeriod (volatile, in seconds, defaults uniform(300s,500s) and uniform(1s,2s)), and the gates in, out. Define a channel MyChannel with delay uniform 90–110 ms and datarate normal(1024 kbps, 1 kbps). The network TokenRing has n nodes (default 5) in a ring.

Model answer

simple TRNode {
  parameters:
    bool sendMsgOnInit = default(false);
    volatile double reqPeriod @unit(s) = default(uniform(300s,500s));
    volatile double usePeriod @unit(s) = default(uniform(1s,2s));
  gates:
    input in;
    output out;
}

channel MyChannel extends ned.DatarateChannel {
  delay = uniform(90ms,110ms);
  datarate = normal(1024kbps,1kbps);
}

network TokenRing {
  parameters:
    int n = default(5);
  submodules:
    node[n]: TRNode;
  connections:
    for i=0..n-1 {
      node[i].out --> MyChannel --> node[(i+1)%n].in;
    }
}

Why

node[n] is a submodule vector, and the for loop builds the connections. (i+1)%n closes the ring: node[n−1] sends to node[0]. Each node has exactly one in and one out gate, so the token moves in one direction only. Defining MyChannel once avoids repeating the delay and datarate on each link.

§4

Simple modules, messages, results, random numbers, ini files

Core idea. A simple module is a C++ class that extends cSimpleModule, is registered with Define_Module, and redefines initialize(), handleMessage() and finish(). Messages are subclasses of cMessage, written in a small message language. Results go to output vectors (.vec) and output scalars (.sca). OMNeT++ gives several RNG streams that you map to modules in omnetpp.ini.

Q15Describe

How do you implement a simple module? Describe the role of initialize(), handleMessage(), finish(), Define_Module, par() and send(). What happens if you forget Define_Module?

Model answer

  • Write a C++ class with the same name as the NED simple module. It extends cSimpleModule.
  • initialize(): called once after the network is built and before the first event. Read parameters, create self-messages, send the first messages.
  • handleMessage(cMessage *msg): called for every event addressed to the module (a message from another module or a self-message). This is the event processing function.
  • finish(): called at the normal end of the simulation. Record scalars, free resources.
  • Define_Module(Name): registers the class, so the kernel can create it from the NED name.
  • par("name"): reads a NED parameter (its value comes from NED or from omnetpp.ini).
  • send(msg, "gateName"): sends a message through an output gate to the connected module.

Without Define_Module, the program compiles, but at network setup the kernel cannot find the class. The run stops with an error like "class not found".

Why

NED and C++ are linked only by name, through a registry. The kernel reads NED, finds "Txc1", and asks the registry for the class "Txc1". The trap: the error appears at run time, not at compile time.

Q16Code

Write the C++ of two simple modules. Source sends a message "job" on gate out after each interval read from the volatile parameter interArrival. Sink counts the jobs it receives, records the delay of each job (now minus creation time) in an output vector, and records the count as a scalar at the end.

Model answer

class Source : public cSimpleModule {
  private:
    cMessage *sendEvt = nullptr;
  protected:
    virtual void initialize() override {
      sendEvt = new cMessage("sendEvt");
      scheduleAt(simTime() + par("interArrival").doubleValue(), sendEvt);
    }
    virtual void handleMessage(cMessage *msg) override {
      // only the self-message arrives here
      send(new cMessage("job"), "out");
      scheduleAt(simTime() + par("interArrival").doubleValue(), sendEvt);
    }
  public:
    virtual ~Source() { cancelAndDelete(sendEvt); }
};
Define_Module(Source);

class Sink : public cSimpleModule {
  private:
    long count;
    cOutVector delayVec;
  protected:
    virtual void initialize() override {
      count = 0;
      delayVec.setName("JobDelay");
    }
    virtual void handleMessage(cMessage *msg) override {
      count++;
      delayVec.record(simTime() - msg->getCreationTime());
      delete msg;                       // the sink owns it now
    }
    virtual void finish() override {
      recordScalar("#received", count);
    }
};
Define_Module(Sink);

Why

A timer is a self-message: scheduleAt puts it in the event list, and it comes back to the same module. The source reuses one self-message object. Each read of a volatile parameter gives a new random value, so the intervals differ. The sink must delete each message it receives; otherwise memory grows and OMNeT++ reports undisposed objects.

Q17Code

Message classes. Define a message NetworkPacket with fields srcAddr, destAddr and hopCount. What does OMNeT++ generate from it? Write the lines that create a packet from 3 to 7 and, in the receiver, increment its hop count.

Model answer

// NetworkPacket.msg (slide syntax)
message NetworkPacket {
  fields:
    int srcAddr;
    int destAddr;
    int hopCount = 0;
}

The message compiler (opp_msgc, called by the makefile) generates NetworkPacket_m.h and NetworkPacket_m.cc. They contain a C++ class NetworkPacket that extends cMessage, with a getter and a setter for each field.

// sender
NetworkPacket *p = new NetworkPacket("data");
p->setSrcAddr(3);
p->setDestAddr(7);
send(p, "out");

// receiver, inside handleMessage(cMessage *msg)
NetworkPacket *p = check_and_cast<NetworkPacket *>(msg);
p->setHopCount(p->getHopCount() + 1);

Why

handleMessage always receives a cMessage*. You must cast it to read the fields. check_and_cast stops the simulation with a clear error if the type is wrong. Use the keyword packet instead of message to get a cPacket subclass: only packets have a bit length and a bit error flag.

Q18Describe

How are results collected in OMNeT++? Compare output vectors and output scalars, and say what statistics classes and signals add.

Model answer

  • Simple modules record results in C++. They go to an output vector file (.vec) and an output scalar file (.sca).
  • Output vectors capture behavior over time. Each vector is a named series of (timestamp, value) pairs, for example cOutVector waitingTime with waitingTime.record(x). In omnetpp.ini you can enable or disable each vector, or limit recording to a simulation time interval.
  • Output scalars contain summary statistics: one value per run, for example the number of packets sent or the average hop-to-hop delay. Typical call: recordScalar("#sent", numSent) in finish().
  • Statistics classes collect and organize values, for example cLongHistogram (min, max, mean, standard deviation, distribution). See tictoc15.
  • Signals decouple the model from statistics collection. The module only emits a value (emit(signal, value)). The NED @statistic property, or the ini file, decides what to record: vector, histogram, mean, count. See tictoc16.

Why

Vectors are large (one entry per event) and show trends and transients. Scalars are small and easy to compare across many runs. With signals, you change what you measure without touching the C++ code. This is the same "separate model from experiment" idea as NED vs ini.

Q19Exercise

The slide shows these Tictoc16 lines. Explain each one. Then write lines that (a) disable all output vectors except WaitingTime in the token ring, and (b) record vectors only between 600 s and 3600 s.

**.tic[1].hopCount.result-recording-modes = +histogram
**.tic[0..2].hopCount.result-recording-modes = -vector

Model answer

  • Line 1: for module tic[1], the statistic hopCount also records a histogram (+ adds a mode to the default modes).
  • Line 2: for tic[0], tic[1], tic[2] (the range 0..2), the statistic does not record the vector (- removes a mode). The other modes stay.
# (a) the first matching line wins, so the specific line goes first
**.WaitingTime.vector-recording = true
**.vector-recording = false

# (b) keep only the steady part of the run
**.vector-recording-intervals = 600s..3600s

Why

OMNeT++ reads ini keys top-down and uses the first key that matches. A general line placed before a specific one hides it. Cutting the first part of the run removes the warm-up transient (for example, the period when no node needs the resource yet) and keeps the vector files small.

Q20Describe

How does OMNeT++ manage random numbers? Explain RNG streams and their mapping, seeding, distributions, and what happens when a parameter is assigned a random variate such as exponential(0.2).

Model answer

  • OMNeT++ provides a configurable number of RNG instances (streams). In omnetpp.ini you map them freely to individual simple modules. Example from the slides: all traffic generators use global stream 0, all MACs use stream 1 for backoff, the physical layer uses streams 2 and 3 for the radio channel.
  • Seeding is automatic or manual. Manual seeds also come from the ini file.
  • Many distributions (uniform, exponential, normal, truncnormal, …) are available from both NED and C++.
  • A non-const (volatile) parameter can be a random variate like exponential(0.2). The C++ code gets a different number each time it reads the parameter.
num-rngs = 2
**.gen[*].rng-0 = 0      # local stream 0 of generators -> global stream 0
**.mac.rng-0 = 1         # local stream 0 of MACs -> global stream 1
seed-0-mt = 1234         # manual seed of global stream 0

Why

With one shared stream, a change in the MAC (one more random draw) shifts all the numbers seen by the traffic generators. Two runs then differ in traffic too, and you cannot compare them fairly. Separate streams keep the traffic identical while you change the MAC. Fixed seeds make a run reproducible.

Q21Exercise

In the lab, reqPeriod is declared volatile double reqPeriod @unit(s) = default(uniform(300s,500s)). The channel has delay = uniform(90ms,110ms). (a) A node calls par("reqPeriod") three times. Does it get the same value? (b) What changes if you remove volatile? (c) With n = 6, how many values of the link delay are drawn during a run, and is the token round time constant?

Model answer

  1. No. A volatile parameter evaluates its expression at every read. Each call draws a new value in [300 s, 500 s].
  2. Without volatile, the expression is evaluated once, at network setup. Each node gets one random value and uses it for the whole run. Node 2 could request every 312 s and node 4 every 487 s, always.
  3. Channel parameters are not volatile: each of the 6 channels draws its delay once. So there are 6 draws. The links have different delays, but each link keeps its delay. The idle round time is the sum of the 6 delays: constant during the run, between 0.54 s and 0.66 s, about 0.6 s on average.

Why

The trap is to think that uniform() always means "random at every use". It depends on volatile. For a request period you want a new value each time (volatile). For a link property, a fixed value per link is more realistic: a cable does not change its length.

§5

The TicToc example, compiling and running

Core idea. TicToc has two nodes that pass a message back and forth. The steps add one concept each: tictoc1 the basic module, tictoc4 parameters and a counter, tictoc5 NED inheritance, tictoc8 timeouts with self-messages and message loss, tictoc9 copies of messages with sequence numbers. You build with opp_makemake and make, then run the executable.

Q23Code

Explain tictoc1. In Txc1, why does only tic send a message in initialize()? Why does handleMessage not delete the message? When does the simulation end?

void Txc1::initialize() {
  if (strcmp("tic", getName()) == 0) {
    cMessage *msg = new cMessage("tictocMsg");
    send(msg, "out");
  }
}
void Txc1::handleMessage(cMessage *msg) {
  send(msg, "out");
}

Model answer

  • tic and toc are two instances of the same class. getName() returns the submodule name. Only the module called "tic" creates the first message, so exactly one message exists.
  • handleMessage sends the same message object back on out. Sending transfers the ownership to the receiver, so the object is reused, not leaked.
  • The message bounces forever: tic at 0, toc at 0.1 s, tic at 0.2 s, … The event list is never empty. The run ends only by a time limit, an event limit, or the user.

Why

Comparing the name is a quick trick. Tictoc4 replaces it with a parameter, sendMsgOnInit, which is cleaner: the role comes from configuration, not from a hard-coded name.

Q24Exercise

Tictoc4: each node has counter = par("limit") (NED default 2). On each received message it decrements the counter; at 0 it deletes the message, else it sends it back. Link delay is 100 ms. (a) Config Tictoc4 sets Tictoc4.toc.limit = 5. Who deletes the message, at what time, and how many sends happen? (b) Config Tictoc5 sets **.limit = 5. Same questions.

Model answer

tic receives at 0.2, 0.4, 0.6, … s. toc receives at 0.1, 0.3, 0.5, … s.

  1. tic limit = 2, toc limit = 5. toc at 0.1 s: 4, send. tic at 0.2 s: 1, send. toc at 0.3 s: 3, send. tic at 0.4 s: 0 → tic deletes the message at t = 0.4 s. Sends: initial + 3 = 4.
  2. Both limits are 5. toc reaches 0 at its 5th reception: toc deletes at t = 0.9 s (tic is at 1 after 4 receptions, at 0.8 s). Sends: initial + 8 = 9.

When the message is deleted, the event list becomes empty and the simulation ends.

Why

With equal limits the node that receives first (toc) reaches zero first. The trap in (b) is to count 0.2 s per reception for toc: toc receives every 0.2 s starting at 0.1 s, so the 5th reception is at 0.1 + 4·0.2 = 0.9 s. WATCH(counter) lets you see the counter in Tkenv.

Q25Describe

What does tictoc5 change with respect to tictoc4? Explain simple Tic5 extends Txc5 and the difference between sendMsgOnInit = default(false) and sendMsgOnInit = true.

Model answer

  • tictoc4 sets the parameters of tic and toc inside the network, in the submodule blocks. tictoc5 uses NED inheritance: Tic5 and Toc5 extend Txc5. They inherit the parameters and gates and only fix sendMsgOnInit and the display icon. The network just writes tic: Tic5; toc: Toc5;.
  • default(false) is a default: omnetpp.ini can override it. = true (without default) is a fixed assignment: the ini file cannot change it.
  • The C++ class is the same (Txc5) for both. The NED subtypes change only parameters. In OMNeT++ a derived simple module uses the C++ class of its parent unless you give a new one.

Why

Inheritance moves the role into a type: a "Tic" is a node that starts. You can now place many Tic5 nodes in other networks without repeating the parameters. The default vs fixed value difference is a common trap in ini questions.

Q26Code

Find the error. This is Tic8::handleMessage as on the slide. Toc8 sends back the same message as acknowledgement, or deletes it with probability 0.1. Explain what the code does, and find the memory problem.

void Tic8::handleMessage(cMessage *msg) {
  if (msg == timeoutEvent) {
    EV << "Timeout expired, resending message and restarting timer\n";
    cMessage *msg = new cMessage("tictocMsg"); send(msg, "out");
    scheduleAt(simTime()+timeout, timeoutEvent);
  } else {
    EV << "Timer cancelled.\n";
    cancelEvent(timeoutEvent);
    cMessage *msg = new cMessage("tictocMsg"); send(msg, "out");
    scheduleAt(simTime()+timeout, timeoutEvent);
  }
}

Model answer

  • msg == timeoutEvent: the self-message fired, so no reply came in time. Tic sends a new message and schedules the timeout again (the self-message is no longer in the list, so it can be reused).
  • Else a reply arrived. cancelEvent removes the pending timeout from the event list. Tic sends the next message and schedules a new timeout.
  • Error: in the else branch the received reply (the parameter msg) is never deleted. The inner cMessage *msg hides the parameter, and the received object is lost. Each successful round leaks one message. At the end OMNeT++ reports undisposed objects. Fix: add delete msg; before creating the new message (and better, use a different name such as newMsg).

In Toc8 the loss is modeled by if (uniform(0,1) < 0.1) { bubble("message lost"); delete msg; }. A deleted message never arrives, so tic sees a timeout.

Why

Rule: the module that receives a message owns it. It must send it on, store it, or delete it. The trap is name shadowing: the code "looks" correct because it uses the name msg in both places, but they are two different objects.

Q27Exercise

In TicToc8, the link delay is 100 ms each way, the timeout is 1 s, and toc loses each message independently with probability 0.1. (a) What is the expected number of messages tic sends per successful reply? (b) What is the expected time per successful exchange? (c) About how many replies does tic get in 100 s of simulated time? (d) Is 1 s a good timeout here?

Model answer

  1. Each try succeeds with probability 0.9. The number of tries is geometric: 1 / 0.9 ≈ 1.11 messages.
  2. A success costs 0.2 s (round trip). Each failure costs 1 s (the timeout, measured from the send). The expected number of failures is 0.1 / 0.9 ≈ 0.111. Expected time = 0.2 + 0.111 · 1 ≈ 0.311 s.
  3. 100 / 0.311 ≈ 321 replies.
  4. The minimum safe value is the round trip, 0.2 s; with fixed delays there is no jitter. A 1 s timeout is safe but slow: each loss wastes 0.8 s more than needed. A timeout of, for example, 0.3 s gives 0.2 + 0.111 · 0.3 ≈ 0.233 s per exchange.

A quick Monte Carlo run in Python gives 0.311 s, as computed.

Why

This is the classic timeout trade-off. Too short: the timeout fires before a correct reply, and you send duplicates. Too long: you wait for nothing after a loss. The token ring lab has the same trade-off, with much larger numbers.

Q28Compare

Compare Tic8 and Tic9. Why does Tic9 keep the original message and send a copy made with dup()? What is seq for? What does Toc9 send back?

Model answer

  • Tic8 creates a brand-new message for each send, also on a retransmission. It cannot really "resend the same message".
  • Tic9 keeps the current message in the member message. A sent message belongs to the receiver, who may delete it (Toc9 deletes it when it "loses" it, and also after it replies). If tic sent the original, it could not use it again. So sendCopyOf() sends msg->dup(), and the original stays with tic for a possible retransmission.
  • generateNewMessage() names each message tic-1, tic-2, … with ++seq. A retransmission keeps the same name, so you can see that it is the same logical message.
  • On the reply, tic deletes the reply and the stored original, cancels the timeout, creates the next message, and sends a copy.
  • Toc9 deletes the received message and sends back a new message "ack". In Toc8 the same object came back as acknowledgement.
  • The destructor ~Tic9() calls cancelAndDelete(timeoutEvent) and delete message.

Why

This is stop-and-wait with retransmission. In a real protocol the sender keeps a copy until it gets the acknowledgement. Ownership in OMNeT++ makes this explicit: once you call send, you must not touch that object again.

§6

Lab: the token ring simulation

Core idea. The lab simulates token ring mutual exclusion. Each TRNode needs the resource after reqPeriod, waits for the token, keeps it for usePeriod, then forwards it. It records the waiting time (vector) and the number of sends (scalar). The exercises: make the channels lossy (ber/per, hasBitError()), rebuild a lost token with a leader timeout, and measure the protocol performance.

Q30Code

This is TRNode (reconstructed from the lab files). Explain what each part does: the members, initialize(), each branch of handleMessage(), and finish().

class TRNode : public cSimpleModule {
  private:
    cMessage *needResEvt, *finishedUsingResEvt, *token;
    long numSent;
    bool needRes;
    simtime_t startWaitingTime;
    cOutVector waitingTime;
  protected:
    virtual void initialize() override;
    virtual void handleMessage(cMessage *msg) override;
    virtual void finish() override;
};
Define_Module(TRNode);

void TRNode::initialize() {
  needResEvt = new cMessage("Need");
  finishedUsingResEvt = new cMessage("Finish");
  token = nullptr;
  numSent = 0; needRes = false;
  waitingTime.setName("WaitingTime");
  scheduleAt(simTime() + par("reqPeriod").doubleValue(), needResEvt);
  if (par("sendMsgOnInit").boolValue()) {
    token = new cMessage("Token");
    send(token, "out"); numSent++;
  }
}

void TRNode::handleMessage(cMessage *msg) {
  if (msg == needResEvt) {
    needRes = true;
    startWaitingTime = simTime();
    bubble("Need resource");
  } else if (msg == finishedUsingResEvt) {
    needRes = false;
    send(token, "out"); numSent++;
    scheduleAt(simTime() + par("reqPeriod").doubleValue(), needResEvt);
  } else {                                   // the token arrived
    token = msg;
    if (needRes) {
      waitingTime.record(simTime() - startWaitingTime);
      scheduleAt(simTime() + par("usePeriod").doubleValue(), finishedUsingResEvt);
    } else {
      send(token, "out"); numSent++;
    }
  }
}

void TRNode::finish() {
  recordScalar("#sent", numSent);
  cancelAndDelete(needResEvt);
  cancelAndDelete(finishedUsingResEvt);
}

Model answer

  • Members. Two self-messages are the node's timers: needResEvt ("I need the resource now") and finishedUsingResEvt ("I finished using it"). token points to the token while the node holds it. needRes and startWaitingTime are state variables. numSent and waitingTime are performance indicators.
  • initialize(). Creates the two timers. Schedules the first need after a random reqPeriod (volatile, so each node gets its own value). Only the node with sendMsgOnInit = true (node[0] in the ini) creates the single token and sends it. Names the output vector.
  • Need branch. The node now wants the resource. It sets needRes and stores the time when waiting started. bubble only shows a label in the GUI.
  • Finish branch. The node releases the resource: it clears needRes, forwards the token, counts the send, and schedules the next need after a new random reqPeriod.
  • Token branch. If the node waits, it records the waiting time (now − start) in the vector and keeps the token for a random usePeriod. Else it forwards the token at once.
  • finish(). Writes the scalar #sent to the .sca file and frees the two timers (cancelAndDelete removes them from the event list if needed, then deletes them).

Why

Map it to discrete event simulation: three event types (need, finish, token arrival), state (needRes, who holds the token), indicators (waitingTime, numSent). The node holds the token while using the resource: holding the token is the permission to enter the critical section. Note: a node that gets the need event while the token is far away just waits; the waiting time measures exactly that.

(a) What is the token round time for n = 6 and n = 50 (mean, minimum, maximum)? (b) How many token transmissions happen in one hour in total, and per node, for n = 6 and n = 50? Q32Exercise

Compare the three ini configs (all with usePeriod = uniform(30s,40s)): TokenRingSmall (n = 6, reqPeriod uniform(300 s, 500 s)), TokenRingSmallGreatUsage (n = 6, reqPeriod uniform(60 s, 120 s)), TokenRingLarge (n = 50, reqPeriod uniform(300 s, 500 s)). For each one, estimate the offered load (demanded usage time / available time). Which configs saturate? For the saturated ones, estimate the steady-state waiting time.

Model answer

A node uses the resource for 35 s on average, then waits reqPeriod (mean) before it needs it again. Without waiting, one node demands 35 / (35 + reqPeriod) of the time.

ConfigLoad ≈ n · 35 / (35 + req)Result
Small6 · 35 / 435 ≈ 0.48Not saturated; short waits
SmallGreatUsage6 · 35 / 125 ≈ 1.68Saturated
Large50 · 35 / 435 ≈ 4.0Strongly saturated

Saturated ring. Every node is ready when the token comes. The token round is about n · (35 + 0.1) s. After use, a node waits reqPeriod, then waits for the rest of the round: wait ≈ round − 35 − req.

  • SmallGreatUsage: round ≈ 6 · 35.1 = 210.6 s; wait ≈ 210.6 − 35 − 90 ≈ 86 s.
  • Large: round ≈ 50 · 35.1 = 1755 s; wait ≈ 1755 − 35 − 400 ≈ 1320 s in steady state. But one hour is only about two rounds, so the run stays in the transient. A quick Python model of the lab gives a mean of about 1030 s in one hour.

The same Python model gives about 84 s for SmallGreatUsage and about 13 s for Small.

Why

Above load 1, the resource is the bottleneck and the token round is set by the usage times, not by the link delays. The trap: one hour of simulated time may be too short to reach steady state. Check the waiting-time vector over time; if it still grows at the end, extend sim-time-limit or cut the warm-up.

Q33Exercise

Node[0] is the leader. It starts a regeneration timer each time it forwards the token, and cancels it when the token comes back. On expiry it creates a new token. Use n = 6, link delay at most 110 ms, usePeriod at most 40 s. (a) What is the smallest safe timeout? (b) Same for n = 50. (c) What goes wrong if the timeout is 60 s with n = 6?

Model answer

After the leader forwards the token, the worst case before it comes back: n hops at the maximum delay, and each of the other n − 1 nodes keeps the token for the maximum usage time.

  1. n = 6: 6 · 0.11 + 5 · 40 = 0.66 + 200 = 200.66 s. Choose a margin, for example 210 s or more.
  2. n = 50: 50 · 0.11 + 49 · 40 = 5.5 + 1960 = 1965.5 s.
  3. With 60 s, if two nodes use the resource in the same round (up to 80 s), the timer expires while the token is still alive. The leader creates a second token. Two nodes can then be in the critical section at the same time: mutual exclusion is violated.

If the timer started at token arrival instead of forwarding, add the leader's own usage: 40 + 200.66 = 240.66 s for n = 6.

Why

A safe timeout must cover the worst case, not the average. Here the worst case is dominated by usage times (200 s), not by the network (0.66 s). The slides say "a (long enough) timeout": this calculation is what "long enough" means. The price is a slow recovery, which the next question shows.

Q34Exercise

Lossy channels. (a) The token is a packet of 1000 bits and the channel has ber = 1e-5. What is the probability that one transmission has a bit error? (b) Take a per-hop loss probability p = 0.01 (per = 0.01) on an idle ring with n = 6. What is the mean time between two token losses? (c) With a regeneration timeout of 210 s, about how many losses happen in one hour, and what fraction of time does the ring work? (d) What changes with a 5 s timeout, and why is 5 s dangerous?

Model answer

  1. P(error) = 1 − (1 − 10−5)1000 ≈ 0.00995, about 1%. (per gives this probability directly.)
  2. The number of hops before a loss is geometric with mean 1 / p = 100 hops. At 0.1 s per hop: about 10 s.
  3. One cycle ≈ 10 s of working ring + about 210 s to detect the loss. Losses per hour ≈ 3600 / 220 ≈ 16. The ring works only about 10 / 220 ≈ 5% of the time. A Python model of this case gives about 17 losses per hour.
  4. With 5 s: cycle ≈ 15 s, about 240 losses per hour, and the ring works about two thirds of the time. But 5 s is shorter than one usage period (30–40 s). As soon as any node uses the resource, the leader creates a duplicate token.

Why

A safe timeout and a fast recovery conflict when usage is long. Options: lower the loss rate (a smaller ber, or retransmission per hop); let the token carry an epoch so a stale token can be discarded; or let a holder tell the leader that the token is alive. The simulation exists exactly to see these effects before building.

Q35Code

Extend TRNode for lossy channels and token loss. Give the NED and ini changes, a message class for the token, and the new C++ logic: drop corrupted tokens, let the leader regenerate the token after a timeout, and discard stale tokens.

Model answer

// Token.msg
packet TokenMsg {
  int epoch;
}

// token_ring.ned (changes)
simple TRNode {
  parameters:
    ...                                        // as before
    bool isLeader = default(false);
    double regenTimeout @unit(s) = default(210s);
}
channel MyChannel extends ned.DatarateChannel {
  delay = uniform(90ms,110ms);
  datarate = normal(1024kbps,1kbps);
  per = 0.001;                                 // or ber = 1e-6
}

# omnetpp.ini
**.node[0].isLeader = true
**.node[0].sendMsgOnInit = true
// new members: cMessage *regenEvt; int epoch; long numRegen;
// in initialize(): regenEvt = new cMessage("Regen"); epoch = 0; numRegen = 0;
//   create the first token with newToken() instead of new cMessage("Token")

TokenMsg *TRNode::newToken() {
  TokenMsg *t = new TokenMsg("Token");
  t->setEpoch(epoch);
  t->setBitLength(1000);                       // needed for ber
  return t;
}

void TRNode::forwardToken() {
  send(token, "out"); numSent++;
  token = nullptr;
  if (par("isLeader").boolValue()) {
    cancelEvent(regenEvt);
    scheduleAt(simTime() + par("regenTimeout").doubleValue(), regenEvt);
  }
}

void TRNode::handleMessage(cMessage *msg) {
  if (msg == needResEvt) { ... as before ... }
  else if (msg == finishedUsingResEvt) {
    needRes = false;
    forwardToken();
    scheduleAt(simTime() + par("reqPeriod").doubleValue(), needResEvt);
  }
  else if (msg == regenEvt) {                  // leader only: token presumed lost
    epoch++; numRegen++;
    bubble("Regenerating token");
    token = newToken();
    handleToken();                             // use it or forward it
  }
  else {
    TokenMsg *t = check_and_cast<TokenMsg *>(msg);
    if (t->hasBitError()) { delete t; return; }       // corrupted = lost
    if (t->getEpoch() < epoch) { delete t; return; }  // stale duplicate
    epoch = t->getEpoch();
    if (par("isLeader").boolValue()) cancelEvent(regenEvt);
    token = t;
    handleToken();
  }
}

void TRNode::handleToken() {
  if (needRes) {
    waitingTime.record(simTime() - startWaitingTime);
    scheduleAt(simTime() + par("usePeriod").doubleValue(), finishedUsingResEvt);
  } else {
    forwardToken();
  }
}
// in finish(): recordScalar("#regenerated", numRegen); cancelAndDelete(regenEvt);

Why

  • The channel does not delete a corrupted packet. It only sets the error flag; the receiver must check hasBitError() and drop it. That is why the token must be a cPacket (keyword packet) with a bit length.
  • Only one node regenerates. If every node had a timer, several nodes could create tokens at the same time.
  • The epoch protects against a timeout that was too short: the old token reaches a node that already saw the newer epoch, and that node deletes it. It is not perfect: a node that has not seen the new epoch yet still accepts the old token. So the timeout must still be safe (see the previous question).
Q36Scenario

Your manager asks: "Is token ring good enough for 50 nodes that each need a lock about every 400 s for 35 s?" Plan the simulation study with the lab. Which performance indicators do you measure, how do you record them in OMNeT++, which configs and runs do you use, and what pitfalls do you avoid?

Model answer

  • Indicators. Waiting time before access (mean, maximum, distribution); number of token transmissions (network cost); resource utilization (fraction of time some node holds the resource); number of regenerated tokens and duplicate tokens (with lossy channels).
  • Recording. Waiting time as an output vector (cOutVector, already in TRNode) and as a histogram or a signal with @statistic(record=vector,mean,max,histogram). Sends as the scalar #sent. Regenerations as a scalar in finish().
  • Configs. Start from TokenRingLarge (n = 50, usage 30–40 s). Vary n or reqPeriod with several configs (or a parameter study). Keep the same RNG mapping so the runs are comparable.
  • Runs. Use several seeds (repetitions) and report means with confidence intervals. Use Cmdenv for speed.
  • Pitfalls. One hour is shorter than one saturated round (≈ 1755 s), so extend sim-time-limit and discard the warm-up. Do not trust one seed. Check that the model is valid (for example, the idle-ring sends ≈ 36,000 per hour as computed by hand).

Expected answer to the manager: no. The offered load is about 50 · 35 / 435 ≈ 4. The resource cannot serve the demand with any algorithm, and waits reach about 20 minutes. The problem is the demand, not token ring.

Why

A simulation study is an experiment: clear indicators, controlled parameters, repetitions, and a check against a simple hand calculation. The quick load estimate tells you the result before you run anything; the simulation confirms it and gives the distribution.
