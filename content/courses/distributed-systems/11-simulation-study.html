§1

Why and how to simulate

Core idea. To study a system you can experiment with the real system or with a model. Emulation sits in between: the real software on an imitated network. Simulation runs a model and analyzes the history it produces. Discrete event simulation jumps from event to event.

Q1Compare

Compare network emulation and simulation. Give examples of emulation tools and say what they can alter.

Model answer

Emulation: the real system runs on an emulated network. The emulator looks like a real network to the OS, and changes the packet flow to imitate a WAN or a wireless network: delay, loss, duplication, reordering. Often combined with node emulation (virtual machines). Tools: Mininet, Dummynet (Emulab), Linux NetEm, marionnet, netkit.

Simulation: a model of the whole system (nodes and network) runs in a simulator; no real code or network is needed. You can test huge scales and "analyze before building".

Emulation gives realism for the software under test; simulation gives scale, control and reproducibility at the cost of model accuracy.

Why

Testing distributed systems in large or complex deployments is hard and expensive. Emulation keeps the real code; simulation keeps only the behavior you model.

Q2Describe

Classify models (analytical vs operational, discrete vs continuous, deterministic vs stochastic). Describe the elements and the main loop of a discrete event simulation.

Model answer

Models: analytical (equations) vs operational (step by step behavior); discrete vs continuous state changes; deterministic vs stochastic (random inputs). Simulation obtains a history of execution and analyzes it.

Elements: a list of events (timestamped objects, ordered by time); a simulation clock; state variables and performance indicators; an event processing function that updates state and indicators and creates new events.

forever:
  e = remove the first event from the list
  clock = e.timestamp
  process(e)   // update state, record statistics, schedule new events

Why

Nothing happens between events, so the clock can jump. A simulation of one hour of network activity can run in seconds, and it is fully reproducible with the same random seeds.

§2

OMNeT++

Core idea. OMNeT++ gives a component model (simple and compound modules with gates), a C++ library (simulation kernel, random numbers, statistics), the NED language for structure, ini files for configuration, runtime environments, and an IDE. Frameworks such as INET add ready-made models.

Q3Describe

Describe the OMNeT++ component model: simple and compound modules, gates, NED, C++ classes, ini files, messages.

Model answer

  • Modules communicate by sending messages through gates. Simple modules hold the behavior; compound modules contain submodules and connections. The whole simulation is an instance of the top-level module (the network).
  • NED defines interfaces (parameters, gates) and wiring (submodules, connections with channel properties such as delay, datarate, ber/per).
  • Each simple module is a C++ class extending cSimpleModule, registered with Define_Module. Main methods: initialize(), handleMessage(cMessage*), finish(). Read parameters with par("name"); send with send(msg, "gate"); timers are self-messages with scheduleAt and cancelEvent.
  • Parameter values go in omnetpp.ini, with several named configurations and wildcards (**.limit = 5). Volatile parameters can be random variates (exponential(0.2)): each read gives a new value.
  • Messages are subclasses of cMessage, defined in a small message language (fields).

Why

Separating structure (NED), behavior (C++) and experiments (ini) lets you reuse modules and run many configurations without recompiling.

Q4Describe

How are results collected in OMNeT++? How are random numbers managed?

Model answer

Output vectors (.vec): named series of (timestamp, value) pairs that capture behavior over time (e.g. cOutVector waitingTime, record()). Recording can be enabled, disabled or limited in time from the ini file. Output scalars (.sca): summary statistics, e.g. recordScalar("#sent", numSent) in finish(). Statistics classes (e.g. histograms) and signals decouple the model from statistics collection.

Random numbers: a configurable number of RNG streams, mapped to modules in the ini file (e.g. traffic generators on stream 0, MACs on stream 1). Seeds are automatic or manual. Many distributions are available from NED and C++.

Why

Separate RNG streams make experiments comparable: changing one module's randomness does not change the random sequence of the others.

Q5Exercise

In TicToc with a lossy toc (10% loss), tic uses a timeout to resend. Why does the second version send a copy of the message (dup()) and keep the original? What does cancelEvent do?

Model answer

A sent message belongs to the receiver (it may delete it, e.g. when it is "lost"). If tic resent the same object, it would use a deleted message. So tic keeps the original and sends msg->dup() each time, including retransmissions after a timeout. Messages carry a sequence number (tic-1, tic-2…) to tell them apart.

The timeout is a self-message scheduled with scheduleAt(simTime()+timeout, timeoutEvent). When the reply arrives in time, cancelEvent(timeoutEvent) removes it from the event list, then tic sends the next message and schedules a new timeout.

Why

This is stop-and-wait with retransmission: the same "time redundancy" technique of the fault tolerance chapter, modeled as events.

Q6Scenario

Lab: the token ring simulation (TRNode) controls access to a shared resource. Extend it for lossy channels: how do you rebuild a lost token? Which performance indicators would you measure and how?

Model answer

Lossy channels. Set ber or per on the channel; on arrival, a packet with hasBitError() is dropped. A single leader node (e.g. node[0]) keeps a timeout, reset every time the token passes. The timeout must be longer than the worst token round: n × (link delay + transmission) + n × max usage time. On expiry, the leader creates a new token.

Risk: a too-short timeout creates a second token (two nodes in the critical section). Mitigation: a token sequence/epoch number; a node discards tokens with an old epoch.

Indicators (the lab already records some): waiting time before access (cOutVector waitingTime, from the "need" event to the token arrival); number of token transmissions (#sent scalar); resource utilization; number of regenerated tokens. Compare configurations from the ini file: small ring (6 nodes), small ring with frequent requests, large ring (50 nodes).

Why

Token ring mutual exclusion (chapter 05) has two problems: lost token and crashed process. The simulation makes the trade-off visible: a short timeout recovers fast but risks duplicate tokens; a long one is safe but wastes time.
