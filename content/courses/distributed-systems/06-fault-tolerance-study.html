§1

Basics and client/server failures

Core idea. A fault causes an error, which can cause a failure (the service is not delivered). Fault tolerance masks faults with redundancy: information (codes), time (retry), physical (replicas, e.g. triple modular redundancy). Even RPC cannot fully hide failures.

Q1Describe

Define availability, reliability, safety and maintainability. Give an example of a system that is highly available but not reliable. Classify faults by frequency.

Model answer

  • Availability: ready for use when needed.
  • Reliability: runs continuously for a long time without failure.
  • Safety: nothing bad happens when it fails.
  • Maintainability: easy to repair.

Example: a system that goes down for 1 ms every hour is 99.999% available, but it is not reliable: it never runs for more than an hour.

Faults: transient (happen once and disappear), intermittent (appear and vanish with no clear reason), permanent (stay until repaired).

Why

Availability is a fraction of time; reliability is the length of uninterrupted operation. The two can differ a lot, so a requirement must say which one matters.

Q3Compare

How do you handle lost replies and client crashes (orphans)? Compare extermination, reincarnation, gentle reincarnation and expiration.

Model answer

Lost replies. The client cannot tell a lost request from a lost reply. Retrying is safe for idempotent requests. For others, the server caches requests with sequence numbers and detects duplicates (open question: how long to keep them).

Orphans = computations started by a crashed client.

  • Extermination: the client logs each RPC; after reboot it asks to kill the orphans. Costly logging; problems with grand-orphans and partitions.
  • Reincarnation: after reboot the client starts a new epoch and broadcasts it; servers kill computations of old epochs (grand-orphans too); replies with an old epoch are discarded.
  • Gentle reincarnation: like reincarnation, but kill only if the owner cannot be found.
  • Expiration: each remote computation has a time limit; the client waits that long before rebooting.

None is perfect: killed orphans may leave open files or locks.

Why

The lesson: a remote call is not a local call. Some failure cases cannot be masked, only made rarer or less harmful.

§2

Process groups and agreement

Core idea. Replicate a process in a group, so that the group survives some failures. Size: k + 1 members tolerate k fail-silent faults; 2k + 1 tolerate k Byzantine faults with voting. When members must agree among themselves (no external voter), you need consensus: FloodSet for crashes, Lamport's algorithm with 3m + 1 generals for traitors.

Q4DescribeExam 17 Jan 2024 · 13 Feb 2015 · 9 Sep 2015 · 1 Feb 2013

Describe the FloodSet algorithm. Which problem does it solve? Under which assumptions? Why are those assumptions fundamental (use counterexamples)? Optional: prove its correctness.

Model answer

Problem: consensus. Each process starts with a value; all non-faulty processes must decide. Agreement: no two processes decide differently. Validity: if all start with v, v is the only possible decision. Termination: all non-faulty processes eventually decide.

Assumptions: synchronous rounds (a message is received in the same round); reliable channels; at most f processes fail, by crash (they stop, possibly in the middle of a send).

Algorithm. Each process keeps W, initially {its value}. For f + 1 rounds: send W to all, add the received sets to W. Then decide: if |W| = 1, its element; else a default v0 (or the same deterministic function, e.g. max(W)).

Proof. Lemma 1: if no process fails in round r, all processes active after r have the same W (each received the W of all others). Lemma 2: if all W are equal after r, they stay equal in all later rounds (no new values appear). With at most f crashes, at least one of the f + 1 rounds has no crash. So all W are equal at the end, and the decision is the same. Validity: if all start with v, W = {v} always.

Counterexamples.

  • Only f rounds (f = 1, 1 round): P1 = 0, P2 = P3 = 1. P1 crashes after sending only to P2. P2 has {0, 1} → v0, P3 has {1} → 1. Disagreement. (Chain of f crashes for general f.)
  • Asynchronous system: a process cannot tell a slow message from a crash, so it cannot end a round. FLP says no deterministic algorithm exists.
  • Lossy channels: a lost message acts like an extra crash at every round: the two-generals problem shows that agreement is impossible.
  • Byzantine processes: a traitor sends {0} to some and {1} to others in the last round; correct processes end with different W.

Optimization: broadcast W in round 1, then broadcast again only when you learn a new value.

Why

The heart of the proof is the clean round. The algorithm does not know which round is clean; it only needs one to exist, and f + 1 rounds guarantee it by the pigeonhole principle.

Q5Describe

Describe the Byzantine generals problem and Lamport's algorithm for 4 generals with 1 traitor. Why are 3m + 1 generals needed for m traitors?

Model answer

n generals announce their troop strengths; communication is perfect; some generals are traitors. Agreement: loyal generals learn the same values. Validity: if a loyal general announces v, all loyal generals learn v for him. Termination.

Algorithm (4 generals, 1 traitor). (1) Each general sends its value to all. (2) Each forms a vector of received values. (3) Each sends its vector to all. (4) For each position, take the majority of the values reported by the others; no majority → "unknown". Loyal generals get the same vector, with correct values for loyal positions.

3m + 1. With 3 generals and 1 traitor, a loyal general cannot tell "the commander lied" from "the other lieutenant lied": both scenarios give him the same messages. In general, with m traitors you need 2m + 1 loyal generals so that the loyal majority wins every vote: 3m + 1 in total.

Why

A traitor can send different values to different processes, so a single report proves nothing. Only a majority of independent reports, from more loyal than traitorous sources, can outvote the lies.

§3

Reliable group communication

Core idea. With fixed groups and correct processes, reliable multicast is about efficiency: avoid ack implosion. With faulty processes and changing groups, you need virtual synchrony: a message is delivered to all correct members or to none, and view changes are ordered with respect to messages.

Q7CompareExam 14 Feb 2024 · 6 Sep 2024 · 5 Sep 2013 · 23 Sep 2015

Describe how to efficiently provide reliable multicast among reliable processes (positive acks, negative acks, scalable reliable multicast, hierarchical feedback control). Which problem does each solve and which assumptions does it make?

Model answer

Setting: fixed group, correct processes, unreliable multicast underneath. Goal: every member receives every message (any order).

  • Positive acks: each receiver acks each message; the sender retransmits until all ack. Problem: ack implosion at the sender with large groups.
  • Negative acks: a receiver sends a NACK only when it detects a gap (sequence numbers). Fewer messages, but the sender must buffer messages, without knowing when it can delete them.
  • Scalable Reliable Multicast (non-hierarchical feedback control): NACKs are multicast to the group after a random delay. If a receiver hears another NACK for the same message, it suppresses its own. One retransmission serves all. Cost: everyone must process all NACKs, including members that did not lose the message.
  • Hierarchical feedback control: receivers form local groups with a coordinator, and coordinators form a tree rooted at the sender. Each coordinator handles retransmissions in its group with any strategy, and asks its parent when it lacks a message. It removes a message from its buffer when all its receivers and child coordinators have acked it. Problem: build and maintain the tree.

Why

Each step moves the feedback work away from the sender: first by sending less feedback (NACK), then by sharing it (multicast NACK with suppression), then by distributing it (hierarchy). For faulty processes the problem changes completely: see the next question.

Q8DescribeExam 14 Feb 2024 (second part)

How does the problem change if processes may fail? Define virtual synchrony and describe its implementation in ISIS.

Model answer

Now a message must reach all correct members or none, and the members must agree on who is in the group (atomic multicast also adds the same order everywhere). Close synchrony (instantaneous delivery to all) is impossible with failures.

Virtual synchrony. Distinguish receive (by the communication layer) and deliver (to the application). A group view is the set of members seen by the sender. View changes are multicast too, and every message is delivered entirely within one view: before or after a view change, never across it. Crashed processes leave the view and must rejoin. Messages of a correct process are delivered to all correct processes; messages of a crashing sender are delivered to all or dropped.

ISIS implementation (reliable FIFO point-to-point channels). A process keeps each message until it is stable (all members received it). On a view change message: stop sending, multicast all unstable messages to the members of the new view, then multicast a flush. Install the new view after receiving a flush from every member of the new view. So all survivors have the same messages before the new view starts.

Why

Because of FLP, you cannot know if a crashed process received a message. Virtual synchrony avoids the question: the crashed process is simply removed, and the survivors make sure they all have the same set of messages before they move on.

§4

Recovery: checkpointing and logging

Core idea. Backward recovery returns to a saved correct state; forward recovery moves to a new correct state (e.g. error-correcting codes). Checkpoints must form a recovery line: a consistent cut. Independent checkpoints risk the domino effect; coordinated checkpoints avoid it; logging lets you replay messages.

Q9ExerciseExam 6 Sep 2024

Exam diagram 1 (P1 crashes; checkpoints 3 per process; messages as in the figure). Compute the recovery line with the rollback-dependency graph. Then diagram 2 (P4 crashes) with the checkpoint-dependency graph.

Model answer

Diagram 1, rollback-dependency graph. Mark the failure state of P1. The message P1 → P2 sent after c1,3 marks c2,3; from there the marks spread through P3 and P4 and come back to P1 and P2 (domino effect). Result: c1,1, c2,1, c3,1, c4,2. In-transit messages to resend: the first message P2 → P1 and the first message P4 → P3.

Diagram 2, checkpoint-dependency graph. Root set: c4,3 (last checkpoint of the crashed P4) and the current states of P1, P2, P3. Iterate: a root reached from another root is replaced with its previous checkpoint. Result: c1,2, c2,2, c3,3, c4,3.

Open the simulator to see each edge and each marking step.

Why

Rollback-dependency: an edge ci,x → cj,y says "if the interval ending at ci,x is undone, the interval ending at cj,y must be undone too", because it received a message from it. Marking follows "undone" through the graph. The checkpoint graph says the same with the edge starting at the checkpoint that begins the sending interval. Both give the same line.

Exam tip

Name the checkpoints first (ci,1, ci,2, …) and list the messages as "sent in Ii,x, received in Ij,y". Then draw the graph. Finish by checking for orphan messages on your line.

Q10DescribeExam 17 Jan 2024 · 14 Feb 2024 · 13 Jul 2015 · 3 Dec 2014

When are rollback-dependency and checkpoint-dependency graphs used, and how is the data to build them collected?

Model answer

When: with independent (uncoordinated) checkpointing, after a failure, to find the most recent consistent set of checkpoints (the recovery line).

Data collection:

  • Each process numbers its checkpoint intervals: Ii,x lies between ci,x−1 and ci,x.
  • Each message piggybacks the sender's current interval.
  • The receiver records the dependency Ii,x → Ij,y with its recovery information (on stable storage, with the checkpoint).
  • After a failure, the recovering process broadcasts a dependency request; all processes stop and send their dependency information.
  • The recovering process computes the recovery line and sends the rollback requests.

Why

Independent checkpoints are cheap to take but expensive to use: you need this extra bookkeeping on every message, you may need a domino rollback, and some checkpoints are useless. That is why coordinated checkpointing is preferred.

Q11Compare

Compare independent, coordinated (blocking and snapshot-based), incremental and communication-induced checkpointing.

Model answer

  • Independent: each process checkpoints alone. Cheap, but domino effect, useless checkpoints, dependency tracking.
  • Coordinated, blocking: the coordinator sends CHKP-REQ; each process takes a checkpoint, queues outgoing application messages, and acks; the coordinator sends CHKP-DONE. No useless checkpoints; processes block during the protocol.
  • Incremental: ask a checkpoint only from processes that depend on the coordinator's recovery (they received messages causally dependent on one sent by the coordinator after its last checkpoint).
  • Coordinated with a global snapshot (Chandy–Lamport): processes are not blocked; the algorithm is more complex.
  • Communication-induced: independent checkpoints, plus information piggybacked on messages that forces a process to take an extra checkpoint when needed to avoid the domino effect.

Why

The trade-off is coordination cost at checkpoint time vs complexity and lost work at recovery time.

Q12Compare

Describe message logging. Define stable message, DEP(m), COPY(m) and orphan process. Compare pessimistic and optimistic logging.

Model answer

Start from a checkpoint and replay logged messages. It works if the system is piecewise deterministic: execution between two receipts is deterministic.

  • Stable message: written to stable storage; it can no longer be lost.
  • DEP(m): processes to which m, or a message that depends on m, was delivered.
  • COPY(m): processes that hold a copy of m, not yet in stable storage.
  • Orphan: a surviving process Q in DEP(m) when every process in COPY(m) has crashed. m can never be replayed, but Q depends on it.

To avoid orphans: every process in DEP(m) must also be in COPY(m).

Pessimistic: an unstable message is delivered to at most one process, and the receiver sends nothing until it writes m to stable storage. No orphans ever; slower. (A variant logs at the sender.)

Optimistic: log asynchronously, hoping it finishes before a crash. If COPY(m) all crash, roll back DEP(m) until they no longer depend on m. Faster in normal operation; complex recovery.

Combining coordinated checkpointing with logging gives the best performance.

Why

The same trade-off as pessimistic vs optimistic concurrency control: pay always to prevent the problem, or pay only when it happens.
