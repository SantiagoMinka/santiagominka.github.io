§1

Dependability, faults and the failure model

Core idea. A dependable system is available, reliable, safe and maintainable. A fault causes an error, and an error can cause a failure: the system does not provide its service. The failure model classifies failures as omission, timing or Byzantine. The key technique to mask failures is redundancy: information, time or physical.

Q1Describe

Define availability, reliability, safety and maintainability. Give an example of a system that is highly available but not reliable. Classify faults by the frequency at which they occur.

Model answer

  • Availability: the system is ready for use when we need it.
  • Reliability: the system runs continuously for a long time without failure.
  • Safety: nothing bad happens, also when the system fails.
  • Maintainability: the system is easy to fix.

Example from the slides: a system goes down for 1 ms every hour. Its availability is 99.999% (or better), but it is highly unreliable: it never runs for more than one hour.

Faults by frequency: transient faults occur once and disappear; intermittent faults appear and vanish with no apparent reason; permanent faults continue to exist until the failed component is repaired.

Why

Availability is a fraction of time. Reliability is the length of uninterrupted operation. Many short outages give high availability and low reliability. A requirement must say which one matters: a web shop wants availability, a long batch computation wants reliability.

Q2Exercise

System A goes down for 1 ms every hour. System B runs for one full year (8760 h) and then goes down once for 4 hours. (a) Compute the availability of A and B. (b) Which system is more available? Which is more reliable? (c) How many minutes of downtime per year does "five nines" (99.999%) allow?

Model answer

  1. A: 1 − 0.001 s / 3600 s = 0.99999972 → 99.99997%. B: 1 − 4 h / 8760 h = 0.999543 → 99.954%.
  2. A is more available. B is more reliable: it runs for one year without failure, A runs for at most one hour.
  3. 0.00001 × 365 × 24 × 60 = 5.26 minutes per year.

Why

The two numbers measure different things. Availability counts the total downtime. Reliability looks at the time between failures. A system with many tiny outages can beat a system with one long outage on availability and lose badly on reliability.

Exam tip

If you quote the slide example, say "99.999%" and then say why it is still unreliable. The point is the contrast, not the exact digits.

Q3DescribeExam 6 Sep 2024 · 13 Jul 2015 · 3 Dec 2014

Discuss (classify) the types of failures that may happen in a distributed system (the failure model). Give a practical example of each. Briefly discuss how hard it is to build a correct system under each type of failure.

Model answer

ClassTypeExample
Omission, processesFail-safe: the output is sometimes wrong, but the error is easy to detectA sensor sends a value with a wrong checksum; the receiver discards it.
Fail-stop: the process crashes and others can detect the crashA server stops; the cluster manager reports "node down" to all.
Fail-silent: the process crashes and others cannot detect itA server freezes; the clients cannot tell if it is dead or only slow.
Omission, channelsSend, channel or receive omission: a message is lostA router drops a packet because its buffer is full (channel omission). A full socket buffer drops an incoming message (receive omission).

Byzantine (arbitrary)Processes: omit steps or add stepsA compromised node sends different values to different peers.
Channels: corrupt content, deliver non-existent messages, deliver real messages more than onceA faulty switch duplicates frames; an attacker injects forged messages.

Difficulty. It grows from top to bottom. Detectable crashes (fail-stop) are the easiest case. Fail-silent crashes are harder: in an asynchronous system you cannot tell a crash from a slow process, so consensus becomes impossible (FLP). Omissions on channels can be masked with acks and retransmissions, but with arbitrary losses agreement is impossible (coordinated attack). Byzantine failures are the hardest: you need 2k + 1 replicas with voting, and 3m + 1 processes for agreement among the group.

Why

The failure model is an assumption. Every algorithm in the chapter is correct only under its own failure model. FloodSet assumes crashes; Lamport's algorithm assumes Byzantine processes but perfect channels. If you choose a weaker model than the real one, the algorithm can break.

Exam tip

Give one concrete example per row. Then end with the "how hard" ranking and link it to the group sizes (k + 1, 2k + 1, 3m + 1). This shows that you connect the model to the rest of the chapter.

Q4Exercise

  1. Transient.
  2. Intermittent.
  3. Permanent.
  4. Fail-stop (detectable crash).
  5. Fail-silent (undetectable crash).
  6. Timing failure.

Q5Exercise

Name the three types of redundancy with an example. Then consider triple modular redundancy (TMR): stage A has A1, A2, A3; each Ai feeds all three voters V1, V2, V3; voter Vi feeds Bi. The correct value is 5. (a) A1 = 5, A2 = 7, A3 = 5, and voter V2 is faulty and outputs 9. What do B1, B2, B3 receive, and is the final output (after the next voting stage) correct? (b) A1 = 7, A2 = 7, A3 = 5. (c) A1 = 7, A2 = 8, A3 = 5. (d) Each module works with probability 0.9, voters are perfect. What is the probability that one TMR stage gives the correct value?

Model answer

Redundancy: information (extra bits, e.g. Hamming codes), time (do it again, e.g. retransmission), physical (extra hardware or processes, e.g. replicas, TMR).

  1. Each voter receives (5, 7, 5). V1 and V3 output 5. V2 is faulty and outputs 9. So B1 and B3 receive 5, B2 receives 9. The next voters receive two correct values and one wrong value. The majority wins: the final output is correct. One faulty element per stage is masked.
  2. Each voter receives (7, 7, 5). The majority is 7: the wrong value wins. Not masked. TMR assumes at most one faulty element per stage.
  3. Each voter receives (7, 8, 5). There is no majority. The voter can detect the problem, but it cannot mask it.
  4. At least 2 of 3 modules must work: p3 + 3p2(1 − p) = 0.729 + 0.243 = 0.972. This is better than one module (0.9).

Why

TMR replicates also the voters, so a voter is not a single point of failure. The price is the assumption: two equal wrong values defeat the vote. Note that TMR improves reliability only if p > 0.5. With p = 0.4 the stage is worse than a single module.

§2

Client/server communication and RPC failures

Core idea. TCP masks omission failures with acks and retransmissions, but it cannot mask crashes. RPC tries to hide the network, and it fails in five ways: server not located, lost request, server crash, lost reply, client crash. You can get at-most-once or at-least-once, but not exactly-once. Idempotent requests, sequence numbers and orphan handling reduce the damage.

Q6Exercise

What does TCP mask, and what can it not mask? Then list the five RPC failure classes and classify each event: (a) the client uses an obsolete version of the protocol and the binder finds no matching server; (b) a router drops the request; (c) the server process is killed while it executes the call; (d) the router drops the reply; (e) the client laptop shuts down after it sends a long query.

Model answer

TCP gives reliable point-to-point communication. It masks omission failures with acks and retransmissions. It does not mask crash failures, e.g. the loss of a connection: the application gets an error and must decide what to do.

The five classes: server cannot be located, lost request, server crash, lost reply, client crash.

  1. Server cannot be located. Benign: raise an exception.
  2. Lost request. Benign: the client sends it again. After too many losses it concludes that the server is down.
  3. Server crash. The client cannot know if the job was done.
  4. Lost reply. The client cannot tell it from a lost request.
  5. Client crash. The query becomes an orphan on the server.

Why

The first two cases are benign because nothing happened on the server. The last three are hard because the server state may have changed and the client does not know. This is why "completely masking" communication failures is not feasible.

Q8Exercise

Use the print server table. (a) The server uses M→P and crashes after M, before P. The client reissues only when it got the confirmation. Result? (b) The server uses P→M and crashes after P, before M. The client always reissues. Result? (c) Which (server, client) combinations guarantee at-least-once (never ZERO)? (d) Which guarantee at-most-once (never DUP)?

Model answer

  1. Case MC(P): the client got M, so it reissues. The document was not printed before, so it is printed once: OK.
  2. Case PC(M): the document was printed, and the client reissues: DUP.
  3. At-least-once: M→P with "always" (DUP, OK, OK); P→M with "always" (DUP, DUP, OK); P→M with "only when not ACKed" (OK, DUP, OK).
  4. At-most-once: "never" with both server orders; M→P with "only when not ACKed" (OK, ZERO, OK).

Why

Each row is a bet on where the crash happened. Reissuing protects against ZERO and risks DUP. Not reissuing does the opposite. You choose the bet that matches the application: a duplicate page is cheap, a missing payment is not, a duplicate payment is worse.

Q9Scenario

A client calls these remote operations and gets no reply: (1) getBalance(acc); (2) setAddress(acc, "Via Roma 1"); (3) deposit(acc, 100); (4) appendLog(line); (5) deleteFile("x"). For each, is it idempotent? Can the client simply retry? What would you do for the others?

Model answer

  • (1) getBalance: idempotent (read only). Retry.
  • (2) setAddress: idempotent (sets an absolute value). Retry.
  • (3) deposit: not idempotent. A retry can deposit 200.
  • (4) appendLog: not idempotent. A retry can append the line twice.
  • (5) deleteFile: the effect is idempotent, but the second call may return "file not found". The client must accept that answer as success.

For (3) and (4): add a request identifier (client id + sequence number). The server caches the requests it executed, with their replies, and returns the cached reply for a duplicate. Another option: change the interface to make it idempotent, e.g. setBalance(acc, newValue, expectedOldValue).

Why

A lost reply and a lost request look the same to the client. Retry is safe only if executing twice gives the same state as executing once. The trap is case (5): the state is idempotent, but the reply is not.

Q10Exercise

A bank server keeps, for each client, the last executed sequence number and its reply. The balance is 0. Client C sends: #1 deposit(100): the server executes it, the reply is lost; C retransmits #1. Then #2 withdraw(30): the request is lost; C retransmits #2. (a) What does the server do at each arrival, and what is the final balance? (b) What would the balance be without duplicate detection? (c) When can the server discard the cached reply of #2?

Model answer

  1. #1 arrives: new number, execute, balance 100, cache reply #1. The reply is lost.
    #1 arrives again: 1 ≤ last executed (1), so it is a duplicate. Do not execute; resend the cached reply.
    #2 (first copy) never arrives.
    #2 arrives: new number, execute, balance 70, cache reply #2.
  2. Without detection, #1 runs twice: 100 + 100 − 30 = 170.
  3. When the client shows that it got the reply, e.g. when request #3 arrives (if the client sends one request at a time, #3 implies that it received reply #2). Without such a sign, the server does not know how long to keep the information: this is the open problem on the slides.

Why

Sequence numbers turn a non-idempotent operation into an at-most-once operation, and client retries add at-least-once. Together they get close to exactly-once, but only while the server does not crash and lose its cache.

Q11Compare

A client crashes during a call. What is an orphan? Compare extermination, reincarnation, gentle reincarnation and expiration. Which one would you pick if network partitions are frequent?

Model answer

Orphan = a computation started by a client that crashed. It still uses server resources.

  • Extermination: the client logs each RPC; after the reboot it asks to kill the orphans. Costly (a log write for each call); problems with grand-orphans (calls made by the orphan) and with network partitions (the client cannot reach the orphans).
  • Reincarnation: after the reboot the client starts a new epoch and broadcasts it. Servers kill the old computations of that client, grand-orphans included. Replies with an old epoch are discarded.
  • Gentle reincarnation: like reincarnation, but a server kills an old computation only if it cannot locate its owner.
  • Expiration: each remote computation gets a time limit. The client waits that long before it reboots, so all its computations are gone.

With frequent partitions: expiration. It needs no message to reach the server, only a bound on time. Extermination and reincarnation depend on a message (kill request or epoch broadcast) that may not reach the other side.

None is perfect: a killed orphan may leave open files or locks. There is a lot of bookkeeping, and not all issues can be solved.

Why

A remote call is not a local call. Some failure cases cannot be masked, only made rarer or less harmful. Expiration trades a longer reboot (or a renewal protocol for long calls) for independence from the network.

§3

Process resilience and agreement

Core idea. Replicate a process in a group, so that the group survives some failures. k + 1 members tolerate k fail-silent faults; 2k + 1 tolerate k Byzantine faults when an external client votes. When the members must agree among themselves, you need consensus: FloodSet (f + 1 rounds) for crashes, Lamport's algorithm (3m + 1 generals) for traitors. In an asynchronous system, consensus is impossible even with one crash (FLP).

Open the FloodSet simulatorRun the counterexamples: f rounds, more than f crashes.
Q12Compare

Compare flat groups and hierarchical groups. How is membership managed in a flat group, and what is the problem with crashes?

Model answer

  • Flat group: all members are equal and decide together. No single point of failure. But decisions need agreement among all members, which is slow and complex.
  • Hierarchical group: a coordinator receives the requests and distributes the work to the workers. Decisions are simple and fast. But the coordinator is a single point of failure: when it crashes, the group must elect a new one.

Membership. A coordinator (group server) makes it easy, but it is again a single point of failure. In a flat group, membership is distributed: join and leave announcements must be (reliably) multicast to all members. A crashed process does not say "I am dying", so the others must detect the crash. If too many processes crash or leave, the group must be rebuilt.

Why

It is the usual trade-off between centralized and distributed control: simplicity and speed against robustness. The membership problem is not a detail: every later algorithm (virtual synchrony, voting) needs the members to agree on who is in the group.

Q13Exercise

(a) A replicated-write store must survive 3 fail-silent replicas. How many replicas? (b) The same, but 3 replicas can be Byzantine and the client votes on the answers. (c) You have 7 replicas. How many fail-silent faults, Byzantine faults with client voting, and traitors in a Byzantine agreement among the replicas can you tolerate? (d) FloodSet must tolerate f = 3 crashes. How many rounds?

Model answer

  1. k + 1 = 4.
  2. 2k + 1 = 7.
  3. Fail-silent: 6 (k + 1 ≤ 7). Byzantine with client voting: 3 (2k + 1 ≤ 7). Byzantine agreement: 3m + 1 ≤ 7, so m = 2.
  4. f + 1 = 4 rounds. One correct process is enough, so you need at least 4 processes for someone to decide.

Why

Fail-silent replicas give no answer or a correct answer, so one survivor is enough. Byzantine replicas give wrong answers, so the correct ones must outnumber them: k + 1 correct against k wrong. Agreement inside the group is harder, because there is no external voter. In practice, you cannot be sure that no more than k processes fail at the same time: k is an assumption.

Q15Describe

Define the consensus problem (agreement, validity, termination). Then describe the coordinated attack problem. Why can the two generals never be sure, whatever algorithm they use?

Model answer

Consensus. Each process starts with an initial value. All non-faulty processes must decide on a value, based on the initial values. Agreement: no two processes decide on different values. Validity: if all processes start with the same value v, then v is the only possible decision. Termination: all non-faulty processes eventually decide.

Coordinated attack. Two generals G1 and G2 decide separately whether to attack at dawn. If both attack, they win; if only one attacks, it fails. They communicate with messengers that can be lost, captured or delayed.

No algorithm works. Suppose that an algorithm exists. Take a run where both attack, and remove the last message that was delivered. The sender of that message cannot see the difference, so it still attacks. The receiver must also attack, otherwise only one attacks. Repeat the argument message by message. You reach a run with no messages delivered, where both generals still attack: but then the decision does not depend on communication, which is absurd (e.g. they attack also when G1 wanted to stay).

Why

Each confirmation needs a confirmation, forever. The lesson: consensus is impossible with arbitrary communication failures. So the next algorithms assume reliable channels and let only the processes fail.

Q16DescribeExam 17 Jan 2024 · 13 Feb 2015 · 9 Sep 2015 · 1 Feb 2013

Describe the FloodSet algorithm. Which problem does it solve? Under which assumptions? Why are those assumptions fundamental (use counterexamples)? Optional: prove its correctness.

Model answer

Problem: consensus. Each process starts with a value; all non-faulty processes must decide. Agreement: no two processes decide differently. Validity: if all start with v, v is the only possible decision. Termination: all non-faulty processes eventually decide.

Assumptions: synchronous system with rounds (a message is received in the same round); reliable channels; at most f processes fail, by crash (they stop, possibly in the middle of a send).

Algorithm. Each process keeps W, initially {its start value}. For f + 1 rounds: send W to all other processes, add the received sets to W. Then decide: if |W| = 1, its element; else a default v0 (or the same deterministic function, e.g. max(W)).

Proof. Lemma 1: if no process fails in round r, all processes active after r have the same W (each received the W of all others). Lemma 2: if all W are equal after round r, they stay equal in all later rounds (no new values appear). With at most f crashes, at least one of the f + 1 rounds has no crash. So all W are equal at the end, and the decision is the same. Validity: if all start with v, W = {v} always.

Counterexamples.

  • Only f rounds (f = 1, 1 round): P1 = 0, P2 = P3 = 1. P1 crashes after it sends only to P2. P2 has {0, 1} → v0, P3 has {1} → 1. Disagreement. (A chain of f crashes for general f.)
  • Asynchronous system: a process cannot tell a slow message from a crash, so it cannot end a round. FLP says that no deterministic algorithm exists.
  • Lossy channels: a lost message acts like a partial crash in every round; the coordinated attack shows that agreement is impossible.
  • Byzantine processes: a traitor sends {0} to some and {1} to others in the last round; correct processes end with different W.

Optimization: broadcast W in round 1, then broadcast again only when you first learn a new value.

Why

The heart of the proof is the clean round. The algorithm does not know which round is clean; it only needs one to exist, and f + 1 rounds guarantee it by the pigeonhole principle.

Q19Describe

Describe the Byzantine generals problem (agreement, validity, termination) and Lamport's algorithm for 4 generals with 1 traitor. Why are 3m + 1 generals needed for m traitors? Why do 3 generals with 1 traitor fail?

Model answer

n generals announce their troop strengths; communication is perfect; some generals are traitors and behave arbitrarily. Agreement: no two loyal generals learn different troop strength values. Validity: if a loyal general announces v, all loyal generals learn v for him. Termination: all loyal generals eventually learn the strength of all other loyal generals.

Algorithm (4 generals, 1 traitor). (1) Each general sends its troop strength to all others. (2) Each forms a vector with the received values. (3) Each sends its vector to all others. (4) For each position, each general takes the majority of the values reported; no majority → "unknown". Loyal generals get the same vector, with the correct values for the loyal positions.

3 generals, 1 traitor. G1 receives "G2 says x" from G2 and "G2 told me y" from G3. G1 cannot know whether G2 lied or G3 lied: both scenarios give G1 exactly the same messages. There is no majority of 2 against 1, so G1 cannot compute a vector that is both correct and equal to the one of the other loyal general.

3m + 1. Lamport (1982): with m traitors, 2m + 1 loyal generals are needed, so that the loyal reports always form a majority. Total 3m + 1.

Why

A traitor can send different values to different processes, so a single report proves nothing. Only a majority of independent reports, from more loyal than traitorous sources, can outvote the lies. With 3 generals, each vote is 1 against 1.

For the traitor's position, the result is "unknown" here, the same for all. The trap: if the traitor arranges a majority for one general only (e.g. the same value twice in the reports seen by G2), loyal generals can disagree on the traitor's entry. The robust form (Lamport's OM(1)) uses, for position j, your own direct value plus the values relayed by the other generals except j. Then all loyal generals vote on the same multiset.

Exam tip

Write the vectors in a table, one row per general, and vote column by column. Say explicitly that loyal positions are correct because 2 loyal reports beat 1 traitor report.

Q21Scenario

A colleague runs FloodSet over the Internet. He replaces the synchronous round with a timeout of 2 s: "if no message arrives in 2 s, the sender has crashed". He claims that the algorithm now solves consensus with one crash in an asynchronous system. Find the error. What does FLP state, and does it also hold for Byzantine failures?

Model answer

Error. In an asynchronous system there is no bound on message delay. A message from a correct but slow process can arrive after 2 s. The receiver treats the sender as crashed and ignores its value, while another process received it in time. The two processes can end with different W and decide differently: agreement is violated. If instead you wait longer, a real crash makes you wait forever: termination is violated.

FLP (Fischer, Lynch, Paterson): no deterministic algorithm solves consensus in an asynchronous system if even one process can fail by crash.

Byzantine: also impossible. A Byzantine process can simulate a crash, so an algorithm for Byzantine failures would also solve the crash case.

Why

A timeout is a guess, not a failure detector. The root problem is that a crashed process and a slow process look the same. Practical protocols always keep agreement and give termination only when the network behaves synchronously long enough.

§4

Reliable group communication: non-faulty processes

Core idea. Reliable multicast is needed to use replicated groups. With fixed groups and correct processes, every member must receive every message (in any order), on top of an unreliable multicast. The problem is efficiency: positive acks cause ack implosion; NACKs force the sender to buffer; scalable reliable multicast suppresses duplicate NACKs; hierarchical feedback control distributes the work.

Q22CompareExam 14 Feb 2024 · 6 Sep 2024 · 5 Sep 2013 · 23 Sep 2015

Describe how to efficiently provide reliable multicast among reliable processes over unreliable links (positive acks, negative acks, scalable reliable multicast, hierarchical feedback control). Which problem does each solve and which assumptions does it make?

Model answer

Setting: fixed group, correct processes, unreliable multicast underneath. Goal: every member receives every message (not necessarily in the same order). Sequence numbers let a receiver detect gaps.

  • Positive acks: each receiver acks each message; the sender retransmits until all ack. Problem: ack implosion at the sender with large groups.
  • Negative acks: a receiver sends a NACK only when it detects a gap. Fewer messages, but the sender must cache messages, without knowing when it can delete them.
  • Scalable Reliable Multicast (non-hierarchical feedback control): NACKs are multicast to the group after a random delay. If a receiver hears another NACK for the same message, it suppresses its own. One retransmission serves all. Cost: everyone must process all NACKs, including members that did not lose the message.
  • Hierarchical feedback control: receivers form local groups with a coordinator, and the groups form a tree rooted at the sender. Each coordinator can use any strategy in its group, and asks its parent coordinator for retransmissions. It removes a message from its buffer when all receivers in its group and all its child coordinators have acked it. Problem: the tree must be built and maintained.

Why

Each step moves the feedback work away from the sender: first by sending less feedback (NACK), then by sharing it (multicast NACK with suppression), then by distributing it (hierarchy). For faulty processes the problem changes completely: see §5.

Q23Exercise

A sender multicasts one message to 200 receivers. 6 receivers lose it; the retransmission reaches everybody.   2. 6 NACKs.
  3. 1 NACK: the first receiver whose timer expires multicasts it; the other 5 hear it and suppress their own.

Why

Positive acks scale with the group size, NACKs scale with the losses. SRM goes further, but it moves part of the cost to all receivers. Hierarchical feedback control fixes that: a NACK stays inside the local group.

Q24Exercise

Scalable reliable multicast. Receivers R1, R2, R3, R4 detect at time 0 that message #7 is missing. Their random NACK timers are R1 = 30 ms, R2 = 12 ms, R3 = 45 ms, R4 = 20 ms. Model answer

  • t = 12: R2's timer expires; R2 multicasts NACK(7). It reaches all at t = 22.
  • t = 20: R4's timer expires. R4 has not yet heard R2's NACK (it arrives at 22), so R4 also multicasts NACK(7).
  • t = 22: R1 (timer 30) and R3 (timer 45) hear R2's NACK and suppress their own.

The timers must be spread over an interval clearly larger than the propagation delay. Otherwise many timers expire before the first NACK arrives, and suppression fails.

Why

Suppression works only for timers that expire after the first NACK has arrived. Larger random delays mean better suppression but a slower recovery. This is the basic trade-off of SRM.

§5

Reliable group communication: faulty processes and virtual synchrony

Core idea. When processes can crash or join and leave, a message must be delivered to all members or to none, in the same order: atomic multicast. Close synchrony is impossible with failures. Virtual synchrony is the weaker model: crashed processes are purged, every message is delivered between two view changes, and a crashing sender's message reaches all or none. ISIS implements it with stable messages and flush.

Q26DescribeExam 14 Feb 2024 (second part)

How does the reliable multicast problem change if processes may fail? Define virtual synchrony and describe its implementation in ISIS. Give the table of multicast types.

Model answer

Now a message must reach all non-faulty members or none, and the members must agree on who is in the group. Atomic multicast also requires the same order at all receivers. Close synchrony (instantaneous delivery to all) is impossible with failures.

Virtual synchrony. Distinguish receive (by the communication layer) and deliver (to the application). A group view is the set of processes to which a message should be delivered, as seen by the sender at sending time. View changes are delivered in a consistent order with respect to other multicasts and to each other. Every message is delivered entirely before or after a view change, never across it. Crashed processes are purged and must rejoin. Messages of a correct process are delivered to all correct processes; messages of a crashing sender are delivered to all or dropped.

ISIS implementation (reliable FIFO point-to-point channels). A process keeps each message until it is stable (all members received it). On a view change message: stop sending new messages, multicast all unstable messages to the non-faulty members of the old view, mark them stable, then multicast a flush. Install the new view after a flush from every other member of the new view. So all survivors have the same messages before the new view starts.

Why

Because of FLP, you cannot know if a crashed process received a message. Virtual synchrony avoids the question: the crashed process is simply removed, and the survivors make sure they all have the same set of messages before they move on.

Q27Describe

Explain with a replicated database why atomic multicast is needed. What is close synchrony, and why can it not be achieved? Why does virtual synchrony separate "receive" from "deliver"?

Model answer

Replicated database. Every replica applies the update commands it receives. Everything is fine if all non-faulty replicas receive the same commands in the same order. If one replica misses an update, or applies two updates in another order, the replicas diverge.

Close synchrony (the ideal): any two processes that receive the same multicasts or observe the same membership changes see them in the same order; a multicast is delivered to the full membership, and send and delivery are one single instantaneous event. With failures this is impossible: a sender can crash in the middle of a multicast, and nobody can know whether the crashed process received or processed a message.

Receive vs deliver. The communication layer receives a message and buffers it. It delivers it to the application only when a condition holds (e.g. the message is known to all, or its predecessors in the required order have been delivered). This buffer gives the middleware time to agree on what to deliver, without exposing partial states to the application.

Why

The buffer is the tool behind every ordering guarantee. A message can be received early, but it is delivered only when delivering it keeps the promise of the model.

Q28Scenario

View (p, q, r). p multicasts m and then crashes; the new view is (q, r). For each case, is it allowed by virtual synchrony? (a) q and r deliver m before they install (q, r). (b) Neither q nor r ever delivers m. (c) q delivers m before the view change; r never delivers m. (d) q delivers m before the view change; r delivers m after it installed (q, r).

Model answer

  • (a) Allowed. All survivors deliver m in the old view.
  • (b) Allowed. The message of a crashing sender may be dropped, if it is dropped by all.
  • (c) Not allowed. m reaches some correct members and not others: "all or none" is violated.
  • (d) Not allowed. m is delivered in two different views. Every message must be delivered between the same two view changes at all members.

Why

A view change works like a barrier. Each member must see the same set of messages before the barrier. Case (d) has the right set of receivers but the wrong side of the barrier: r's state in view (q, r) differs from q's.

Q30Exercise

  2. P1 has m4 unstable: it multicasts m4 to P2 and P3, marks it stable and multicasts a flush.
  3. P3 has m3 unstable (P4 never acknowledged it): it multicasts m3 to P1 and P2 (they discard the duplicates), marks it stable and multicasts a flush.

§6

Recovery: checkpointing and logging

Core idea. Backward recovery returns to a saved correct state; forward recovery moves to a new correct state. Checkpoints must form a recovery line: the most recent consistent cut. Independent checkpoints risk the domino effect and need dependency tracking; coordinated checkpoints avoid it. Logging lets you replay messages after a checkpoint, if the system is piecewise deterministic.

Q31Exercise

Define backward and forward recovery. Classify: (a) TCP retransmits a lost segment; (b) a video stream uses erasure correction codes to rebuild a lost packet; (c) a process restarts from its last checkpoint; (d) a RAID-5 array rebuilds a lost block from parity. Then explain the difference between checkpointing and logging.

Model answer

Backward recovery: bring the system back to a previously saved correct state. Forward recovery: bring the system into a new correct state from which it can continue.

  1. Backward (send again what was lost).
  2. Forward (compute the missing data from redundancy).
  3. Backward.
  4. Forward (same idea as erasure correction).

Checkpointing: periodically save the distributed state to stable storage. It is expensive. Logging: record events (messages) to stable storage, so that you can replay them from a checkpoint.

Why

Forward recovery needs to know in advance which errors can happen, so that you can add the right redundancy. Backward recovery is general, so it is the common choice, but you must save states, and you lose the work done after the save.

Q32DescribeExam 17 Jan 2024 · 14 Feb 2024 · 13 Jul 2015 · 3 Dec 2014

When are rollback-dependency and checkpoint-dependency graphs used, how is the data to build them collected, and which general goal does the algorithm solve? Give the rules to build each graph and to compute the recovery line.

Model answer

Goal: find the recovery line, i.e. the most recent consistent cut made of one checkpoint per process.

When: with independent (uncoordinated) checkpointing, after a failure.

Data collection:

  • Each process numbers its checkpoint intervals: Ii,x lies between ci,x−1 and ci,x.
  • Each message piggybacks the sender's current interval.
  • The receiver records the dependency Ii,x → Ij,y with the rest of its recovery information.
  • After a failure, the recovering process broadcasts a dependency request; all processes stop and send their dependency information.
  • The recovering process computes the recovery line and sends the rollback requests.

Rollback-dependency graph: an edge ci,x → cj,y if i = j and y = x + 1, or if i ≠ j and a message is sent from Ii,x to Ij,y. Mark the failure states and every node reachable from them. Each process rolls back to its last unmarked checkpoint.

Checkpoint-dependency graph: an edge from ci,x−1 (the checkpoint that starts the sending interval) to cj,y. Start from the latest checkpoint of the failed process and the current states of the others. While one of these nodes is reachable from another, replace it with its previous checkpoint. The result: the latest checkpoints with no dependencies among them.

Why

Independent checkpoints are cheap to take but expensive to use: you need bookkeeping on every message, you may need a domino rollback, and some checkpoints are useless. That is why coordinated checkpointing is usually preferred.

Q37Compare

Compare independent, coordinated (blocking and snapshot-based), incremental and communication-induced checkpointing.

Model answer

  • Independent: each process checkpoints alone. Cheap, but domino effect, useless checkpoints, dependency tracking on every message.
  • Coordinated, blocking: the coordinator sends CHKP-REQ; each receiver takes a checkpoint, queues outgoing application messages, and sends an ACK; when all are done the coordinator sends CHKP-DONE. No useless checkpoints; processes block during the protocol.
  • Incremental: request a checkpoint only from processes that depend on the recovery of the coordinator: those that received a message causally dependent (directly or indirectly) on one sent by the coordinator after its last checkpoint.
  • Coordinated with a global snapshot (Chandy–Lamport): processes are not blocked; the algorithm is more complex.
  • Communication-induced: independent checkpoints, plus information piggybacked on messages that tells a process when it must take an extra checkpoint, to avoid the domino effect.

Why

The trade-off is coordination cost at checkpoint time against complexity and lost work at recovery time.

Q38Scenario

(a) In blocking coordinated checkpointing, P2 receives CHKP-REQ, takes its checkpoint, and then does not queue its outgoing messages: it sends m to P3 at once. P3 receives m before CHKP-REQ. What goes wrong? (b) Incremental snapshot. Since its last checkpoint, coordinator P1 sent x to P2. Then P2 sent y to P3. P4 sent z to P1. Q39Compare

Describe message logging. Define piecewise deterministic, stable message, DEP(m), COPY(m) and orphan process. Compare pessimistic and optimistic logging.

Model answer

Start from a checkpoint and replay the logged messages. Each message header contains the information to replay it. It works if the system is piecewise deterministic: execution proceeds deterministically between the receipt of two messages.

  • Stable message: written to stable storage; it can no longer be lost.
  • DEP(m): processes to which m, or a message m' that depends on m, has been delivered.
  • COPY(m): processes that have a copy of m, not yet in stable storage; they could hand it over to replay it.
  • Orphan: a surviving process Q in DEP(m) when every process in COPY(m) has crashed. m can never be replayed, but Q depends on it.

To avoid orphans: every process in DEP(m) must also be in COPY(m); a process that becomes dependent on m keeps a copy of m.

Pessimistic: an unstable message is delivered to at most one process; the receiver is in COPY(m), and it sends no other message until it writes m to stable storage. No orphans ever; slower. A variant logs messages at the sender.

Optimistic: log asynchronously, hoping it finishes before a crash. If all of COPY(m) crash, roll back DEP(m) until they no longer depend on m (like uncoordinated checkpointing). Faster in normal operation; complex recovery.

Logging was designed for uncoordinated checkpointing, but coordinated checkpointing with logging gives better performance.

Why

The same trade-off as pessimistic vs optimistic concurrency control: pay always to prevent the problem, or pay only when it happens.

Q40Exercise

P1 sends m to P2 and keeps a copy in memory. m is not yet on stable storage. P2 delivers m, then sends m' to P3; P3 delivers m'. (a) Give DEP(m) and COPY(m). (b) P1 and P2 crash.   2. All of COPY(m) crashed, and P3 survives in DEP(m): P3 is an orphan. m can never be replayed.
  3. No orphan: P1 still has m, so P2 can recover from its checkpoint and replay m.
  4. Pessimistic: P2 must write m to stable storage before it sends m'. Then m is stable before anyone else depends on it, and no orphan can appear. Optimistic: in case (b) P3 is rolled back to a state before it delivered m', so that it is no longer in DEP(m).

Why

An orphan is a process whose state depends on something that nobody can rebuild. Pessimistic logging keeps the rule "if you depend on m, m is safe" at every step. P3 is the trap: it never received m, but it depends on m through m'.

Q41Scenario

A server recovers with checkpoint + message logging. Between two messages, it reads the local clock to timestamp records and calls rand() to choose a worker thread. After a crash, the replayed state differs from the lost state. Why? How do you fix it?

Model answer

Logging assumes a piecewise deterministic system: the execution between two receipts depends only on the state and on the received message. Reading the clock and calling rand() (and thread scheduling) are non-deterministic events. During replay they give other values, so the process reaches another state, and the messages it sent before the crash may no longer match its new state.

Fix: treat each non-deterministic event as an input and log it like a message (the clock value, the random seed or the chosen value). During replay, read the values from the log. Alternatively, remove the non-determinism (seed the generator from the checkpointed state, use logical timestamps).

Why

Replay rebuilds a state only if the same inputs give the same outputs. Every hidden input breaks that promise, so it must become a logged input.
