§1

Software architecture: network OS vs middleware

Core idea. The software architecture tells where the "distribution" services live. With a network OS, the application programmer handles platform differences. With middleware, a layer between OS and application hides those differences and gives higher-level services.

Q1Compare

Describe and compare the network-OS-based and the middleware-based software architectures of a distributed system.

Model answer

Network-OS based. Each machine runs its own network OS. The OS gives only basic communication services (for example sockets). Different machines can have different OSes. The application programmer must mask these platform differences.

Middleware based. A middleware layer sits between the network OS and the applications. It gives a standard API on every machine. It masks most platform differences. It also gives advanced services: communication and coordination, special application services, and management services.

Comparison. Middleware raises the abstraction level and improves portability and interoperability. The cost is an extra layer (some overhead) and dependence on a specific middleware.

Why

A distributed system is heterogeneous: different hardware, OSes and languages. Somebody must hide this heterogeneity. In the first model the application does it, so every application repeats the same work. Middleware does it once, for all applications. This is the main reason why middleware exists.

Q2Describe

Which services does a middleware usually provide? What does it mean that these services are "business-unaware"?

Model answer

  • Communication and coordination: synchronous and asynchronous, point-to-point or multicast. These services mask the differences of the network OS.
  • Special application services: distributed transactions, groupware and workflow, messaging, notification services.
  • Management services: naming, security, failure handling.

"Business-unaware" means that the services do not depend on the application domain. A bank and a game can use the same messaging or naming service.

Why

Middleware is general-purpose. It solves the problems that every distributed application has (find a peer, send a message, handle a failure). The business logic stays in the application. This separation makes the middleware reusable.

§2

Run-time architecture: architectural styles

Core idea. The run-time architecture names the component types, the connectors between them, and the data they exchange. The course lists eight styles: client-server, service oriented, REST, peer-to-peer, object-oriented, data-centered, event-based, mobile code.

For each style, know three things: who has which role, how components communicate, and one pro and one con.

Q3Describe

Describe the client-server style. What is a multi-tiered architecture, and how can the three classes of services be split between tiers?

Model answer

Components have different roles. Servers offer services through a well-defined API and are passive: they wait for requests. Clients access the services. Communication is message based or RPC. The Web is the main example.

A server can itself be the client of another server. Then the system has more tiers. The services split into three classes: user interface, application logic, data storage.

  • Two tiers: client and server. The split can be in many places: only the GUI on the client (thin client), GUI and part of the application on the client, or GUI, application and some data (cache) on the client (fat client).
  • Three tiers: GUI on the client, application logic on an application server, data on a DBMS server. Example: browser, web/application server, database.
  • N tiers: the application tier itself splits into many components, each one a server for the previous.

Why

Tiers let you scale and manage each class of service on its own. You can replicate the application tier without touching the database. A thin client is easy to update, because the logic stays on the server. A fat client lowers server load and latency, but it is harder to keep up to date.

Exam tip

Draw the small table "GUI / Application / Data" with a line that moves between client and server. A small drawing gets the point across faster than a long paragraph.

Q4DescribeExam 23 Sep 2015

Describe the Service Oriented Architecture in general and the Web Service technology as an example of its implementation.

Model answer

SOA uses four concepts:

  • Services: loosely coupled units of functionality.
  • Service providers: they export services.
  • Service brokers: they hold the descriptions of available services.
  • Service consumers: they search the broker, then bind to and invoke the services they need.

Orchestration is the invocation of a set of services in an ad-hoc workflow to reach a goal. Incarnations: OSGi, Jini, JXTA, Web Services.

Web Services (W3C: "a software system designed to support interoperable machine-to-machine interaction over a network"):

  • WSDL describes the interface: the set of operations.
  • SOAP is the XML-based protocol for messages (operation calls). It usually runs on HTTP, but it can use other transports.
  • UDDI is the registry. It defines how to publish and search web services. UDDI is the broker.

Why

Map each SOA role to a technology: provider = the web service, description = WSDL, broker = UDDI, invocation = SOAP. This mapping is the core of the answer. It also shows why SOA is loosely coupled: the consumer knows only the description, and it finds the provider at run time.

Q5Describe

List the main constraints of the REST style. Why does the "stateless" constraint improve scalability?

Model answer

  1. Interactions are client-server.
  2. Interactions are stateless: the client sends all the state the server needs.
  3. Responses are labeled as cacheable or not.
  4. The system is layered: a component sees only the next layer.
  5. Code on demand (optional).
  6. Uniform interface, with four sub-constraints: identification of resources (URIs); manipulation through representations (data + metadata, format chosen dynamically); self-descriptive messages (control data tells the action, e.g. the HTTP method and cache headers); hypermedia as the engine of application state (links move the client from state to state).

The goals: scalability, general interfaces, independent deployment of components, and intermediaries (proxies, caches, gateways).

Why stateless helps

The server keeps no session state. So any server replica can serve any request. A load balancer can send requests anywhere, and a crashed server loses no session. Caches and proxies can also work, because each request is complete on its own. The cost is larger messages, because the client resends its state every time.

Q6CompareRelated: 5 Sep 2013

Why was the peer-to-peer style introduced? Compare it with client-server. What is a "pure" P2P system?

Model answer

In P2P all components have the same role. There is no distinction between clients and servers. Peers share resources by direct exchange: CPU cycles (SETI@home), collaboration (Skype), storage (Freenet), bandwidth, data.

Client-server problems that P2P solves:

  • It does not scale well, because service provision and management are centralized.
  • The server is a single point of failure.

P2P works because end hosts now have much processing power and broadband connections. The idea: "take advantage of resources at the edges of the network".

A pure P2P system has no central component at all. Napster is not pure (central index). Original Gnutella is pure. Kazaa (super-peers) and BitTorrent (trackers) are hybrid.

Why

In client-server, more clients means more load on one server. In P2P, every new peer also brings resources. So capacity grows with the number of users. The cost: P2P is harder to manage, to secure and to search.

Q7Describe

Describe the object-oriented style. Why is it called "peer-to-peer" if it is often used to build client-server applications? Give its advantages.

Model answer

Each component encapsulates a data structure and gives an API to access and change it. The component keeps the data consistent. Its internal organization is hidden. Components interact through RPC (remote method invocation).

It is "peer-to-peer" because every object can call any other object: there are no fixed roles. But in practice a set of objects often acts as a server.

Pros:

  • Information hiding hides the complexity of the shared data.
  • Encapsulation makes management easier. For example, you can move server objects at run time to share the load.
  • Objects are easy to reuse.
  • You can wrap legacy components inside objects.

Why

The client calls only the interface. So the object can move or change its internals without any change on the client. This is the same principle as OO programming, applied across machines.

Q8Describe

Describe Linda and the tuple space model. Explain the operations out, rd, in, and the probes rdp, inp. Why is communication called "persistent, implicit, content-based, generative"?

Model answer

Linda (Carriero and Gelernter, 1980s) is a data-centered style. Data are tuples: ordered sequences of typed fields, e.g. <"Italy", "Milan">. Tuples live in a persistent, global, shared tuple space.

  • out(t): writes tuple t.
  • rd(p): returns a copy of a tuple that matches template p. It blocks if there is no match. If many tuples match, it chooses one non-deterministically.
  • in(p): like rd, but it removes the tuple.
  • eval(a): some implementations; inserts the tuple that process a generates.
  • rdp(p), inp(p): non-blocking probes. They return null at once if there is no match.
  • Persistent: a tuple stays in the space after the writer terminates.
  • Implicit: the writer does not name the reader.
  • Content-based: the reader selects tuples by their content (template), not by an address.
  • Generative: a tuple has its own life, independent of the process that made it.

Why

These four properties give decoupling in space (processes do not know each other) and decoupling in time (the writer and the reader do not need to be alive at the same time). This high decoupling is the strength of the model.

Q9Scenario

You must implement a tuple space distributed over a wide-area network. Which problems do you meet? Why do probes (inp, rdp) need a distributed transaction? What do commercial products do instead?

Model answer

  • Storage: how to store and replicate tuples efficiently over many nodes.
  • Routing: how to route a query (template) to the node that holds a matching tuple.
  • Proactive only: processes must ask for tuples. For a reactive behavior you need an extra process blocked on rd.

Probes. inp(p) can return null only if no node holds a match at that moment. So the system must check all nodes as one atomic step. Otherwise a matching tuple can arrive on a node that you already checked. This atomic global check is a distributed transaction.

Commercial products (JavaSpaces, TSpaces, GigaSpaces) use one server that holds the tuple space, with remote clients. They also add reactive operations such as notify, which registers a listener that the space calls when a matching tuple is written.

Why

A blocking rd is easy to distribute: you wait until any node answers. A "no" answer is hard: to say "no tuple exists", you must look at the whole system at the same instant. In a distributed system, a global instant does not exist without coordination. This idea comes back in the snapshot and agreement chapters.

Q10CodeExam 5 Sep 2013

Implement in Java the class IntSpace: a Linda tuple space where tuples and patterns are integers. out(t) writes t. rd(p) returns at once if p is present (without removing it), else it suspends the caller. in(p) is like rd but removes p. When readers and inputters wait for the same integer, a new out must wake the readers first, then one inputter. Use only the base Java synchronization.

Model answer

import java.util.*;

public class IntSpace {
  // value -> number of copies in the space (a multiset)
  private final Map<Integer,Integer> tuples  = new HashMap<>();
  // value -> number of readers that wait for it
  private final Map<Integer,Integer> readers = new HashMap<>();

  private static int count(Map<Integer,Integer> m, int k) {
    return m.getOrDefault(k, 0);
  }

  public synchronized void out(int t) {
    tuples.merge(t, 1, Integer::sum);
    notifyAll();                      // wake readers and inputters
  }

  public synchronized int rd(int p) throws InterruptedException {
    readers.merge(p, 1, Integer::sum);
    try {
      while (count(tuples, p) == 0) wait();
    } finally {
      readers.merge(p, -1, Integer::sum);
      notifyAll();                    // inputters may continue now
    }
    return p;
  }

  public synchronized int in(int p) throws InterruptedException {
    // give priority to readers: wait while a reader for p still waits
    while (count(tuples, p) == 0 || count(readers, p) > 0) wait();
    tuples.merge(p, -1, Integer::sum);
    return p;
  }
}

Why

  • All methods are synchronized, so the maps are always consistent.
  • Each wait() is inside a while: after a wake-up, the thread checks its condition again (spurious wake-ups, or another thread took the tuple first).
  • Use notifyAll(), not notify(): threads wait for different values, so one notify() can wake the wrong thread and lose the signal.
  • The readers counter gives the required order. An inputter cannot take p while a reader for p still waits. Each reader decrements the counter on exit and calls notifyAll(). After the last reader leaves, exactly one inputter removes the tuple. The others see count 0 and wait again.

Exam tip

In these Java questions the grader checks three things: mutual exclusion, while around wait, and the correct wake-up policy. State your policy in one comment line.

Q11CompareExam 17 Jan 2024

Describe the event-based (publish-subscribe) style. Then compare it with RPC: addressing (unicast vs multicast, implicit vs explicit), synchronicity, persistency.

Model answer

Components publish notifications about the events they observe. Components subscribe to the events they want to receive (e.g. topic=fire* & place=1st floor). An event dispatcher delivers each notification to all matching subscribers. Communication is message based, asynchronous, multicast, implicit and anonymous.

RPCPublish-subscribe
AddressingUnicast, explicit: the caller names the server.Multicast, implicit: receivers are chosen by their subscriptions.
SynchronicitySynchronous: the caller blocks until the reply.Asynchronous: the publisher continues at once.
PersistencyTransient: both parties must be alive.Usually transient: only subscribers connected now receive the event.
CouplingCaller and callee know each other.Publishers and subscribers do not know each other.

Why

Pub-sub is good when the producer does not know (or must not know) who needs the information: monitoring, alarms, news feeds. RPC is good when you need a result to continue. Note the difference with Linda: Linda is persistent and proactive (the reader asks), pub-sub is reactive (the system pushes events to you).

Q12DescribeExam 14 Feb 2024 · 13 Feb 2015 · 19 Sep 2013

Describe the mobile code paradigms, making appropriate examples.

Model answer

Mobile code lets you relocate components at run time: only the code, or the code and its state. The paradigms differ by where three things are before and after the interaction: the know-how (code), the resources, and the computational component (with its execution state). Component A on site A starts the interaction.

ParadigmBeforeAfterCake metaphorExample
Client-server (reference, no mobility)B has know-how and resourcesSame; A gets the result"Please make me a chocolate cake."HTTP request for a page; call to a remote API.
Remote evaluationA has know-how; B has resourcesKnow-how moves to B; B runs it"Make me a cake. Here is the recipe."Send a script via ssh; a Spark/MapReduce job sent to the data nodes; PostScript sent to a printer.
Code on demandA has resources; B has know-howKnow-how moves to A; A runs it"Please tell me the recipe."JavaScript in a web page; Java applets; download of plug-ins.
Mobile agentA has know-how and the component; B has resourcesComponent (code + state) moves to B"Here I am. Can I use your oven?"An agent that visits many shops to compare prices, then comes back.

Pros: high flexibility. You can update components without a stop, add new functions and services, and adapt services to the client. Con: security is very difficult (protect the host from the code, and the code from the host).

Why

The key question is always "what moves, and in which direction?". Remote evaluation moves code towards the data: good when data is large and code is small. Code on demand moves code towards the user: good to lower server load and latency. Mobile agent moves the whole running unit: good for disconnected operation, but it needs strong mobility.

Exam tip

The question says "making appropriate examples". Give one real example per paradigm. Also add the strong vs weak mobility point (next question) for full marks.

Q13Compare

Define strong and weak mobility. Which one does Java provide? Why is strong mobility rare?

Model answer

Strong mobility: the system can move the code and the execution state (stack, program counter) of a running unit to another environment. Only a few research systems provide it.

Weak mobility: the system can move only the code (and maybe some data). Execution starts again from the beginning or from a fixed entry point. Java, .NET and the Web provide it.

Java gives weak mobility: dynamic class loading and object serialization. A Java "mobile agent" must save its state into fields by hand and restart from a known method.

Why

The execution state is inside the virtual machine (thread stack, program counter). Standard VMs do not let a program capture and restore it. Also, the target machine can have a different architecture. So capturing a running thread and resuming it elsewhere needs a modified VM.

Q14Scenario

Name the architectural style or mobile code paradigm for each case and justify it: (a) a browser downloads a script that checks a form before submission; (b) a scientist sends an analysis program to the cluster that holds 50 TB of telescope data; (c) sensors of a building send "temperature > 40°C on floor 2" and the fire-control and logging systems receive it; (d) worker processes take tasks from a shared bag of tasks and put back results.

Model answer

  1. Code on demand. The know-how (script) moves from the server to the client, which has the resource (the form data).
  2. Remote evaluation. The code is small and the data is huge. Move the code to the data.
  3. Event-based (publish-subscribe). Sensors do not know who is interested. Many receivers get the same event. Communication is asynchronous.
  4. Data-centered (Linda tuple space). Workers do in(<"task", ?x>) and out(<"result", r>). Workers and master are decoupled in time and space. Load balances automatically: a free worker takes the next task.

Why

Scenario questions test if you can choose by properties, not by names. Ask: who knows whom? Who must be alive at the same time? What moves: data or code? The answer to these questions points to the style.

§3

Interaction model: synchronous vs asynchronous

Core idea. A distributed algorithm depends on three timing factors: process speed, message delay, clock drift. A synchronous system has known bounds on all three. An asynchronous system has no bounds. Some problems (agree on "who") work in both. Problems that need time (agree on "when", detect a crash) work only with bounds.

Q15Describe

Define synchronous and asynchronous distributed systems. Why is a solution for an asynchronous system also valid for a synchronous one, but not the other way?

Model answer

Synchronous: (1) the time for each process step has known lower and upper bounds; (2) each message arrives within a known bounded time; (3) each local clock has a known bound on its drift from real time.

Asynchronous: no bounds on process speed, message delay or clock drift.

An asynchronous algorithm makes no timing assumption. A synchronous system respects every assumption that this algorithm makes (none). So the algorithm works there too. A synchronous algorithm uses the bounds (e.g. timeouts). In an asynchronous system the bounds do not exist, so the algorithm can fail.

Why

Think of it as "fewer assumptions = more general". The asynchronous model is a worst case. The Internet is close to asynchronous, so algorithms for the asynchronous model are the safest choice. But some problems have no solution there (see Q17 and FLP).

Q16Scenario

In Pepperland, two divisions on two hills must agree on who leads the charge and when to charge. Messengers always arrive. (a) How can they agree on the leader in asynchronous Pepperland? (b) Why can they not charge together in asynchronous Pepperland? (c) How do they charge together in synchronous Pepperland?

Model answer

(a) Leader. Each general sends a messenger with a value (for example the number of soldiers, or a random number). Each general compares the two values with the same deterministic rule: the larger value leads; on a tie, a fixed order of the names decides. The messengers always arrive, so after a finite time both generals have the same two values. They then make the same decision. No time bound is necessary.

(b) Charge together. If the leader sends "charge!", the messenger can take 5 minutes or 3 hours. The leader does not know when the other division charges. A message with a time ("charge at 15:00") does not help, because the clocks can drift without limit.

(c) Synchronous. Let min and max be the bounds on message delay. The leader sends "charge!", waits min, then charges. The other general charges when the message arrives. The second division charges at most max − min after the first. If the charge lasts longer than max − min, the two charges overlap and victory is certain.

Why

"Who" is a decision on data: it needs only that all messages arrive eventually. "When" is a decision on time: it needs bounds. This is the general lesson of the interaction model. Ask yourself if a problem is about data or about time.

Q17Exercise

Synchronous Pepperland: message delay is between 20 and 60 minutes. A charge lasts 30 minutes. With the protocol of the slides (leader waits min, then charges), is victory guaranteed? Can you change the leader's waiting time to guarantee it?

Model answer

Slide protocol. The gap is up to max − min = 60 − 20 = 40 minutes. The charge lasts 30 minutes, which is less than 40. So victory is not guaranteed.

Better wait. Let the leader wait w before it charges. D2 charges at arrival a ∈ [20, 60]. The worst gap is max(|20 − w|, |60 − w|). This is smallest at the midpoint, w = (min + max)/2 = 40. Then the gap is at most (max − min)/2 = 20 minutes < 30. Victory is guaranteed.

Why

With w = min, the leader always charges first, and the full uncertainty falls on one side. With the midpoint, the uncertainty is split in two halves: D2 can be up to 20 minutes early or late. Victory needs overlap, not order, so the symmetric choice is better. This is the same idea as Cristian's algorithm in the synchronization chapter (estimate the delay with the midpoint).

Exam tip

The exam often adds a small twist to a slide example. Write the general formula first, then the numbers.

§4

Failure model

Core idea. Processes and channels can both fail. The failure model lists how they can fail: omission (something does not happen), Byzantine (something wrong happens), timing (something happens too late or too early; only in synchronous systems). The weaker the model, the more expensive a correct system becomes.

Q18DescribeExam 6 Sep 2024 · 3 Dec 2014 · 13 Jul 2015

Discuss (classify) the various types of failures that can happen in a distributed system. Give a practical example of each. Briefly discuss how difficult it is to build a correct system under each type.

Model answer

Difficulty. Fail-stop is the easiest: you know who failed. Crash is harder: you must suspect, not know. Timing failures break the assumptions of synchronous algorithms. Byzantine is the hardest: you cannot trust any single message. As an order of magnitude, to tolerate k faulty processes you need k+1 replicas for fail-silent processes, 2k+1 to mask Byzantine values by voting, and 3k+1 for Byzantine agreement (see the fault-tolerance chapter).

Why

The classes go from "benign" to "malicious". With omission, a received message is always correct; the only question is if it arrives. With Byzantine, a message can arrive and be wrong. So you need redundancy and voting. With crash vs fail-stop, the difference is only detection, and detection depends on the interaction model (next question).

Exam tip

The 2024 text says "make a practical example of each". A table with one example per row answers it quickly and clearly.

Q19Exercise

Classify each failure: (a) a process computes a wrong checksum because of a memory bit flip; (b) the receiver's socket buffer is full and the OS drops a packet; (c) a router reboots and loses its queue; (d) in a system with a 100 ms delay bound, a message arrives after 300 ms; (e) a network card sends each frame twice.

Model answer

  1. Byzantine process failure: the process does a wrong step.
  2. Receive omission: the message reached the machine, but not the process.
  3. Channel omission: the messages are lost inside the network.
  4. Timing failure: a bound of the synchronous model is violated.
  5. Byzantine channel failure: a real message is delivered more than once.

Why

For each case ask two questions. Where is the problem: process, or channel (and which part of the channel)? What is wrong: missing (omission), wrong (Byzantine), or late (timing)?

Q20Exercise

How do you detect a defeated division in synchronous Pepperland, and why is it impossible in asynchronous Pepperland? Numeric part: a division sends "I am still here" every T = 10 minutes. Message delay is between min = 5 and max = 30 minutes. After the last message received, how long must the other general wait before he decides "defeated"?

Model answer

Synchronous: each division sends periodic heartbeats. If no heartbeat arrives within the bound, the other division is defeated. Asynchronous: a late heartbeat and a defeated division look the same. The messenger can be just very slow. So you cannot decide.

Numbers. The last heartbeat arrived at time r. It was sent at s, with s ≥ r − max and s ≤ r − min. The next heartbeat is sent at s + T and arrives at most at s + T + max ≤ r − min + T + max.

Timeout = T + max − min = 10 + 30 − 5 = 35 minutes.

Why

The slide gives the idea ("no messengers for longer than max"). The exact timeout must count the period T and the uncertainty max − min of the previous message. A shorter timeout gives false suspicions. A longer timeout is safe but slow. In the asynchronous model no finite timeout is safe, so crash is not distinguishable from slowness. This is why fail-stop needs a synchronous system.

Q21Exercise

In "failing Pepperland" the enemy can capture messengers. Prove that the two generals cannot be sure to agree on "charge" or "surrender".

Model answer

  1. To agree on a decision, at least one message must arrive.
  2. Suppose a protocol exists. Let scenario A be the run that reaches agreement to attack with the fewest delivered messages.
  3. Let scenario B be equal to A, but the last message of A is lost, and all later messages are lost too.
  4. Say the last message goes from General 1 to General 2. General 1 sees the same messages in A and B. So he attacks in both.
  5. A is minimal. So in B, General 2 (who has one message less) cannot decide to attack. He decides differently.
  6. In B the generals disagree. Contradiction: no such protocol exists.

Why

The sender of the last message never knows if it arrived. An acknowledgment does not help: then the ack is the last message, and the problem moves to its sender. This "last message" argument works for any number of messages. The proof uses the minimality of A to make that argument rigorous.

Q22Describe

What does the FLP theorem state? Why does it matter in practice, and how do real systems work around it?

Model answer

FLP (Fischer, Lynch, Paterson, 1985): in an asynchronous system where even one process can crash, no deterministic algorithm can guarantee that consensus is always reached.

Why it matters: many real tasks are consensus problems:

  • Commit or abort a distributed transaction (e.g. a cash withdrawal at an ATM).
  • Agree on the values of replicated sensors.
  • Agree that a component is faulty.

Workarounds:

  • Change the assumptions: e.g. make links reliable enough, or assume partial synchrony (timeouts that are usually correct).
  • Reduce the guarantees: e.g. probabilistic instead of deterministic agreement, or safety always but progress only when the network is stable (this is what Raft and Paxos do).

Why

In an asynchronous system you cannot tell a crashed process from a slow one (Q20). An algorithm that waits for the slow process can wait forever. An algorithm that does not wait can decide without it, and then the slow process can decide differently. FLP proves formally that this dilemma has no deterministic way out. Link this to the Raft question of recent exams: Raft guarantees safety, but liveness only when timing is good.
