§1

Basics: names, addresses, identifiers

Core idea. A name refers to an entity. You reach the entity through an access point, which has an address. An entity can have many access points and can change them, so an address is a bad name. An identifier is a name that never changes and is never reused. Name resolution maps a name to the address of an access point.

Q1Describe

Define name, address and identifier. Why should we not use an address as the name of an entity? What does an identifier make possible?

Model answer

  • Name: a string that refers to an entity (host, user, file, service). Names can be global (same entity everywhere) or local (meaning depends on where you use it), human-friendly ("My Mobile") or machine-friendly (00:15:2A:2E:E1:97).
  • Address: the name of an access point of the entity. An address is a special name.
  • Identifier: a name with three properties: (1) it never changes during the life of the entity; (2) each entity has exactly one identifier; (3) it is never assigned to another entity.

Do not use an address as a name: an entity can have many access points at the same time (e-mail, mobile, office phone), and it can change them (a laptop gets a new IP at home). A good name is location-independent.

Identifiers split the problem in two: name → identifier (naming) and identifier → address (locating). Only the second mapping changes when the entity moves.

Why

Mobility is the reason. If the name contains the location, every move breaks every stored name. With an identifier in the middle, the name stays valid and only the location service updates. Examples of resolution: DNS (domain → host), LDAP (person → e-mail, phone), RMI registry (name → remote reference), UDDI (service description → service metadata).

§2

Flat naming

Core idea. A flat name is a string with no structure. It tells nothing about where the entity is. Four families of solutions: simple (broadcast, multicast, forwarding pointers), home-based, DHT, hierarchical.

Q2Compare

Describe and compare the simple solutions for flat naming: broadcast, multicast, forwarding pointers. Where are they suitable?

Model answer

They are made for small scale (a LAN).

  • Broadcast: like ARP. Send "find X" on the broadcast channel; only X replies. Problem: every host processes every request → traffic and CPU overhead.
  • Multicast: the same, but to a multicast group, which reduces the scope of the search.
  • Forwarding pointers (for mobile entities): when the entity moves, it leaves a reference to its new location at the old one. Problems: chains become long; a broken link breaks the chain; latency increases at each dereference; chain reduction is complex (when and how to clean up?).

For distributed objects, the forwarding pointers are proxies that forward to the next proxy or to the real object. You can short-cut the chain by sending the current location back to the first proxy (along the path, or directly). Skeletons know when no proxy refers to them, so they can be deleted.

Why

Broadcast asks everybody, so cost grows with the number of hosts. Forwarding pointers ask nobody, but cost grows with the number of moves. Neither scales to the Internet. That motivates the next three families.

Q3Describe

Describe the home-based approach (e.g. Mobile IP) and its problems.

Model answer

Each mobile entity has a home node that always knows its current location. The home is stable and can be replicated. The original IP of the host acts as its identifier. Used in Mobile IP and in cellular networks. A client contacts the home, which forwards the request (or returns the current address).

Problems:

  • The extra step to the home increases latency.
  • The home address must be supported for the whole life of the entity.
  • The home is fixed: a burden when the entity moves permanently elsewhere.
  • Poor geographical scalability: the entity can be next to the client, but the request travels to a far home.

Why

The home is a single fixed point of reference: simple, but it ignores locality. Example: you are in Milan, your home is in Tokyo, and your caller is also in Milan. Every lookup goes to Tokyo and back. A two-tier variant (look in a local registry first, then contact the home) fixes part of this. The hierarchical approach generalizes that idea.

Q4DescribeExam 27 Jun 2013

Describe the hierarchical approach to implement a flat naming system. How are lookup, insert and delete done? What are its problems?

Model answer

The network is divided into domains in a tree. The root domain spans the whole network; leaf domains are a LAN or a mobile cell. Each domain has a directory node that tracks the entities in that domain.

  • The root has an entry for every entity. An entry points to the sub-domain where the entity is.
  • A leaf holds the real address of an entity in its domain. An entity with several addresses (replication) has entries in several leaves.

Lookup: start at the leaf of the client. If the entry is not there, go up to the parent. When an entry is found, follow its pointers down to the leaf with the address. Local queries stay local (an expanding ring search).

Insert: starts at the new location. Records are created top-down or bottom-up; bottom-up allows queries at once.

Delete: starts at the old leaf and goes up. It stops at a node that still has other children with entries for that entity.

Problems:

  • The root holds data for all entities. Records are small, but lookups through the root make a bottleneck.
  • You can partition the root, but then assigning entities to root partitions is difficult. A user in the US, managed by the Italian part of the root, is inefficient.
  • Caching addresses directly is inefficient for mobile entities. You can short-cut the search if you know the mobility patterns.

Why

The tree gives locality: a nearby entity is found low in the tree, with few messages. The cost: a far entity needs a path through the root, and the root must know everybody, because a flat name does not tell which branch to take.

Q5Describe

Describe Chord: how nodes and keys are placed, the basic lookup, the finger table, the routing rule, and the cost (table size and number of hops).

Model answer

A DHT gives put(id, item) and item = get(id) on a structured overlay. For naming, the key is the name or identifier and the value is the address.

  • Nodes and keys are on a logical ring of 2m positions. Node id = hash of its IP. Key = hash of the item.
  • The item with key k is stored at the successor of k: the node with the smallest id ≥ k (wrapping around the ring).
  • Basic lookup: each node knows its successor. The query moves around the ring one node at a time: O(N) hops.
  • Finger table: m entries. Entry i of node n points to succ(n + 2i), for i = 0 … m−1. Finger i points about 1/2m−i of the way around the ring.
  • Routing rule (slides): a node that receives a query for key k checks if it stores k. If not, it forwards the query to the successor in the entry with the largest start (n + 2i) that does not exceed k (measured clockwise from n).
  • Cost: log N fingers per node; each hop at least halves the distance to k, so O(log N) hops.

Why

The fingers work like a binary search on the ring: the first jump covers about half the remaining distance, the next a quarter, and so on. This gives logarithmic routing with a logarithmic table. The hash spreads keys evenly, so the load is balanced. When nodes join or leave, only the keys of the neighbors move.

Q10ScenarioExam 12 Jul 2024

You implement a document lookup service: given a document key, find the host that holds the document. Scenario 1: tens of thousands of hosts that join and leave dynamically. Scenario 2: fewer than a hundred hosts that never join or leave. Where would you use Chord and why? How would you implement the other one?

Model answer

Scenario 1 → Chord.

  • Each node keeps only O(log N) entries: about 15 for 30,000 hosts. A full table would be too large and would change at every join or leave.
  • Lookup takes O(log N) hops.
  • A join or leave moves only the keys of one neighbor and updates a few fingers.
  • No central server: no bottleneck and no single point of failure.

Scenario 2 → full knowledge, one hop. With fewer than 100 static hosts, every host can keep the full list of hosts. Map a key to a host with a hash (e.g. consistent hashing, or hash(key) mod N, which is fine because N never changes). Any client finds the host in one hop. A replicated central directory is another valid option. Chord would add log N hops for no benefit.

Why

Chord pays extra hops to keep small tables and to handle churn. When the system is small and static, neither problem exists, so you do not need to pay. This kind of question checks that you know why a technique exists, not only how it works.

§3

Structured naming

Core idea. Names are paths in a name space: a labeled graph of directory nodes and leaf nodes. Large name spaces are split among name servers in three layers: global, administrational, managerial. DNS is the main example. The structure of the name tells the resolver where to go.

Q11DescribeExam 17 Jan 2024 · 3 Dec 2014

Describe the concept of structured naming and how a structured naming system can be implemented with a hierarchy of servers.

Model answer

Name space: a labeled graph.

  • A leaf node is a named entity. It stores information about the entity, at least its identifier or address.
  • A directory node has labeled outgoing edges, each to another node. A directory node is itself an entity, with an identifier.
  • Entities are named by path names, e.g. /alpha/beta/gamma, absolute or relative.
  • Many paths can lead to the same entity (hard links), or a leaf can store the path of another entity (symbolic link). A file system is an example.

Distribution. The name space is split into layers, and each node is assigned to a name server:

Resolution: iterative or recursive (next question).

Why

The layers match how stable the data is. Top-level directories (e.g. .it) almost never change, so they can be replicated a lot and cached for a long time. Lower nodes change often but are used locally, so one local server is enough. The table is what makes the system scale. Learn it as the core of the answer.

Q12Exercise

A client in Milan resolves ftp.cs.vu.nl. The servers are: root, nl, vu.nl, cs.vu.nl; the last three are in the Netherlands. Compare iterative and recursive resolution: who talks to whom, how many long-distance messages, and where caching helps.

Model answer

Iterative. The client asks the root, which returns the address of the nl server. The client asks nl, which returns vu. Then the client asks vu, then cs. That is 4 requests + 4 replies, all from Milan: about 8 long-distance messages. Only the client caches the intermediate results.

Recursive. The client asks the root (if the root accepts recursion). The root asks nl, nl asks vu, vu asks cs. Replies come back along the chain. Inside the Netherlands the messages are short; the client sends only 1 long-distance request and gets 1 reply. Each server on the chain caches the results for later queries.

IterativeRecursive
Communication costHigher for a far clientCan be lower
CachingOnly at the clientAt each server along the chain → faster lookups
Server loadLow: each server answers and forgetsHigh: each server keeps a thread suspended while it waits

In practice the client asks for a mode, but servers need not comply. Global servers support only iterative resolution.

Why

Recursive resolution moves the work and the waiting to the servers. That is good for caching and for far clients, but bad for heavily loaded servers. So the root and top-level servers, which get the most queries, refuse recursion.

Q13CompareExam 17 Jan 2024 · 9 Sep 2015 · 27 Jun 2013

Explain why the same hierarchy of servers does not perform equally well with flat names. How does the structure of names improve performance?

Model answer

With structured names, the name itself says which branch to follow: /nl/vu/cs/ftp goes root → nl → vu → cs.

  • Each server stores only its own part of the name space. The root knows only the top-level domains, not each entity.
  • Resolution goes top-down with no search.
  • Upper levels are stable, so clients can cache prefixes (e.g. the address of the vu.nl server) and skip the top for later names in the same domain.
  • Names follow the organization, so each administration manages its own subtree.

With flat names, the name gives no information about the location:

  • The root must store an entry for every entity → large tables and a bottleneck.
  • A lookup starts at the client's leaf and goes up until some node knows the entity, then down. A far entity always goes through the root.
  • You cannot cache prefixes, because there are no prefixes. Each entity must be cached alone.
  • Splitting the root is hard: you must decide arbitrarily which part of the root owns each entity.

Why

A structured name is partly a routing instruction. A flat name is not. In the structured case the hierarchy partitions the names. In the flat case the hierarchy can partition only the locations, so every entity must be registered all the way up to the root.

Q14Scenario

The host ftp.elet.polimi.it moves (a) to another machine in the same department, (b) to a different domain, cs.wustl.edu, and keeps its name. What happens in DNS in each case? Why is DNS bad for truly mobile entities?

Model answer

(a) Same domain: no problem. Update the database of the elet.polimi.it name servers. Only that zone changes.

(b) Other domain: keep the name, because users and applications use it. Two options:

  • The elet.polimi.it servers store the new IP address (an A record). Lookups are not affected, but later updates are no longer local: each move needs an update in Milan, so the managerial layer is no longer efficient.
  • The servers store the new name (a CNAME, a symbolic link). Lookups are slower: in practice two distributed lookups. Later updates stay local in wustl.edu. This is like a forwarding pointer.

Mobility: DNS assumes that the global and administrational layers are stable, and that the managerial layer changes often but is used locally. A truly mobile entity changes often and far away. Caches with long TTLs then hold stale addresses (inconsistencies can last days at the global level).

Why

DNS is fast because of caching and replication, and these work only if the data is stable. Mobility breaks that assumption. This is why mobile systems use identifiers plus a separate location service (home-based, hierarchical, DHT).

Q15Describe

Describe DNS in practice: zones, resource records, resolution, caching and replication.

Model answer

  • The name space is a rooted tree (no hard links). Each subtree is a domain, under a separate authority. Each name server is responsible for a zone.
  • Names are case-insensitive, max 255 characters, max 63 per label.
  • Each node has a set of resource records: SOA (zone info), A (IP address of a host), MX (mail server), SRV (server for a service), NS (name server of a zone), CNAME (symbolic link to the primary name), PTR (canonical name, for reverse lookup), HINFO (host info), TXT (any info).
  • Resolution is a mixture of iterative and recursive. Global servers support only iterative mode. Root servers are mirrored (13 root names, over 1,700 instances) and use IP anycast.
  • Caching and replication are used heavily. Secondary servers update from the primary periodically (e.g. twice a day). Each record has a TTL that limits its life in caches. Temporary inconsistencies (days at the global level) are accepted.

Why

DNS trades consistency for availability and speed. A stale address for a few hours is acceptable; a slow or unavailable root would stop the Internet. Note that NS, MX, SRV and CNAME are all symbolic links in the name-space model.

§4

Attribute-based naming

Core idea. You find an entity by its properties, not by its name: "all printers on floor 2 that print in color". Such systems are directory services, usually built on DBMS technology. LDAP combines attributes with a structured name space.

Q16CompareExam 12 Jul 2024

First describe attribute-based naming in general (with LDAP as an example). Then explain why it does not scale as efficiently as structured naming.

Model answer

General. Each entity has a set of attributes that describe its properties. Clients query by the values of some attributes. A query can return many entities. These systems are called directory services and are usually implemented with DBMS technology.

LDAP (derived from X.500) combines structured and attribute-based naming:

  • A directory is a set of entries; each entry is a collection of typed <attribute, value> pairs (single or multi-valued).
  • All entries form the Directory Information Base (DIB). Each entry has a unique name, made of naming attributes (relative distinguished names), e.g. /C=NL/O=Vrije Universiteit/OU=Comp. Sc./CN=Main server. The names form a Directory Information Tree (DIT).
  • For large directories the DIB is partitioned by the DIT, like DNS. Servers are Directory Service Agents (DSA); clients are Directory User Agents (DUA).
  • LDAP adds search: search("&(C=NL)(O=Vrije Universiteit)(OU=*)(CN=Main server)").

Why it scales worse.

  • In structured naming, resolution follows one path. Each component of the name selects one server. The cost is proportional to the depth.
  • An attribute query does not give a path. The matching entries can be in any partition. The system must contact many DSAs, in the worst case all of them. In the example, OU=* forces a search of every organizational unit of the VU.
  • A query returns a set, so the system must collect and merge results from many servers.
  • Matching attribute values needs indexes or exhaustive search. Caching is less effective, because queries vary a lot.

LDAP scales well only when the query fixes the top naming attributes (C, O), which restrict the search to one subtree.

Why

The same idea as the "flat vs structured" question above: structure in the query gives a route. A name is a key with structure. An attribute query is a filter, and a filter can match entries anywhere. In general, "find all X such that…" costs more than "go to X".

§5

Removing unreferenced entities

Core idea. Naming gives global references. When no one refers to an entity any more, the system should remove it. In a distributed system this is hard: no node has global knowledge, and messages can be lost or reordered. Four techniques: reference counting, weighted reference counting, reference listing, distributed mark-and-sweep.

Q17CompareExam 18 Jun 2024 · 25 Feb 2015 · 19 Feb 2013

Describe and compare the various approaches to remove unreferenced entities in a distributed system.

Model answer

Reference counting. The object (in its skeleton) counts how many references exist. Each increment and decrement is a message, so delivery must be exactly-once (acks, duplicate detection). There is a race condition when a process passes a reference to another (next question). The fix needs 3 messages per copy → performance problem at large scale.

Weighted reference counting. Sends only decrements, which removes the race. The skeleton has a total weight and a partial weight. When a reference is copied, its partial weight is split in two, with no message to the skeleton. When a reference is deleted, its partial weight is subtracted from the total. When the total equals the skeleton's own partial weight, no proxy remains → remove. Problem: weights cannot be split forever, so the number of references is limited. An indirection removes the limit but adds one hop to reach the object.

Reference listing. The skeleton keeps the identities of the proxies, not a number. Insert and delete are idempotent, so unreliable communication is fine (repeat until acked). Easier to keep consistent with failures (e.g. ping the clients, which does not scale). Race conditions remain when references are copied. Used by Java RMI: a client creates its proxy only after the server acks the insertion; failures are handled with leases that the client must renew (fixed by the run-time); GC messages use UDP.

Distributed mark-and-sweep (Emerald). Finds entities unreachable from the root set, also cycles. Each site runs a collector; all objects, proxies and skeletons start white. Mark: objects reachable from a local root become grey with their proxies; a grey proxy sends a message to its skeleton, and the object becomes grey; a proxy turns black after the ack. Sweep: each site removes its white objects when all local objects are black or white. It needs a stable reachability graph → a distributed transaction that blocks the system → poor scalability.

Why

Each technique fixes a problem of the previous one. Counting has races, so weighted counting sends only decrements. Counters break with lost or duplicated messages, so listing uses idempotent operations. None of them finds unreachable cycles, so mark-and-sweep traces the graph, at the price of a global stop.

Q18Exercise

With plain reference counting, process P1 has a reference to object O. P1 passes the reference to P2, then deletes its own reference. Show how O can be removed while P2 still uses it. How do you fix it, and what does the fix cost?

Model answer

  1. Count of O = 1 (P1).
  2. P1 sends the reference to P2. P2 must send "increment" to O.
  3. P1 deletes its reference and sends "decrement" to O.
  4. The decrement arrives before P2's increment (different senders, so no ordering). The count becomes 0 and O is removed.
  5. P2's increment arrives too late: P2 has a dangling reference.

Fix: P1 first tells O "increment for P2" and waits for the ack. Only then P1 passes the reference to P2. Now passing a reference needs three messages: increment, ack, and the reference itself.

Why

In a single machine, copying a reference and incrementing the counter is one atomic step. In a distributed system they are separate messages from different processes, and messages from different senders have no order. The race does not exist in non-distributed systems.

Q20Scenario

In Java RMI a client holds a remote reference, then its network is down for 20 minutes. The lease is 10 minutes. What happens? Why does RMI use leases and UDP for garbage collection?

Model answer

The client cannot renew the lease. After 10 minutes the server removes the client from the reference list. If no other client refers to the object, the object can be collected. When the network comes back, the client's reference can be dangling: a call fails with a remote exception.

Leases: the server cannot know if a silent client crashed or is only disconnected (asynchronous system). A lease makes the client responsible for showing that it is alive. With no renewal, the server assumes the reference is gone. This avoids memory leaks from crashed clients. The cost: problems with long failures. The lease duration is set by the run-time and is not negotiable.

UDP: reference listing uses idempotent insert and delete, so a lost or duplicated message is harmless; the client repeats until it gets an ack. TCP connections would add cost for no benefit.

Why

This links naming to the failure model of chapter 02. Crash and slowness look the same in an asynchronous system, so a lease is a timeout that trades safety (an object may be removed too early) for liveness (memory is freed).
