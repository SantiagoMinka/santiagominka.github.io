§1

Big data: the problem and the gas-station example

Core idea. Data science needs large amounts of data. The data has volume, velocity, variety and veracity problems. At scale, reading the input and storing the state become the bottleneck. The solution is to split the work into independent parallel steps that transform immutable data, connected by channels.

Q1Describe

What is data science? List the four "V" consequences of large data availability and explain each one in one sentence.

Model answer

Data science is an interdisciplinary field. It uses scientific methods, processes, algorithms and systems to extract knowledge from structured and unstructured data. Examples: recommender algorithms, genomic data, medicine, transportation, finance.

  • Volume (data at rest): there is a lot of data. In 2008 Google processed 20 PB per day.
  • Velocity (data in motion): data arrives fast. In many domains it loses value as it becomes old, so we must process it as soon as possible.
  • Variety: data comes in many formats, versions and sources.
  • Veracity: data is not always correct.

Why

Volume motivates batch systems like MapReduce. Velocity motivates stream processing. Keep this link in mind: the chapter follows the same order, first volume (MapReduce), then velocity (streams).

Q2Exercise

Which "V" is the main challenge in each case? (a) A bank must block a fraudulent card payment before it completes. (b) A genomics lab stores 2 PB of DNA sequences. (c) A city joins traffic data from GPS traces, CSV files from buses and JSON feeds from taxis. (d) Smart watches send heart rates, but some sensors are badly placed and send wrong values.

Model answer

  1. Velocity. The information is useful only while it is fresh.
  2. Volume. The data does not fit on one disk.
  3. Variety. Different sources and formats must be combined.
  4. Veracity. Some values are not correct.

Why

One application often has more than one V. Ask which property makes a simple single-machine solution fail. In (a) a very fast batch job is still too late; this is the velocity problem.

Q3Describe

What is the problem scope of data processing platforms? Which functions must such a platform provide?

Model answer

Scope: scalability to large data volumes, and support for quickly changing data.

Required functions:

  • Automatic parallelization and distribution.
  • Fault tolerance.
  • Status and monitoring tools.
  • A clean abstraction for programmers.

Why

The programmer must write only the application logic. The platform hides the hard distributed problems. Every system in this chapter (MapReduce, Spark, Flink) is judged on how well it gives these four functions.

Q4Describe

A map is a graph: nodes are points of interest, edges are roads. We want the shortest path from each node to the nearest gas station. Describe the naive solution. Which hidden assumptions does it make? Which assumptions on the scale of the problem and on the computing infrastructure change the picture?

Model answer

Naive solution: run a single-source shortest-path algorithm (for example Dijkstra, O((N + E) log N)) from each gas station. For each node, keep the best distance found so far and update it when a better path appears. Optimization: discard paths longer than a maximum distance (for example 50 km).

Hidden assumptions:

  • We can easily access the entire input data.
  • We can easily store and update the state of the computation (discovered paths, current minimum per node).
  • The state fits in memory, or at least on the disk of one node. Random access to disk then becomes a problem.

Scale assumptions: terabytes or more. The data does not fit on one disk (or it is too slow to read from one disk). It certainly does not fit in memory.

Infrastructure assumptions (a Google datacenter in the early 2000s): a cluster of hundreds to thousands of normal computers, no dedicated hardware. It is cheap and easy to update, but not reliable: hardware failures are common.

Why

Some problems appear only at scale. With one machine, the bottleneck is reading the input and the state. With many machines, the bottleneck moves to coordination and communication. A good solution must reduce both, and it must survive failures.

Q5Exercise

Two gas stations G1 and G2. Phase 1 splits the data into blocks centered on each station and computes distances in each block (in km): block b1 (G1): n1 = 3, n2 = 5, n3 = 9. Block b2 (G2): n2 = 4, n3 = 2, n4 = 6. (a) Show the result of phase 2. (b) How is the data partitioned in each phase, and what can run in parallel? (c) Map this solution to MapReduce.

Model answer

(a) Phase 2 repartitions the data by node and keeps the minimum:

NodeValues receivedResult
n1(G1, 3)G1, 3 km
n2(G1, 5), (G2, 4)G2, 4 km
n3(G1, 9), (G2, 2)G2, 2 km
n4(G2, 6)G2, 6 km

(b) Phase 1: data split by gas station. Each block is processed independently, on a different computer, and nodes read input blocks in parallel. Phase 2: data split by node. Each node is processed independently. Between the phases, communication is necessary: n2 and n3 are in both blocks.

(c) Phase 1 is the map: for each block it emits ⟨node, (station, distance)⟩. The repartition is the shuffle by key = node. Phase 2 is the reduce: for each node it outputs the minimum.

Why

The 50 km assumption makes the blocks small and independent. The only shared information (nodes in several blocks) is solved by a repartition, not by a shared mutable table. This is the full MapReduce idea in one example.

Q6Compare

Compare "global and mutable state" with "transformations of immutable data". Why is the second approach better for a cluster of unreliable machines?

Model answer

Global mutable state: all workers read and update a shared structure (for example the current minimum per node). At scale, it needs random access, locks or coordination, and it is a single point of contention. If a worker fails during an update, the state can become inconsistent.

Transformations of immutable data: each step reads an input that never changes and writes a new output. Steps are independent, so they run in parallel. Data moves between steps through channels.

Why better: no synchronization on shared state, sequential reads, and simple fault tolerance. If a step fails, the platform runs it again on the same immutable input and gets the same output.

Why

Re-execution is safe only if the input did not change. This single property makes fault tolerance in MapReduce (re-run tasks) and in Spark (lineage) possible. Remember it as the root of all the later mechanisms.

Q7Scenario

Data moves between transformations through channels: a distributed file system, messages (for example TCP), or queues (for example Kafka). Pick a channel for each case: (a) a nightly batch job whose intermediate results must survive the crash of any machine; (b) two operators of a streaming job that must exchange data with minimum latency; (c) sensors produce data continuously, and the processing job must be able to replay old data after a failure.

Model answer

  1. Distributed file system. Data is stored durably and replicated. The next step can read it later.
  2. TCP messages. Data flows directly from task to task, with no storage in the middle. This is what Flink does.
  3. Queue (Kafka). It decouples producers and consumers, keeps data durably and lets the consumer read again from an old position.

Why

The trade-off is always durability and decoupling against latency. Case (c) is the "durable input" that Flink needs to replay elements after a snapshot recovery.

§2

The MapReduce programming model

Core idea. The programmer writes two functions. Map processes one input element and emits ⟨key, value⟩ pairs. Reduce receives all the values with the same key, as an iterator, and emits a result. The platform guarantees that all pairs with the same key reach the same reducer.

Q8Exercise

Word count on "All you need is love / All you need is love / All you need is love, love / Love is all you need", split into 4 map tasks (one per line) and 3 reducers by key range (a–h, i–p, q–z). Show the map output, what each reducer receives, and the final result. Words are case-insensitive.

Model answer

Map (each mapper counts locally): lines 1, 2, 4 emit ⟨all,1⟩ ⟨you,1⟩ ⟨need,1⟩ ⟨is,1⟩ ⟨love,1⟩; line 3 emits ⟨all,1⟩ ⟨you,1⟩ ⟨need,1⟩ ⟨is,1⟩ ⟨love,2⟩.

Shuffle (same key → same reducer): a–h gets all; i–p gets is, love, need; q–z gets you.

Reduce (sum the list): ⟨all, [1,1,1,1]⟩ → 4; ⟨is, [1,1,1,1]⟩ → 4; ⟨need, [1,1,1,1]⟩ → 4; ⟨love, [1,1,2,1]⟩ → 5; ⟨you, [1,1,1,1]⟩ → 4.

Why

The pair ⟨love, 2⟩ shows that the mapper counts inside its own block before it emits. This reduces the data sent to reducers. The reducer does not care: it sums the values, whatever they are.

Q9Code

Write the map and reduce functions of word count in pseudocode. What are the input key and value of each function? The slides say that "the map function is stateless". What does it mean, and why is it important?

Model answer

// key: document name, value: document contents
def map(key: String, value: String):
  count = {}
  for w in value:
    if not w in count: count[w] = 1
    else: count[w] = count[w] + 1
  for w in count:
    emit(w, count[w])

// key: a word, values: an iterator over counts
def reduce(key: String, values: Iterator):
  result = 0
  for v in values:
    result += v
  emit(result)

Stateless: the output of map depends only on its own input element (here, its part of the document). It keeps no state between inputs and shares no state with other mappers.

Why important: any map task can run on any machine, in any order, in parallel, and it can be re-executed after a failure with the same result.

Why

The local dictionary count is not "state" in this sense: it lives only during one call and it is rebuilt from the same input on re-execution. The trap is to think that a mapper may keep a counter across blocks: then a re-run would give a different result.

Q10Describe

Reducers receive an immutable list, actually an iterator, over the values of each key. Why an iterator and not a normal list?

Model answer

The iterator ensures that the data is read sequentially, from disk, only once. The list of values for one key can be larger than the memory of the reducer. The platform sorts the intermediate pairs by key and streams them from disk to the reduce function.

Why

Sequential disk reads are fast; random reads are slow. An iterator forbids random access and repeated scans, so the platform can stream any amount of data. The trap: a reduce function that stores all values in a list, or sorts them, can run out of memory on a frequent key.

Q11Code

Inverted index. Input: d1 = "red fish blue fish", d2 = "blue sky", d3 = "red sky red". Output: for each word, the sorted list of documents that contain it. Write map and reduce in pseudocode and show the result.

Model answer

// key: document id, value: document text
def map(docId, text):
  for w in distinct(words(text)):
    emit(w, docId)

// key: a word, values: iterator of document ids
def reduce(word, docIds: Iterator):
  emit(word, sorted(distinct(docIds)))

Map output: d1 → ⟨red,d1⟩ ⟨fish,d1⟩ ⟨blue,d1⟩; d2 → ⟨blue,d2⟩ ⟨sky,d2⟩; d3 → ⟨red,d3⟩ ⟨sky,d3⟩.

Result: blue → [d1, d2]; fish → [d1]; red → [d1, d3]; sky → [d2, d3].

Why

The key of the output is the word, so the word must be the intermediate key. The mapper removes duplicates inside one document ("fish" twice, "red" twice), so it sends less data. The list of documents for a word is usually small enough to sort; for very frequent words a real system relies on the platform's sort by key and value.

Q12Exercise

Average temperature per city. Mapper 1 reads A: 10, 20 and B: 6. Mapper 2 reads A: 30 and B: 2, 4. A student lets each mapper emit the local average, and the reducer averages the averages. (a) Which results does the student get? (b) Which are the correct ones? (c) Write correct map and reduce functions that still aggregate inside the mapper.

Model answer

(a) Student: A = (15 + 30) / 2 = 22.5; B = (6 + 3) / 2 = 4.5.

(b) Correct: A = (10 + 20 + 30) / 3 = 20; B = (6 + 2 + 4) / 3 = 4.

(c) Emit partial sums and counts:

def map(blockId, readings):
  acc = {}                       // city -> (sum, count)
  for (city, t) in readings:
    (s, c) = acc.get(city, (0, 0))
    acc[city] = (s + t, c + 1)
  for city in acc:
    emit(city, acc[city])

def reduce(city, pairs: Iterator):
  s = 0; c = 0
  for (ps, pc) in pairs:
    s += ps; c += pc
  emit(city, s / c)

With the data: A receives (30, 2), (30, 1) → 60 / 3 = 20. B receives (6, 1), (6, 2) → 12 / 3 = 4.

Why

Sum and count can be combined in any order and grouping; the average cannot. A partial result must be "mergeable". The trap: averaging averages gives too much weight to small groups (mapper 2 has only one value of A).

Q13Exercise

Maximum temperature per city. Mapper 1: (Milan,12) (Rome,18) (Milan,15). Mapper 2: (Rome,21) (Turin,9) (Milan,11). Mapper 3: (Turin,14) (Rome,17). There are R = 2 reducers, and the partition function is length(city) mod 2. (a) Write map and reduce. (b) Which reducer gets which city? (c) Show the final output. (d) Is the load balanced?

Model answer

def map(blockId, readings):
  best = {}
  for (city, t) in readings:
    if city not in best or t > best[city]: best[city] = t
  for city in best: emit(city, best[city])

def reduce(city, temps: Iterator):
  m = -infinity
  for t in temps: if t > m: m = t
  emit(city, m)

(b) Milan: 5 mod 2 = 1. Rome: 4 mod 2 = 0. Turin: 5 mod 2 = 1. Reducer 0 gets Rome. Reducer 1 gets Milan and Turin.

(c) Mapper outputs: M1 → (Milan,15) (Rome,18); M2 → (Rome,21) (Turin,9) (Milan,11); M3 → (Turin,14) (Rome,17). Reducer 0: Rome [18, 21, 17] → 21. Reducer 1: Milan [15, 11] → 15; Turin [9, 14] → 14.

(d) Reducer 0 receives 3 values, reducer 1 receives 4 values. With only 3 keys the balance depends on luck; with many keys a hash spreads them evenly.

Why

Max, like sum, is associative and commutative, so the mapper can pre-aggregate safely. The partition function decides only where a key goes, never what the result is.

Q14Code

Join. Users(uid, name) = {(1, Ada), (2, Bob)}. Orders(oid, uid, amount) = {(o1, 1, 30), (o2, 2, 10), (o3, 1, 5)}. Produce (name, oid, amount) for every order. Write a reduce-side join in MapReduce and show what each reduce call receives.

Model answer

def map(source, record):
  if source == "Users":
    (uid, name) = record
    emit(uid, ("U", name))
  else:
    (oid, uid, amount) = record
    emit(uid, ("O", oid, amount))

def reduce(uid, tagged: Iterator):
  names = []; orders = []
  for t in tagged:
    if t[0] == "U": names.append(t[1])
    else: orders.append((t[1], t[2]))
  for n in names:
    for (oid, a) in orders:
      emit(n, oid, a)

reduce(1, [("U",Ada), ("O",o1,30), ("O",o3,5)]) → (Ada, o1, 30), (Ada, o3, 5).

reduce(2, [("U",Bob), ("O",o2,10)]) → (Bob, o2, 10).

Why

The join attribute (uid) must be the intermediate key, so matching records meet in the same reducer. The tag tells the reducer the source of each value, because the order of values in the iterator is not guaranteed. The trap: this reducer stores lists in memory, so a user with millions of orders can be a problem; a real system sorts values so that the "U" record comes first.

Q15Code

A web log contains (user, page) pairs: (u1,p) (u2,p) (u1,p) (u3,q) (u2,q) (u1,p). (a) Count the number of distinct users in the whole log. (b) Count the number of distinct users per page. Write the MapReduce jobs and give the results.

Model answer

(a) Two chained jobs.

// Job 1: remove duplicates
def map1(_, (user, page)):  emit(user, null)
def reduce1(user, _vals):   emit(user)

// Job 2: count
def map2(_, user):          emit("all", 1)
def reduce2(k, ones):       s = 0; for v in ones: s += v; emit(s)

Job 1 gives u1, u2, u3. Job 2 gives 3.

(b) One job, with the page as key:

def map(_, (user, page)):   emit(page, user)
def reduce(page, users):    emit(page, size(distinct(users)))

p receives [u1, u2, u1, u1] → 2. q receives [u3, u2] → 2.

Why

In (a) the grouping key (the user) is not the output key (one global number), so one step is not enough without a single reducer that sees all users. Chaining jobs is the typical MapReduce application: "a sequence of steps, each one a map and a reduce". In (b) a reducer that keeps a set of users can use a lot of memory for a popular page; an alternative is to use (page, user) as key in a first job.

§3

The MapReduce platform: scheduling, locality, fault tolerance

Core idea. The platform does scheduling, data distribution and fault tolerance. One master assigns M map tasks (about 64 MB of input each) and R reduce tasks (key k goes to hash(k) mod R) to free workers. It puts map tasks close to the GFS replicas of their input. It re-runs the tasks of failed workers and launches backup copies of stragglers.

Q16Describe

How does MapReduce schedule tasks, exploit data locality, and tolerate failures and stragglers? What are its strengths and limits?

Model answer

  • Scheduling: one master, many workers. Input split into M map tasks (typically 64 MB); R reduce tasks, partitioned by hash(k) mod R. The master assigns tasks to free workers dynamically. Each mapper writes R local files; each reducer fetches its part from all mappers, sorts, and applies reduce.
  • Locality: GFS stores 3 replicas of each 64 MB block. The master puts a map task on a machine with a replica (or in the same rack), so input is read at local disk speed.
  • Worker failure (detected by heartbeats): re-run its completed and in-progress map tasks (their output is on its local disk); re-run only in-progress reduce tasks (completed output is in the global file system). Reducers are told about re-executed maps. Master failure: state checkpointed to GFS; a new master recovers and continues.
  • Stragglers: near the end, reschedule the remaining tasks as backup copies; take the first copy that finishes.

Strengths: developers write simple functions; the system manages allocation, synchronization, communication, fault tolerance and stragglers; very general; good for large-scale analysis. Limits: high overhead, lower raw performance than HPC, very fixed paradigm: each MapReduce step must complete before the next one starts.

Why

Immutable intermediate data is the key to simple fault tolerance: a lost result can always be recomputed from its input. This idea carries over to Spark's lineage.

Q17Exercise

The input is three files of 200 MB, 100 MB and 30 MB. Splits are 64 MB and a split never crosses a file. R = 4. (a) How many map tasks M? (b) How many intermediate local files are written in total? (c) From how many workers does each reducer read? (d) How many map tasks for 1 TB (1 TB = 1 048 576 MB)?

Model answer

(a) 200 MB → ⌈200/64⌉ = 4 splits (64, 64, 64, 8). 100 MB → 2 splits (64, 36). 30 MB → 1 split. M = 7.

(b) Each map task writes R = 4 local files: 7 × 4 = 28 files.

(c) Each reducer reads its partition from every map task: 7 map outputs (on at most 7 workers).

(d) 1 048 576 / 64 = 16 384 map tasks.

Why

M follows the input size; R is chosen by the user and fixes the number of output files. The shuffle is an M × R exchange: this is why it is the most expensive phase. Many small map tasks also help load balancing and fast recovery: a lost task is short to re-run.

Q19Exercise

All map tasks are finished. W1 ran maps m1, m4 (completed) and reduce r1 (completed). W2 ran maps m2, m5 (completed) and reduce r2 (in progress). W3 ran maps m3, m6 (completed) and reduce r3 (in progress). (a) W2 crashes. Which tasks are re-executed, and why? What happens to r3? (b) Instead, W1 crashes. Which tasks are re-executed? (c) Instead, the master crashes. What happens?

Model answer

(a) The master detects the failure because W2 stops answering heartbeats. It re-executes m2, m5 and r2 on other workers.

  • m2, m5: completed, but their output (R local files) is on W2's local disk, which is now unreachable.
  • r2: in progress, so its work is lost.

r3 continues on W3. The master notifies all reduce workers about the re-execution of m2 and m5, so r3 reads the missing partitions from the new workers.

(b) Re-execute m1, m4 (completed map, output on a local disk). Do not re-execute r1: it is completed, and its output is in the global file system (GFS), which is replicated.

(c) The master state (which tasks are idle, in progress or completed, and where intermediate files are) is checkpointed to GFS. A new master reads the last checkpoint and continues.

Why

The rule depends on where the output is stored, not on the type of task: local disk is lost with the worker, GFS survives it. The common trap is to answer "re-run only the in-progress tasks". Completed map tasks also go back, because the reducers may still need their output.

Exam tip

Say explicitly: "completed map: output on local disk, re-run; completed reduce: output in GFS, keep".

Q20Scenario

GFS block b7 has replicas on N3 (rack 1), N8 (rack 2) and N12 (rack 3). Map task m7 reads b7. The free workers are N5 (rack 1) and N20 (rack 4). (a) Where does the master put m7, and why? (b) What would the master do if N8 were free? (c) What is the goal of this policy?

Model answer

(a) On N5. No free worker has a replica, so the master picks a worker on the same rack (switch) as a replica (N3, rack 1). N5 reads b7 through the rack switch only.

(b) On N8: it has a local replica, so the task reads at local disk speed.

(c) Limit the use of network bandwidth. If thousands of mappers read over the network, the rack switches limit the read rate. With locality, thousands of machines read input in parallel at local disk speed.

Why

The idea is "move the computation to the data, not the data to the computation". Code is small; 64 MB blocks are big. The 3 replicas give the master 3 good choices for each task.

Q21Exercise

A job has 200 map tasks on 20 workers. Each task takes 1 minute on a normal machine. At minute 10, 199 tasks are done. The last task started at minute 9 on a machine with a bad disk that works at 1/10 of the normal speed. (a) When does the map phase end without backup tasks? (b) When does it end if the master starts a backup copy on a normal machine at minute 10? (c) What is the cost of this technique?

Model answer

(a) The task needs 10 minutes on the slow machine: it ends at minute 9 + 10 = 19. No reducer can complete before that.

(b) The backup needs 1 minute: it ends at minute 11. The master takes the first copy that finishes and ignores the other one. The map phase is 8 minutes shorter.

(c) Some redundant work (one extra task here), and the master must track redundant executions. The extra resources are small, because backups start only when most tasks are done.

Why

The job ends when the slowest task ends. A straggler can come from slow hardware, poor partitioning or a bug. The re-execution is safe because map is deterministic and its input is immutable. Note: backups do not help if the cause is poor partitioning (a huge key), because the copy is as slow as the original.

Q22Scenario

You run PageRank with 30 iterations in MapReduce. Each iteration is one MapReduce job. Explain why this is slow, and which limit of MapReduce it shows. What would a more general model change?

Model answer

  • Each job writes its full output to the global file system, and the next job reads it again: 30 writes and 30 reads of the whole graph.
  • Each job must complete before the next one starts, and each one pays the scheduling overhead.
  • The graph structure, which never changes, is read again in every iteration.

Limits shown: high overhead and a very fixed paradigm. A dataflow system (Spark) describes the whole computation as one graph of many stages and caches reused data (the graph structure) in main memory.

Why

A typical MapReduce application is "a series of data transformations, iterating until convergence". MapReduce can express it, but it pays storage and scheduling costs at every step. This is exactly the motivation for the dataflow model.

§4

The dataflow model: scheduling (Spark) vs pipelining (Flink)

Core idea. Generalize MapReduce from two steps to an arbitrary directed acyclic graph of transformations, each one run as many parallel tasks, with one abstraction for batch and streams. Two ways to run it: scheduling of tasks (Spark) decouples stages through storage; pipelining of tasks (Flink) connects always-active tasks directly.

Q23DescribeExam 14 Feb 2024 · 18 Jun 2024 · 6 Sep 2024 (part a)

Describe the key characteristics of the dataflow model for big data processing.

Model answer

  • A job is a graph of operators (transformations such as map, filter, join, group/reduce) connected by data channels: an arbitrary DAG, not only map + reduce.
  • Operators work on immutable data: each one consumes input elements and produces new elements; no global shared mutable state.
  • Data parallelism: each operator is split into many tasks working on partitions of the data; data is repartitioned by key between operators when needed (shuffle).
  • The runtime, not the programmer, handles parallelization, distribution, scheduling, load balancing, communication and fault tolerance.
  • The same abstraction covers batch (static data) and stream processing (continuous data with windows).
  • Channels between operators can be a distributed file system, messages (TCP), or queues (Kafka).

Why

A declarative graph tells the system what can run in parallel and what must be exchanged. That is what lets the system scale to thousands of machines and recover from failures transparently.

Q24CompareExam 14 Feb 2024 · 18 Jun 2024 · 6 Sep 2024 (part b)

Describe the two architectures to implement the dataflow model: scheduling of tasks and pipelining of tasks.

Model answer

Scheduling (Apache Spark). Like MapReduce, but with any number of stages. The job is split into stages; tasks of a stage are scheduled on workers when their input is ready, close to the data. Intermediate results go to storage (memory, cached if reused, or disk).

  • Elasticity: decisions at run time can size stage B on the data produced by stage A.
  • Load balancing: data of stage A can be redistributed across the tasks of B.
  • Fault tolerance: fine-grained, by lineage: re-run only the tasks needed to rebuild the lost intermediate data.
  • Cost: scheduling decisions and storage access add latency: not ideal for low-latency streaming.

Pipelining (Apache Flink). All tasks are deployed when the job starts and stay active; they talk over TCP channels. A task processes data as soon as it arrives, so operators of different stages run at the same time.

  • Low latency: no scheduling overhead, no storage between stages.
  • No elasticity or dynamic load balancing: allocation is fixed at start.
  • Fault tolerance: distributed snapshots (Chandy–Lamport style): sources inject markers; a task that got a marker on one input stops that input until it has markers on all inputs, then saves its state, forwards the marker, resumes. On failure: redeploy the whole graph, restore the last complete snapshot, replay the input after it (needs durable input and state storage).
  • Adaptation: snapshot, stop, restart with different resources, resume: possible but expensive.

Why

Everything follows from one choice: decouple stages through storage (scheduling) or connect them directly (pipelining). Decoupling buys flexibility and cheap recovery; direct connection buys latency.

Exam tip

Structure your answer as a two-column comparison: how tasks are allocated, latency, elasticity, load balancing, fault tolerance, best use (batch vs low-latency streaming).

Q25Scenario

Choose an architecture: (a) a nightly job over 50 TB of logs on a shared cluster whose free resources change; (b) fraud detection on card payments with a 50 ms latency target; (c) an hourly dashboard that tolerates a few seconds of delay but has bursty load.

Model answer

  1. Scheduling. Batch, latency irrelevant; elasticity uses whatever resources are free; lineage recovery is cheap for a long job.
  2. Pipelining. Each payment must be processed in milliseconds; scheduling and storage overhead would break the target.
  3. Scheduling with micro-batches is acceptable (hundreds of ms – seconds of latency) and adapts resources between micro-batches to the bursts.

Why

Decide on two axes: required latency, and how much resources or load change over time.

Q26Scenario

A batch job has stage A (filter, 4 tasks) and stage B (group by customer). After stage A you discover that one customer owns 60% of the data, and that A produced 10 times less data than expected. Which architecture can react, and how? What would the other architecture do?

Model answer

Scheduling (Spark) can react, because the decision for stage B is taken at run time, after A has written its results to storage.

  • Elasticity: A produced little data, so the scheduler gives B fewer tasks and cores.
  • Load balancing: it looks at the distribution of the intermediate results and allocates the data across B1, B2, … so that no task gets far more than the others.

Pipelining (Flink) fixed the number of B tasks and the routing when the job started. The task that gets the big customer becomes a bottleneck, and the extra B tasks stay idle. The only way to change is snapshot, stop, restart with new resources, resume: expensive.

Why

Both advantages come from the decoupling between upstream and downstream stages. In pipelining, B is already running while A produces data, so nobody knows the full output of A when B starts.

Q27Exercise

Spark job: stage 1 has tasks A1–A4 (read a GFS/HDFS file, map). A shuffle by key follows. Stage 2 has tasks B1–B3 (reduce by key). Stage 3 has tasks C1–C3 (map each B partition); B results are cached in memory. Worker W2 holds the shuffle output of A2 and the cached result of B2. W2 fails while C1–C3 run. Which tasks are re-executed? Which are not, and why?

Model answer

The lost data is the cached partition of B2 (needed by C2) and the output of A2.

  1. Follow the lineage of B2: B2 needs its key partition from all A tasks. A1, A3, A4 outputs are still available; A2's output is lost. So re-run A2 (it reads its input block again from the replicated file system).
  2. Re-run B2 with the outputs of A1–A4.
  3. Re-run C2 if it was running on W2 or had not completed.

Not re-executed: A1, A3, A4, B1, B3, and C1, C3 (if they are on other workers). Their data is not lost.

Why

Lineage is the "recipe" of each partition: which input and which transformations produced it. Because data is immutable, the system re-runs only that recipe. Compare with Flink: there, a failure restarts the whole graph from the last snapshot. The trap: forgetting A2. B2 needs one partition from every A task, so the loss of any A output blocks it.

Q29Describe

In the pipelining architecture: (a) what are the steps of recovery after a failure, and which storage do they need? (b) How can the snapshot mechanism give dynamic adaptation for a long-running job, and why is it expensive compared to scheduling?

Model answer

(a) Recovery:

  1. Re-deploy the entire graph of tasks.
  2. Recover the last saved state: the snapshot of the last marker received by all nodes.
  3. Replay all elements that were not part of the snapshot, that is, the elements received after the marker.

It needs durable storage for the input data (to replay it, for example a Kafka queue) and durable storage for the state snapshots.

(b) Adaptation:

  1. Take a global snapshot.
  2. Stop the job.
  3. Restart the job with a different amount of resources.
  4. Resume from the last stored snapshot.

It is expensive because the whole job stops and restarts. A scheduler changes resources at every stage, at run time, with no stop.

Why

In pipelining there is no intermediate storage between stages, so one failed task cannot be recomputed alone: its upstream tasks did not keep their outputs. The whole graph goes back to a consistent cut. This is the price of low latency.

§5

Stream processing: windows, time and watermarks

Core idea. Stream processing reverses batch: a static query runs on dynamic data and outputs new results continuously. Windows (count- or time-based, with a size and a slide) give precise semantics. Event time with watermarks gives a correct order despite network and processing delays. Pipelining runs streams with low latency; micro-batches trade latency for elasticity.

Q30Describe

How does stream processing differ from batch processing? For the job "compute the average temperature in the last hour for each room", which semantic questions are not clear, and what solves them?

Model answer

Batch: static data, on-demand query; the job analyzes the data and produces one output. Stream: static query (job), dynamic data; the job continuously outputs new results as new data arrives.

Unclear points:

  • When should the result be updated?
  • What happens if no value arrives for several minutes?
  • What happens if no value arrives for more than one hour?

Solution: windows. A window isolates the portion of the stream on which the computation runs, and defines when the computation runs. The job becomes "average per room in a sliding time-based window of size 1 hour, slide 5 minutes".

Why

"The last hour" is relative to a moment, and in a stream the moment always moves. The slide fixes the moments; the size fixes the data. Even then a question stays open: which clock measures the hour? This leads to processing time vs event time.

Q31Exercise

Stream: 1 3 1 3 3 5 0 0 0 4. Compute the average (a) in a count-based window of size 4, slide 2; (b) in a tumbling window of size 5. Which one is sliding and which tumbling?

Model answer

(a) Windows [1 3 1 3] → 2; [1 3 3 5] → 3; [3 5 0 0] → 2; [0 0 0 4] → 1. Results: 2, 3, 2, 1. Slide < size: sliding (overlapping) window.

(b) [1 3 1 3 3] → 2.2; [5 0 0 0 4] → 1.8. Slide = size: tumbling window (no overlap).

Why

The slide decides when a result is produced; the size decides how much data each result uses. Count-based windows are "physical" (number of elements); time-based are "logical" (amount of time).

Q32Exercise

Same stream: 1 3 1 3 3 5 0 0 0 4. A window produces a result only when it is full. Compute: (a) sum, count-based, size 3, slide 1; (b) max, count-based, size 3, slide 3; (c) sum, size 2, slide 3. What is special about (c)?

Model answer

(a) [1 3 1] 5; [3 1 3] 7; [1 3 3] 7; [3 3 5] 11; [3 5 0] 8; [5 0 0] 5; [0 0 0] 0; [0 0 4] 4. Results: 5, 7, 7, 11, 8, 5, 0, 4 (8 windows).

(b) Tumbling: [1 3 1] 3; [3 3 5] 5; [0 0 0] 0. Results: 3, 5, 0. The last element (4) waits for two more elements.

(c) Windows start at positions 1, 4, 7: [1 3] 4; [3 3] 6; [0 0] 0. Results: 4, 6, 0. Slide > size: the elements at positions 3, 6 and 9 (values 1, 5, 0) belong to no window. They are never used. The window that starts at position 10 waits for one more element.

Why

Count windows: number of results ≈ (n − size) / slide + 1. With slide = 1 every new element gives a result. The slides define only sliding (slide < size) and tumbling (slide = size). Case (c) is a trap: it samples the stream and loses data, so it is rarely what you want.

Q34Compare

Compare processing time and event time. What is a watermark and how does it propagate in a distributed job?

Model answer

Processing time: the wall clock of the machine that computes. Easy, but out of the application's control: with overload, multiple sources, or distributed processing, the order and grouping depend on queues, network delays and executor speed. A receiver cannot tell how up to date its results are.

Event time: a timestamp attached to each element by the source (or the ingestion system). The application controls the order, but elements can arrive out of order, so the processor must buffer them until it is sure no earlier element will arrive. This can add delay.

Watermark: a contract from a source: "a watermark with time t means no element with time ≤ t will follow". When a processor has a watermark ≥ t from all its inputs, it can safely process all elements with time ≤ t, then forward the watermark downstream.

Why

A watermark plays the role of a token: it separates "complete" from "still incomplete" data, like the marker in Chandy–Lamport. Waiting for all inputs is what makes the result deterministic.

Q35Scenario

Two sensors measure the temperature of the same room. Sensor 1 is on a fast LAN (2 ms delay). Sensor 2 is on a mobile link that sometimes buffers data for 90 s. The job computes a 1-minute tumbling average using processing time. Describe what goes wrong. How does event time fix it, and what does it cost?

Model answer

With processing time: readings of sensor 2 arrive late, so they fall into a later window than the minute in which they were measured. A window can contain readings from two different real minutes, and another window can lack sensor 2 entirely. The result depends on network delays, not on the room. If the processor is overloaded, queues add even more shift, and nobody can tell how up to date a result is.

With event time: each reading carries the time of measurement. The processor puts it in the correct window whatever its arrival time.

Cost: the processor must buffer the window until it is sure that no earlier reading will come (watermark from both sensors). With sensor 2, the result of a minute can be delayed by up to about 90 s.

Why

Processing time is "out of the control of the application": order depends on network delays between sources and system, and on the speed and load of each executor. Event time moves control to the sources, and the price is latency.

Q37Exercise

A job has three sources S1, S2, S3 → operator A (inputs S1, S2) and operator B (input S3) → operator C (inputs A, B). The last watermarks received are: S1 = 40, S2 = 35, S3 = 28. (a) Which watermark do A, B and C forward? (b) C computes 10-second windows covering times 21–30 and 31–40. Which windows can C close? (c) S3 then sends wm(45). What changes?

Model answer

(a) A: min(40, 35) = 35. B: 28. C: min(35, 28) = 28.

(b) Window 21–30 needs a watermark ≥ 30, and window 31–40 needs ≥ 40. With 28 C can close neither.

(c) B forwards 45. C: min(35, 45) = 35. Now C can close window 21–30 (35 ≥ 30), but not 31–40: it waits for S2 (through A) to reach 40.

Why

A watermark propagates only when it holds on all incoming channels. Each operator forwards the minimum of its inputs, so the slowest source in the whole upstream graph limits every downstream window. This is how order is preserved in distributed processing, and it is also the source of the extra delay of event time.

Q38Compare

"Average temperature over a sliding time window of 1 hour, slide 5 minutes": how is it implemented with pipelining, and with micro-batches?

Model answer

Pipelining: operator A is always active and keeps the last hour of readings in its local state; every 5 minutes it emits the new average. Results with no batching or scheduling overhead.

Micro-batch: the system cuts the input into batches that divide both size and slide (e.g. 5 minutes each). A separate job runs per micro-batch; the window state is saved to external storage after each batch and read back at the next one. Latency of hundreds of ms to seconds; resources can change between batches.

Why

Micro-batching turns a stream into many small batch jobs, so it inherits the strengths (elasticity) and weaknesses (latency) of the scheduling architecture.

Q39Exercise

A micro-batch system must run a window of size 10 minutes, slide 4 minutes. Micro-batch lengths are whole minutes. (a) Which lengths are valid? (b) With the longest valid length, how many micro-batches form one window, and after how many micro-batches does a new result appear? (c) Same questions for size 1 hour, slide 5 minutes, with 5-minute batches.

Model answer

(a) The length must divide both 10 and 4: 1 or 2 minutes (divisors of gcd(10, 4) = 2). A 5-minute batch is not valid: 5 does not divide 4.

(b) With 2-minute batches: one window = 10 / 2 = 5 micro-batches; a new result every 4 / 2 = 2 micro-batches.

(c) One window = 60 / 5 = 12 micro-batches; a new result after every micro-batch.

Why

A window must start and end on a batch boundary, otherwise a batch would belong partly to a window. Smaller batches mean lower latency, but more jobs to schedule and more reads and writes of the window state in external storage.

Q40Scenario

Choose a stream implementation (pipelining or micro-batch) and justify: (a) collision alerts for autonomous robots in a warehouse, deadline 20 ms; (b) a social-media trending-topics page refreshed every 10 s, with traffic that grows 20 times during big events; (c) monitoring of a power grid that must react in under 100 ms and runs for months with stable load.

Model answer

  1. Pipelining. 20 ms is far below the hundreds of ms of micro-batches. Data must flow continuously from task to task.
  2. Micro-batch. A latency of seconds is acceptable. Dynamic resource allocation adds resources across micro-batches when the traffic grows.
  3. Pipelining. Low latency is required. The load is stable, so the lack of elasticity is not a problem; a rare change can use snapshot, stop and restart.

Why

The slides summarize it: pipelining is ideal for low-latency jobs; micro-batch suits jobs that tolerate hundreds of milliseconds to seconds and gains dynamic resource allocation. Ask first "what latency?", then "does the load change?".
