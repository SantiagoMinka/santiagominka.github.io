§1

Unstructured systems

Core idea. P2P uses resources at the edges of the network. Every node is client, server and router; nodes come and go; there is no global view. The central problem is retrieval: search (find all items about X) or lookup (find one specific item).

Q1CompareExam 1 Feb 2013 · Margara questions

Compare centralized search, query flooding, hierarchical query flooding and structured topologies in terms of search expressivity and performance. Describe how each system tried to solve the problems of the previous one.

Model answer

Centralized (Napster)Flooding (Gnutella)Super-peers (Kazaa)DHT (Chord)
Join / publishContact server; send file listContact a few neighbors (PING/PONG); no publishContact a super-node; send file list to itBootstrap node; route publication to the key's node
SearchAsk the serverNeighbors, recursively, limited by hops-to-liveFlood among super-nodes onlyRoute by key, O(log N) hops
ExpressivityAny queryAny query (text, fuzzy…)Any queryExact key only
Search scopeO(1)O(N); CD messagesSmaller, no guaranteeO(log N), guaranteed
Weak pointO(N) state at server; single point of failure and of controlTraffic; may miss items; unstableStill no guaranteesFragile; no fuzzy search; ignores physical topology

The journey. Napster's central server was a single point of failure and of legal control → Gnutella removed it with flooding, but flooding wastes bandwidth and scales badly → Kazaa used heterogeneity: powerful nodes become super-nodes and flood only among themselves → BitTorrent attacked free riders with tit-for-tat, and moved search out of band (web, magnet links) → DHTs give guaranteed lookups (BitTorrent's trackerless Mainline DHT is Kademlia-based).

Why

The trade-off is expressivity vs guarantees: unstructured systems can answer any query but cannot promise to find anything; structured systems promise to find a key but cannot search by content.

Q2Exercise

In the simulator's flooding network, peer 3 searches for an item held by peers 0 and 6, with hops-to-live = 3. List the query messages per hop and the replies. How many messages in total?

Model answer

Edges: 0–1, 1–2, 1–3, 3–4, 2–5, 4–6, 2–6, 5–7, 6–7, 0–3.

  • Hop 1: 3 → 1, 3 → 4, 3 → 0 (hit at 0).
  • Hop 2: 1 → 0 (duplicate), 1 → 2, 4 → 6 (hit at 6), 0 → 1 (duplicate).
  • Hop 3 (last): 2 → 5, 2 → 6 (duplicate), 6 → 2 (duplicate), 6 → 7.

11 query messages. Replies follow the reverse path: 0 → 3 and 6 → 4 → 3. The requester then downloads directly from 0 or 6. Open the simulator's flooding tab to check.

Why

Peers drop queries they have already seen (same id), but the duplicate messages are still sent: that waste is the price of flooding. Peers beyond the hops-to-live are never asked, even if they hold the item.

Q3DescribeExam 5 Sep 2013

Define a "pure" P2P system. Among Napster, Gnutella, Kazaa, the eDonkey network and BitTorrent, which are pure, and why not the others?

Model answer

In a pure P2P system all nodes have the same role and there is no central component: any node can leave without breaking the system.

  • Napster: not pure: the central index server is needed for search (peers still serve files).
  • Gnutella (original): pure: all peers are equal; flooding.
  • Kazaa: hybrid: super-nodes have a special role.
  • eDonkey: hybrid: servers index files (the later Kad network is a DHT, so closer to pure).
  • BitTorrent: not pure with a tracker (central for each torrent); trackerless with a DHT is closer to pure, but search is still out of band.

Why

Pure systems pay for the missing center with inefficient search or complex structure. Most successful systems are hybrid: they keep a small central part where it helps most.

Q4Describe

How does BitTorrent distribute content and fight free riders? Explain fragments, rarest-first, choking and the optimistic unchoke.

Model answer

  • Join: contact the tracker, get a list of peers. Search is out of band (.torrent file or magnet link). A torrent has file names, sizes, block checksums, tracker address.
  • Files are split into fragments (~256 KB) with hashes for integrity. Peers download missing fragments from each other in any order, and upload what they have.
  • Rarest-first: request the fragment held by the fewest peers, to keep many sources for each fragment.
  • Seeds have the whole file; leeches are still downloading; the swarm is all of them. Everyone can finish as long as one distributed copy exists.
  • Choking: a temporary refusal to upload. Every 10 s a peer unchokes a fixed number of peers, chosen by their download rate to it (rolling 20 s average): tit-for-tat.
  • Optimistic unchoke: one extra peer, rotated every 30 s, gets uploads regardless. It lets newcomers start and discovers better partners.

Why

Incentives replace trust: the more you upload to me, the more I upload to you. Earlier credit systems (eMule, Kazaa) were easy to cheat with modified clients; tit-for-tat needs no global accounting. It approximates Pareto efficiency.

Q5CompareExam 3 Dec 2014

Describe the routing of Freenet and of Chord (with finger tables), and compare them.

Model answer

Freenet: goals are anonymity and censorship resistance. A request for a file id goes to the neighbor that is the "best guess" (closest known id): steepest-ascent hill climbing with backtracking, limited by hops-to-live. The file returns along the same chain and every node caches it (LRU). Inserts follow the same route, so data is placed where requests will look. Similar ids cluster on the same nodes; the network becomes a small world; popular files spread, unpopular ones may disappear. Link and document encryption, content-hash ids.

Chord: ring of m-bit ids; a key is stored at its successor; each node has m fingers (succ(n + 2i)); each hop halves the distance: O(log N) hops, O(log N) state; join costs O(log² N); successor lists and stabilization handle churn.

FreenetChord
GuaranteeNone (may not find)Always finds the key
Routing stateLearned, approximateStructured, exact
Caching / replicationAlong request paths, popularity-drivenNot built in (successor list)
AnonymityYes, by designNo

Why

Both route "towards closer ids", but Freenet learns its routing tables from traffic, while Chord builds them from a mathematical structure. Learning gives adaptivity and anonymity; structure gives guarantees.

§2

Structured systems: DHTs and Chord

Core idea. A DHT offers put(id, item) and get(id) on a structured overlay. In Chord the key k lives at succ(k); finger i of node n is succ(n + 2i); a lookup forwards to the finger whose interval contains k.

Q6ExerciseMargara, exercise 3

Three peers (0, 1, 4), 3 bits. (a) Show the routing tables. (b) Peer 4 looks up key 1. (c) Peer 0 looks up key 6. (d) Peer 0 looks up key 3.

Storage: node 0 holds (4, 0] = {5, 6, 7, 0}; node 1 holds {1}; node 4 holds {2, 3, 4}.

(b) Key 1 at node 1. Node 4: 1 is in [0, 4) → node 0. Node 0: 1 is in [1, 2) → node 1. Path 4 → 0 → 1.

(c) Key 6 is stored at node 0 itself: no message.

(d) Key 3 at node 4. Node 0: 3 is in [2, 4) → node 4. Path 0 → 4.

Why

Case (c) is the trap: always first check whether the asking node stores the key. Intervals make wrap-around explicit: [5, 1) at node 1 means 5, 6, 7, 0.

Q7Describe

How does a node join Chord, and how does Chord handle concurrent joins and failures? Give the costs.

Model answer

  • Each node also keeps its predecessor.
  • Join of n: n knows some node n′. (1) Initialize n's predecessor and fingers through n′ (finger i = successor of n + 2i). (2) Update other nodes: n becomes finger i of p iff p precedes n by at least 2i and the current finger i of p succeeds n; the first such p is the predecessor of n − 2i. One lookup per finger: log N × log N = O(log² N). Keys in (pred(n), n] move to n.
  • Stabilization: concurrent joins/leaves can break successor pointers, so each node periodically re-looks up the successor of n + 2i for each finger.
  • Failures: each node keeps a list of its first R successors; if the successor does not answer, try the next. Survives R − 1 simultaneous failures.

Table size O(log N); lookup O(log N) hops; join O(log² N).

Why

Correctness depends only on successor pointers: with correct successors a lookup always succeeds, maybe slowly. Fingers are only shortcuts, so they can be repaired lazily.
