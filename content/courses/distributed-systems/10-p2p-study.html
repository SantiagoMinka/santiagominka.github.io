§1

What P2P is: paradigm, characteristics, overlays, retrieval

Core idea. P2P takes advantage of resources at the edges of the network. Every node is a client, a server and a router. Nodes are independent, dynamic and heterogeneous, and nobody has a global view. The peers form an overlay network on top of the physical network. The central problem of the chapter is retrieval: search for something, or look up a specific item.

Q1Compare

Compare the client-server paradigm and the P2P paradigm. What changed in the Internet to make P2P possible? Which resources can peers share? Where does P2P live today?

Model answer

Client-serverP2P
ParadigmA client requests data or a service; a server satisfies the request.Peers share resources and services by direct exchange.
ExamplesWeb, mail, web servicesBitTorrent, Freenet, Folding@Home
ProblemsHard to scale (clouds and CDNs add cost and complexity); single point of failure; needs administration; leaves resources at the edges unused.No global view; nodes come and go; retrieval is difficult.

What changed: end-host resources increased dramatically, and broadband connectivity became common.

Shared resources: network bandwidth (ad hoc networking, Internet), processing cycles (Folding@Home), storage space (Freenet), data (most of the other systems).

P2P today: file distribution (BitTorrent), content-addressed storage (IPFS), blockchains (peer discovery and replicated data), browser-to-browser communication (WebRTC), anonymity (Tor, Freenet/Hyphanet). File sharing declined because of streaming platforms, but BitTorrent still dominates upload traffic.

Why

The key sentence is "take advantage of resources at the edges of the network". Each client-server problem is the reverse of a P2P advantage: more users bring more resources, and there is no single machine to fail or to administer. Remember also the price: without a center, finding things becomes the hard problem.

Q2Describe

List the characteristics of a P2P system. Then explain what an overlay network is. Two peers are neighbors in the overlay. Are they also close in the physical network?

Model answer

  • All nodes are potential users and potential providers of a service. Nodes act as servers, clients and routers (ad hoc communication).
  • Each node is independent: no central administration is necessary.
  • Nodes are dynamic: they come and go unpredictably.
  • The capabilities of nodes are highly variable.
  • The scale can be Internet-wide: there is no global view, and resources are geographically distributed.

An overlay network is a logical network built on top of the physical network. Its links are virtual links: one virtual link is a transport connection that can cross many routers and physical links.

Overlay neighbors are not necessarily close physically. A peer in Milan can have an overlay neighbor in Tokyo. One overlay hop can cost hundreds of milliseconds.

Why

Every P2P protocol in this chapter (flooding, super-nodes, Freenet, Chord) defines who the neighbors are in the overlay. The overlay ignores the physical topology unless the protocol takes care of it. This is why "it does not consider physical topology" is a con of Chord, and why Kazaa was rumored to consider network locality.

Q3Scenario

For each request, say if it is a search or a lookup, and if the system should return the data or a reference to it: (a) "all documents about distributed systems"; (b) "a copy of RFC 3268"; (c) "the 4 GB file with hash h"; (d) "the IP address of the host that stores the document with key k".

Model answer

  1. Search: it can match many items. Return references: returning the data is meaningless for a search, because it returns multiple items.
  2. Lookup of one specific item. Data or reference are both possible. A short document can come back as data.
  3. Lookup. Return a reference: 4 GB routed through the overlay is a burden for every intermediate peer. The requester then fetches the file directly.
  4. Lookup. The value is small, so the system returns it as data. Note: the value itself is a reference to the host.

Why

Search asks "which items match this description?". Lookup asks "where is this exact item?". The answer to a search is a list, so it must be references. For a lookup, the choice depends on the size: query results that travel through the overlay load every peer on the path.

Q4DescribeExam 9 Sep 2015

Describe the evolution of distributed systems, from client-server interactions to hybrid implementations (partly client-server, partly P2P), to full P2P implementations.

Model answer

  1. Client-server. Web, mail. Simple, but hard to scale, a single point of failure, needs administration, and leaves edge resources unused.
  2. Hybrid. A central part keeps the hard function, the peers do the heavy work. Napster: a central server indexes the files, the peers transfer the files directly. Kazaa: super-nodes index and search, normal nodes only publish and fetch. BitTorrent: a tracker lists the peers of a torrent, the peers exchange fragments.
  3. Full P2P. All nodes have the same role. Gnutella floods queries. Freenet routes queries by "best guess". DHTs such as Chord route on a structured overlay with guaranteed lookup. Trackerless BitTorrent uses the Mainline DHT.

The driving forces: the server is a single point of failure and of "control" (Napster was shut down); flooding does not scale; free riders must get an incentive to contribute.

Why

Hybrid systems keep a small central part exactly where it helps most: search or coordination. Full P2P removes it, and pays with either a lot of traffic (flooding) or a structure that must be maintained (DHT). Structure your answer as a sequence of problems and solutions.

§2

Unstructured retrieval: Napster, Gnutella, Kazaa

Core idea. Describe each system with the same four operations: join, publish, search, fetch. Napster centralizes search on a server (O(1) scope, O(N) state). Gnutella floods queries to neighbors with a hops-to-live limit (up to CD messages, O(N) scope, O(2D) time). Kazaa floods only among super-nodes. In all three, the fetch is direct between peers.

Q5Describe

Describe Napster with join, publish, search and fetch. Give its pros and cons, its search scope and the state at the server.

Model answer

Napster was the first P2P file-sharing application (free music). Key idea: share the storage and bandwidth of home users.

  • Join: the client contacts the central server.
  • Publish: the client sends the list of its files to the server.
  • Search: the client asks the server who owns the requested file.
  • Fetch: the client gets the file directly from the peer.

Pros: simple; search scope is O(1) (one query to the server).

Cons: the server keeps O(N) state; the server does all the search processing; single point of failure; single point of "control" (legal attacks).

Why

Napster is P2P only for the transfer. The search is client-server. This gives perfect search (any query, one hop), but it puts all the state and all the risk on one machine. The legal "control" problem is what killed Napster, and it motivated the decentralized successors.

Q6DescribeExam 5 Sep 2013

Define a "pure" P2P system. Among Napster, Gnutella, Kazaa, the eDonkey network and BitTorrent, which are pure, and why not the others?

Model answer

In a pure P2P system all nodes have the same role and there is no central component: any node can leave without breaking the system.

  • Napster: not pure. It depends on the availability of the central index server. Many researchers said it is not P2P at all. Still, all peers are active providers, not only consumers.
  • Gnutella (original): pure. All peers are equal and search by flooding.
  • Kazaa: hybrid. Super-nodes have a special role.
  • eDonkey: hybrid. Servers index the files. Its later Kad network is a DHT, so it is closer to pure.
  • BitTorrent: not pure with a tracker, which is central for each torrent. Trackerless BitTorrent with the Mainline DHT is closer to pure, but search is still out of band (web, magnet links).

Why

Ask one test question for each system: "if this special node disappears, does the system still work?". Pure systems pay for the missing center with inefficient search or with complex structure. Most successful systems are hybrid.

Q7Describe

Describe Gnutella: how a node joins the network, how a query propagates, and what limits it. Give the pros and cons with their costs.

Model answer

  • Join: there is no central authority, so the new node connects to a well-known anchor node. It sends a PING; the PING is forwarded to other nodes. Hosts that offer new connections answer with a PONG. The new node then opens direct connections to the discovered nodes: they become its neighbors.
  • Publish: no need. Files stay where they are.
  • Search: flooding. The node asks its neighbors, they ask their neighbors, and so on. A HopsToLive field limits the propagation: each hop decrements it, and at zero the query stops. A node that sees the same query again drops it. When a node has the file, it replies to the sender (back along the query path).
  • Fetch: directly from the peer.

Pros: fully decentralized; search cost distributed; any kind of query ("search for S" can be a database query, simple text matching, fuzzy matching…).

Cons: a "flood" of requests: with C neighbors on average and hops-to-live D, each search can cause CD messages; search scope O(N); search time O(2D) (D hops out, D hops back); nodes leave often, so the network is unstable.

Why

Flooding needs no structure, so churn cannot break it and any query works. But the traffic grows exponentially with D, and hops-to-live cuts the scope: an item outside the horizon is never found, even if it exists. This is the opposite trade-off of a DHT.

Q8Exercise

(Margara, exercise 1, on the simulator's network.) Edges: 0–1, 1–2, 1–3, 3–4, 2–5, 4–6, 2–6, 5–7, 6–7, 0–3. Node 3 searches for item A, stored at nodes 0 and 6. Peers use query flooding with hops-to-live = 3. List the query messages hop by hop, the replies, and the total number of query messages.

Model answer

Rule: a node forwards a new query to all its neighbors except the one it received it from. It drops a query it has already seen.

  • Hop 1: 3 → 1, 3 → 4, 3 → 0 (hit at 0).
  • Hop 2: 1 → 0 (duplicate), 1 → 2, 4 → 6 (hit at 6), 0 → 1 (duplicate).
  • Hop 3 (last): 2 → 5, 2 → 6 (duplicate), 6 → 2 (duplicate), 6 → 7.

Total: 11 query messages. Nodes 5 and 7 receive the query at hop 3 and do not forward it (hops-to-live is used up).

Replies follow the reverse path: 0 → 3 and 6 → 4 → 3. Node 3 then downloads A directly from 0 or from 6.

Why

Duplicates are dropped, but they are still sent: this waste is the price of flooding on a graph with cycles. A node that has the item still forwards the query, because the requester may want all copies (it is a search, not a lookup).

Exam tip

The figure in Margara's slides is a different graph. Its official solution lists the search messages 3 → 4, 3 → 1, 1 → 0, 1 → 2, 2 → 5 and the reply 0 → 1 → 3 (or directly 0 → 3). Whatever the graph, write the messages hop by hop, mark hits and duplicates, and stop at hops-to-live.

Q9Exercise

Overlay edges: A–B, A–C, A–D, B–E, C–E, C–F, D–G, F–H, G–H, E–H. (a) D searches for an item stored only at E, hops-to-live = 3. List the messages per hop and count them. Which path does the reply follow? (b) A searches for an item stored only at H, hops-to-live = 2. Is it found? How many messages? What is the minimum hops-to-live to find it?

Model answer

(a)

  • Hop 1: D → A, D → G.
  • Hop 2: A → B, A → C, G → H.
  • Hop 3 (last): B → E (hit), C → E (duplicate), C → F, H → E (duplicate), H → F (duplicate: F gets two copies in the same hop).

Total: 10 messages. E receives three copies in hop 3. It answers once, along the path of the copy it accepts first. All three paths have 3 hops: E → B → A → D, or E → C → A → D, or E → H → G → D.

(b) Hop 1: A → B, A → C, A → D. Hop 2: B → E, C → E (duplicate), C → F, D → G. Total 7 messages. H is not found: H is 3 hops away from A, and the query dies after 2 hops. The minimum hops-to-live is 3.

Why

Part (b) shows the main weakness of flooding: no guarantee. The item exists, but it is outside the horizon of the query. Increasing hops-to-live finds it, but each extra hop multiplies the traffic.

Q10Exercise

In a Gnutella network, each peer has C = 4 neighbors on average. (a) How many query messages can one search cause with hops-to-live D = 7? And with D = 4? (b) The network receives 100 searches per second. How many messages per second with D = 7? (c) One overlay hop takes 50 ms. What is the worst-case search time with D = 7?

Model answer

  1. With the slide formula CD: 47 = 16,384 messages. With D = 4: 44 = 256 messages, but the search reaches far fewer peers.
  2. 100 × 16,384 = 1,638,400 messages per second, only for queries.
  3. Search time is O(2D): the query travels up to D hops, the reply travels D hops back. 2 × 7 × 50 ms = 700 ms.

Why

CD is an order of magnitude, not an exact count. Real counts are lower, because nodes do not send back to the sender and cycles cause duplicates. In exercise 1 the graph has 8 nodes and 10 edges: average degree 2.5, 2.53 ≈ 15.6, and the real count was 11. The important point is the exponential growth with D: reducing D saves traffic but shrinks the scope.

Q11Describe

Describe Kazaa's hierarchical topology with join, publish, search and fetch. Which problem of Gnutella does it address, and which problem remains?

Model answer

Kazaa distinguishes normal nodes and super-nodes.

  • Join: the client contacts a super-node. It may become a super-node itself later.
  • Publish: the client sends its list of files to its super-node.
  • Search: the client sends the query to its super-node. Super-nodes flood the query among themselves.
  • Fetch: directly from the peer(s). A client can fetch from multiple peers simultaneously.

Pros: it considers node heterogeneity: bandwidth, computational resources, availability. Kazaa was rumored to consider network locality too. Flooding involves only the super-nodes, so it costs less and each super-node answers for many normal nodes.

Cons: still no real guarantees on search scope or search time.

Why

Kazaa is a mix of Napster and Gnutella: each super-node is a small Napster server for its normal nodes, and super-nodes form a Gnutella network. Flooding is still flooding, only on a smaller and more stable set of nodes.

Q12Scenario

A Kazaa-like system must promote two of these peers to super-nodes. P1: home desktop, 100 Mbit/s, on 24 h a day, 8 cores. P2: smartphone on 4G, sessions of 20 minutes. P3: laptop, 50 Mbit/s, on 2 h a day. P4: university server, 1 Gbit/s, always on, 32 cores. P5: old home PC, 5 Mbit/s, on 10 h a day. Which two do you choose, and why not the others?

Model answer

Choose P4 and P1. They have the best bandwidth, computational resources and availability: the three criteria of the slides.

  • P2: very short sessions and limited resources. Each departure forces its normal nodes to join another super-node and to publish their file lists again.
  • P3: good bandwidth, but it is on only 2 h a day: low availability.
  • P5: low bandwidth and an old CPU. Super-nodes receive the queries of all their normal nodes and flood queries among super-nodes.

Why

A super-node holds the index of its normal nodes and carries search traffic. If it leaves, this state is lost and must be rebuilt. So availability matters as much as bandwidth: a fast node that leaves often is a bad super-node.

§3

Free riders and BitTorrent

Core idea. Free riders download without contributing. BitTorrent makes contribution pay: peers swap fragments of a file, and each peer uploads to the peers that upload most to it (tit-for-tat, through choking). One optimistic unchoke lets newcomers start and discovers better partners. Search stays out of band: a .torrent file or a magnet link, with a tracker or the Mainline DHT.

Q13Describe

What is a free rider? Describe the first attempts to stop free riders in Napster, Direct Connect, eMule and Kazaa, and explain why they did not work well.

Model answer

A free rider only downloads and does not contribute to the network.

  • Napster: user-based: "I refuse to upload if you do not share anything worth it". It depends on each user's decision.
  • Direct Connect: you must share something to join. But there is no guarantee that you share something valuable.
  • eMule / Kazaa: credit systems control the priority of clients. They proved easy to circumvent with unofficial clients that fake their credits.

Why

All these solutions trust information that the client controls: what it says it shares, or the credits it reports. A modified client can lie. BitTorrent's tit-for-tat uses only what each peer measures by itself: the rate at which it receives data. You cannot fake bytes you never sent.

Q14Describe

Describe BitTorrent: join, publish, search, fetch; the terms torrent, seed, leech, swarm and tracker; how fragments are distributed and verified.

Model answer

  • Join: contact the centralized tracker, get a list of peers. Publish: run a tracker. Search: out of band: find a .torrent file or a magnet link on the Web. Fetch: download chunks from your peers, and upload the chunks you have to them.
  • Torrent: metadata file. It contains the names and sizes of the files, the checksum of every block, the address of the tracker (and of peers).
  • Seed: a peer with the complete file that still offers it for upload. Leech: a peer with an incomplete download. Swarm: all seeds and leeches of a torrent. Tracker: a server that tracks seeds and peers in the swarm and gathers statistics. A new peer asks it for a list of peers.
  • The file is split into fragments (usually 256 KB). The .torrent holds the SHA hash of each fragment, so a peer verifies the integrity of each fragment it receives.
  • Fragments are not downloaded in order; the receiver assembles them. Clients upload the fragments they have before the download ends. When a peer finishes, it should stay and become an extra seed.

Each new downloader uses bandwidth, but also gives bandwidth back to the swarm. So many people can download the same file without slowing down each other. BitTorrent is still the dominant P2P file-sharing protocol (since 2007).

Why

Fragments turn one big transfer into many small independent transfers. A leech can upload after its first fragment, so capacity grows with the number of downloaders. Per-fragment hashes make it safe to accept data from untrusted peers: a bad fragment is detected and downloaded again.

A file has 6 fragments. Peer P has fragments {1, 2}. Its neighbors have: A {1, 2, 3, 4}, B {1, 3, 5}, C {1, 2, 3, 6}, D {3, 4, 5}. With rarest-first, which fragment does P request first, and from whom? In which order does it continue? Why is this policy useful?

P requests fragment 6 from C first. Then 4 and 5 (tie, 2 holders each), and fragment 3 last.

Rarest-first keeps the number of sources for each fragment as high as possible and spreads the load. If C leaves before anyone copies fragment 6, nobody in this neighborhood can complete the file.

Why

Common fragments can wait: many peers can give them later. Rare fragments are at risk, and they are also the most valuable for trading: once P has fragment 6, A, B and D want it from P. The trap: do not pick the fragment that is easiest to get (fragment 3).

Q17Exercise

A file has 6 fragments. The only seed leaves the swarm. The remaining leeches have: L1 {1, 2, 3}, L2 {2, 4, 5}, L3 {1, 4}. (a) Can any leech complete the file? (b) Same question if L3 has {1, 6}. (c) Which slide principle does this show?

Model answer

  1. The union of the fragments is {1, 2, 3, 4, 5}. Fragment 6 is missing: nobody can complete the file until a seed comes back.
  2. The union is {1, 2, 3, 4, 5, 6}: all leeches can eventually complete the file by exchanging fragments.
  3. Everyone can get the complete file as long as there is "one distributed copy" of the file in the network, even with no seed.

Why

No single peer needs the whole file: the swarm as a whole is the "server". This is why rarest-first matters: it spreads rare fragments before their only holder leaves, so the distributed copy survives departures.

Q18Describe

Give the pros and cons of BitTorrent. How does BitTorrent work without a tracker?

Model answer

Pros: works reasonably well in practice; gives peers an incentive to share resources; avoids free riders.

Cons: Pareto efficiency is a relatively weak condition; search is performed out of band; the tracker is a central server.

Trackerless BitTorrent: a magnet link carries only the hash of the torrent. Peers use a P2P network, the Mainline DHT, to find the peers for that hash. The Mainline DHT is based on Kademlia. It is the largest structured P2P network in the world: on the order of 10 million or more nodes per day.

Why

The DHT replaces only the tracker: it answers the lookup "who has the torrent with this hash?". It does not replace keyword search, because a DHT supports only exact keys. So users still find magnet links on the Web.

§4

Freenet: secure, anonymous storage

Core idea. Freenet (now Hyphanet) lets anybody publish and read information with reasonable anonymity. A request goes to the neighbor that is the best guess for the file id (steepest-ascent hill climbing with backtracking), limited by hops-to-live. The file returns along the same chain, and each node caches it (LRU). Inserts follow the same route, so data is where requests look for it.

Q19Describe

What are the goals of Freenet? Describe join, publish, search and fetch, and the routing protocol.

Model answer

Goals: practical one-to-many publishing; reasonable anonymity for producers and consumers; no centralized control or administration; scalable from tens to hundreds of thousands of users; robust against node failures and malicious attacks.

  • Join: contact a few known nodes; get a unique node id.
  • Publish: route the file contents toward the node that stores other files with the closest ids.
  • Search: route the query for the file id with steepest-ascent hill climbing and backtracking.
  • Fetch: when the query reaches a node that has the file, that node returns the file to the sender.

Routing: each node stores some information locally and has approximate knowledge of what its neighbors store. If it does not have the information, it forwards the request to its "best guess" neighbor. If that path fails, it backtracks and tries the next best neighbor. If the information is found within the request's hops-to-live, it goes back through the chain of nodes to the requester. Intermediate nodes store it in their LRU cache.

Why

Freenet is between flooding and a DHT. Like a DHT it routes toward "closer" ids, so only the nodes on one path work (no flooding). Unlike a DHT, its routing tables are learned and approximate, so there is no guarantee. Returning data along the chain is what hides the origin and what spreads copies.

Q20Exercise

Slide example. Routing tables: A has key 8 → B. B has 7 → C and 10 → D. D has 8 → E. C has nothing useful. E owns a copy of file 8. Closeness is numeric distance between keys. (a) A requests file 8. List the messages. (b) What changes in caches and routing tables? (c) Afterwards, A inserts a new file with key 9 with hops-to-live 3. Where does the file go?

Model answer

(a)

  1. A → B: "8?" (A's only entry for 8 points to B).
  2. B → C: "8?" (best guess: key 7 is at distance 1, key 10 at distance 2).
  3. C → B: "No, sorry" (dead end).
  4. B → D: "8?" (backtracking: next best guess, key 10).
  5. D → E: "8?" (D's entry 8 → E).
  6. E → D: "8!" (file 8).
  7. D → B: "8!".
  8. B → A: "8!".

8 messages.

(b) D, B and A store file 8 in their LRU caches. Each node adds a routing entry that associates key 8 with the data source; for anonymity this source can be decided at random (for example, B can point 8 to D, or claim to be the source itself). The next request for 8 that reaches B is answered by B directly.

(c) The insert is routed like a request for 9. A → B (A's closest key is 8). At B, keys 8 and 10 are both at distance 1 and both point to D: B → D. At D, the closest key is 8: D → E. Hops-to-live is used up and id 9 was not found, so the data is sent along the same path: B, D and E store file 9.

Why

Backtracking is what makes Freenet "steepest ascent with backtracking": a dead end is not a failure, the previous node tries its next best guess. Part (c) shows why close ids cluster on the same nodes: a request for 9 will follow the same path A → B → D and meet the file. Part (b) shows why data migrates toward the interested parties.

Q22Describe

Explain the routing properties of Freenet (clustering, small world), its anonymity and security mechanisms, and its pros and cons.

Model answer

  • Clustering: close file ids tend to be stored on the same node, because publications of similar ids route toward the same place.
  • Small world: most nodes have few local connections, but a few nodes have many neighbors. Well-known nodes see more requests and become even better connected. So most queries traverse only a few hops.
  • Anonymity: messages are forwarded back and forth, so a node cannot tell where a message originated.
  • Censorship resistance: two file ids must not collide, otherwise an attacker could create a denial of service. Solution: robust hashing, so the id of a file is directly related to its content.
  • Link-level encryption: prevents snooping of messages. Messages are quantized to hinder traffic analysis (still possible, but a huge task).
  • Document encryption: node operators do not know what data they cache.
  • Document verification: documents can be authenticated; secure date-based publishing (the sender publishes a new version).

Pros: intelligent routing makes queries short; small search scope (only nodes on the path, no flooding); anonymity can give "plausible deniability". Cons: still no provable guarantees; anonymity makes the system hard to measure and debug.

Why

Each mechanism protects one party: link encryption protects the messages, document encryption protects the node operator (it cannot know what it stores), content-hash ids protect the publisher against fake files with the same id. The same features that protect users also hide the system from its developers.

§5

DHTs and Chord: ring, finger tables, lookup

Core idea. A DHT offers put(id, item) and item = get(id) on a structured overlay. In Chord, node ids and keys are m-bit numbers on a ring; key k is stored at its successor, the first node with id ≥ k (with wrap-around). Row i of the finger table of node n has start = n + 2i mod 2m, the interval [starti, starti+1) (the last interval ends at n), and succ = successor(start). Routing rule: if k is in (predecessor, n], node n stores k; otherwise it forwards to the succ of the row whose interval contains k.

Q23Describe

Describe the DHT abstraction and the four operations join, publish, search and fetch on a structured overlay.

Model answer

A DHT is a distributed hash table: put(id, item) and item = get(id). The item can be any resource, for example a reference to a file. Each node holds a part of the table.

  • Join: contact a "bootstrap" node and integrate into the distributed data structure; get a node id.
  • Publish: route the publication for file id toward a close node id along the data structure.
  • Search: route a query for file id toward a close node id. The data structure guarantees that the query meets the publication.
  • Fetch: if the publication contains the file, fetch it from where the query stops. If it contains a reference, fetch from the location in the reference.

Why

Publish and search use the same deterministic function of the id, so they always end at the same node. That is the guarantee that flooding and Freenet do not have. The price: you must know the exact id, so only lookup is possible, not search.

Q24DescribeExam 27 Jun 2013

Briefly illustrate the Chord algorithm. Explain the routing table size and the routing and joining time complexity. Explain why it is better than the algorithms historically used in P2P systems (Gnutella, Kazaa). Give numbers for N ≈ 106 nodes.

Model answer

  • Nodes and keys are on a logical ring of m-bit ids. A node id is usually the hash of its IP address; a key is usually the hash of the item. The item with key k is stored at the successor of k.
  • Basic lookup: each node knows its successor; search goes linearly around the ring: O(N).
  • Finger table: m entries; entry i of node n is the first node with id ≥ n + 2i. The i-th finger points 1/2m−i of the way around the ring.
  • Routing: if the node does not store k, it forwards to the finger responsible for the interval that contains k.

Table size: log N fingers. Routing time: each hop halves the distance to the target: O(log N) hops. Joining: O(log² N) messages with high probability.

Numbers for N ≈ 106 ≈ 220: about 20 distinct fingers; at most about 20 hops per lookup; about 202 = 400 messages per join. Gnutella with C = 4 and D = 7: up to 47 = 16,384 messages per search, with no guarantee of success.

Why better: lookup is guaranteed (if the key exists, it is found); traffic per lookup is O(log N), not exponential; state per node is small, O(log N), not O(N) at a server; there is no special node (no super-node, no server).

Why

The halving argument is the heart of Chord: the fingers sit at distances 1, 2, 4, …, 2m−1, so the best finger always covers at least half of the remaining distance. Do not forget the honest limits in the comparison: exact-match only, more fragile under churn, and no physical locality.

§6

Chord under churn, other DHTs, and comparisons

Core idea. When node n joins, it takes the keys in (predecessor(n), n] from its successor, and some fingers of other nodes must point to n. Join costs O(log² N). Correctness relies only on successor pointers: periodic stabilization repairs fingers, and a successor list of size R survives R − 1 simultaneous failures. Other DHTs (Kademlia, CAN) make other trade-offs. IPFS uses a DHT for content addressing.

Q35Describe

How does a node join Chord? How does Chord handle concurrent joins and failures? Give the costs.

Model answer

  • Each node also keeps its predecessor, to allow counter-clockwise routing, which helps the join.
  • Join of n (n knows some node n′ already in the system): (1) initialize the predecessor and fingers of n through n′: finger i = successor of n + 2i; (2) update the fingers and predecessors of existing nodes. Node n becomes the i-th finger of node p if and only if p precedes n by at least 2i and the i-th finger of p succeeds n. The first such p is the immediate predecessor of n − 2i. Search for it and update it. Do this for each of the log N fingers, with a lookup of cost log N each: O(log² N). The keys in (pred(n), n] move to n.
  • Stabilization: concurrent joins and leaves can break the successor pointers. Each node periodically looks up the successor of n + 2i for each finger i.
  • Failures: each node keeps a list of its first R successors. If the immediate successor does not respond, the node contacts the next one in the list. It survives R − 1 simultaneous failures.

Table size O(log N); lookup O(log N) hops; join O(log² N).

Why

Correctness depends only on successor pointers: with correct successors a lookup always succeeds, maybe slowly. Fingers are only shortcuts, so they can be repaired lazily by stabilization.

  2. 14 does not respond, so node 8 contacts the next entry, 20; it does not respond either; node 8 contacts 27, which answers. Node 27 becomes the successor of node 8, and the ring stays connected. Stabilization then repairs the fingers.
  3. All three entries of node 8 are dead. Its fingers (14, 14, 14, 20, 27) are dead too. Node 8 cannot find its successor: the ring breaks at node 8.
  4. R − 1 = 2 simultaneous failures of consecutive successors.

Why

The successor list is a cheap insurance for the only pointer that matters for correctness. Failures are independent, so R consecutive failures are very unlikely when R is about log N. The same list is a natural place to replicate data: the next R nodes are exactly the nodes that take over the keys.

Q40Describe

Give the pros and cons of Chord. Which other DHTs exist and where are they used? What is IPFS and how does it use a DHT?

Model answer

Chord pros: guaranteed lookup; O(log N) per-node state and search scope.

Chord cons: Chord itself is rarely deployed, but its relatives are; more fragile than unstructured networks; non-exact-match search is hard; it does not consider the physical topology.

Other DHTs: they make different trade-offs between search scope, information to store, and cost to maintain the structure under joins and leaves.

  • Kademlia: tree-based structure. It powers BitTorrent's Mainline DHT (trackerless search), IPFS, and Ethereum's peer discovery.
  • CAN: a d-dimensional space. The number of dimensions can change to adapt the system to the application.

IPFS (InterPlanetary File System): the address-based Internet tends to be centralized and vulnerable to single points of failure. IPFS uses a DHT to create a content-based infrastructure: the DHT maps a content id (CID) to the peers that provide that content. Order of magnitude (early 2026): about 4k nodes consistently online, more than 500k clients, lookups of about 0.4 s.

Why

Content addressing is the DHT idea applied to the Web: you ask for "this content" (its hash), not for "this server". Any peer that has the content can serve it, and the hash lets you verify it. The same idea appears in Freenet's content-hash ids and in BitTorrent's magnet links.

Q41ScenarioExam 12 Jul 2024

You implement a document lookup service: each document has a key, and the service finds the host of a document from its key. Scenario 1: tens of thousands of hosts that dynamically join and leave. Scenario 2: fewer than a hundred hosts that never join or leave. In which scenario would you use Chord, and why? How would you implement the service in the other scenario?

Model answer

Scenario 1: Chord. Each host keeps only O(log N) state (about 15 fingers for 215 hosts). A lookup takes O(log N) hops and is guaranteed. Joins cost O(log² N), and stabilization plus successor lists handle churn. No host needs a global view, which is impossible to keep up to date with tens of thousands of dynamic hosts. Store references (key → host), not the documents.

Scenario 2: no Chord. With fewer than a hundred static hosts, each host can keep the full membership list. Use a deterministic mapping (for example, hash the key and assign key ranges to hosts, or a replicated directory table). A lookup takes one hop (or zero), with no routing and no maintenance. A small replicated central index is also acceptable.

Why

Chord exists to avoid a global view when the global view is too big or changes too often. With 100 static hosts the full table is tiny and never changes, so log N hops and stabilization traffic are pure overhead. Justify the choice with the two variables of the question: size and churn.

Q44CompareExam 3 Dec 2014

Describe the routing mechanisms of Freenet and of Chord (the version with finger tables), and compare them.

Model answer

Freenet: the goals are anonymity and censorship resistance. A request for a file id goes to the neighbor that is the "best guess" (closest known id): steepest-ascent hill climbing with backtracking, limited by hops-to-live. The file returns along the same chain, and every node caches it (LRU). Inserts follow the same route, so data is placed where requests will look. Similar ids cluster on the same nodes; the network becomes a small world; popular files spread, unpopular ones may disappear. Link and document encryption, content-hash ids.

Chord: ring of m-bit ids; a key is stored at its successor; each node has m fingers (succ(n + 2i)); a node forwards to the finger whose interval contains the key; each hop halves the distance: O(log N) hops, O(log N) state; join costs O(log² N); successor lists and stabilization handle churn.

FreenetChord
GuaranteeNone (may not find)Always finds the key
Routing stateLearned from traffic, approximateStructured, exact
Failure of a pathBacktracking, hops-to-liveSuccessor list, stabilization
Caching / replicationAlong request paths, popularity-drivenNot built in (successor list)
AnonymityYes, by designNo

Why

Both route "toward closer ids", but Freenet learns its routing tables from traffic, while Chord builds them from a mathematical structure. Learning gives adaptivity and anonymity; structure gives guarantees.
