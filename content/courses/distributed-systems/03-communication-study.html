§1

Fundamentals: protocols, middleware, types of communication

Core idea. The transport layer (TCP, UDP) gives the basic communication. Middleware adds common services on top: marshalling, naming, security, replication. Each communication service has two independent properties: transient or persistent, and synchronous or asynchronous.

Q1Exercise

Define transient vs persistent and synchronous vs asynchronous communication. Then classify: (a) a normal RPC; (b) a one-way RPC; (c) e-mail; (d) a message queue put; (e) a send on a UDP socket.

Model answer

Transient: sender and receiver must both run for the message to be delivered. Persistent: the communication system stores the message until it can deliver it.

Synchronous: the sender blocks until the receiver has stored, received or processed the message. These are three levels: receipt-based, delivery-based, response-based. Asynchronous: the sender continues at once.

  1. Normal RPC: transient, response-based synchronous.
  2. One-way RPC: transient, asynchronous (or receipt-based if it waits for an ack).
  3. E-mail: persistent, asynchronous.
  4. Queue put: persistent, asynchronous.
  5. UDP send: transient, asynchronous.

Why

The two properties are independent questions. Persistency asks: "must the receiver be alive now?" Synchronicity asks: "how long does the sender wait?" Keep them separate and every case is easy to classify. The slides name two popular combinations: transient with synchronization after processing (RPC), and persistent with synchronization at request submission (message queuing).

§2

Remote procedure call

Core idea. RPC hides remote communication behind a normal procedure call. A client stub and a server stub do the work: they marshal parameters, send messages, and unmarshal results. The stubs are generated from an IDL description. The difficult parts: parameter passing, binding the client to a server, and the cost of synchronous calls.

Q2DescribeExam 25 Feb 2015

Describe Remote Procedure Call: communication model, operation, technological and practical alternatives and issues.

Model answer

Model. Developers know procedure calls. A well-engineered procedure is a black box. So there is no reason not to execute it on another machine. RPC is transient and synchronous: the caller blocks until the result arrives.

Operation.

  1. The client calls the client stub like a local procedure.
  2. The stub serializes the parameters (flattens structures into bytes) and marshals them (converts to a common representation: endianness, character sets).
  3. The middleware sends the invocation message.
  4. The server stub unmarshals the parameters and calls the real procedure.
  5. The result goes back in the same way.

The stubs are generated automatically from an IDL. The IDL separates interface from implementation, and has mappings to many languages.

Technologies. Sun RPC (ONC RPC): XDR data format, TCP or UDP, pass by copy only, used by NFS. DCE RPC: several call semantics (at-most-once, idempotent, broadcast), directory, time and file services, Kerberos security; basis of DCOM and .NET remoting.

Issues and alternatives. Pass by reference; binding (portmap, DCE directory); dynamic activation (inetd); lightweight RPC on a single machine; asynchronous, batched and queued RPC. The next questions cover each one.

Why

The question has three parts. The grader checks each part. Give the call flow with stubs as a numbered list, name the two technologies, then list the issues. The list of issues is also the structure of the slides, so it is easy to remember.

Q3Exercise

Explain pass by value, by reference and by copy/restore. Then give the final value of a under pass by reference and under copy/restore:

void inc2(int *x, int *y) { *x = *x + 1; *y = *y + 1; }
int a = 0;
inc2(&a, &a);

Model answer

  • By value: the callee gets a copy. Changes do not reach the caller.
  • By reference: the callee gets the address of the variable. Changes go directly to the caller's variable.
  • By copy/restore (value/result): the value is copied in; at the end, the final value is copied back into the caller's variable.

By reference: x and y point to the same variable. a = 0 → 1 → 2. Result a = 2.

Copy/restore: x and y are two separate copies, both 0. Each becomes 1. Both are restored into a. Result a = 1.

Why

A pointer has a meaning only in the address space of one process. So RPC cannot send a real reference. Copy/restore is the usual replacement, but the slides say: "semantics is different!". The difference shows with aliasing, when two parameters refer to the same memory. Also, copy/restore works for arrays but not for arbitrary linked structures. Optimization: copy only in, or only out, when the IDL marks a parameter as input-only or output-only.

Q4CompareExam 12 Jul 2024 · 9 Sep 2015

Consider RPC and RMI and focus on parameter passing. Describe how parameter passing works in the two systems. Explain why pass by reference is a problem in RPC, how RMI addresses it, and why pass by value is a problem for RMI.

Model answer

RPC. Parameters go by value: serialized and marshalled by the stubs. By reference is a problem because a pointer is valid only in the caller's address space. Sun RPC does not support it (only one input and one output parameter, copied). Some systems use copy/restore, which has different semantics with aliasing and does not work for arbitrary data structures.

RMI. It is the OO version of RPC. Two kinds of parameters:

  • Remote objects go by reference. RMI has remote object references: a reference that is valid in the whole system (host, port, object id). The receiver gets a proxy (stub) that forwards calls to the original object. So pass by reference is natural in RMI.
  • Non-remote objects go by value (in Java they must be serializable). The receiver gets a copy.

By value is a problem in RMI because an object is data and code. The receiver needs the methods of the object's class. If the class is not available there, the copy is useless. Java RMI solves this with code on demand: it downloads the class. CORBA is multi-language, so it cannot move code: with valuetype, the programmer must provide an implementation of the methods on each side with the same semantics.

Why

The two problems are symmetric. RPC handles data well but has no global reference. RMI has global references, but a copy of an object carries behavior, and behavior is code. Java can move code because it is a single platform (JVM). CORBA cannot, because sender and receiver can use different languages.

Exam tip

Use the exact words "remote object reference", "proxy/stub", "serializable", "code on demand" and "valuetype". They show that you know the specific mechanisms.

Q5Compare

How does a client find and bind to a server? Compare Sun's portmap with DCE's solution. What is dynamic activation?

Model answer

Binding has two problems: (1) find where the server is (which host); (2) find how to talk to it (which port). Do not hard-wire this information in the client.

Sun: a portmap daemon on each host. The server picks a free port and registers it with portmap, with its service id. The client asks portmap for the port. Portmap serves only local servers, so it solves only problem (2). The client must know the host in advance, or multicast the query to many daemons, or use a directory service.

DCE: a DCE daemon works like portmap (problem 2). A directory server (binder) gives location transparency (problem 1): the client knows only where the directory is. The directory can be distributed for scalability. The client contacts the directory only once per session.

Dynamic activation: a server that waits with no requests wastes resources. A local daemon (inetd in Sun) starts the server process when a request arrives, or redirects the request if the process already runs. The map service → program is in a configuration file. Cost: the first request is slower.

Why

Splitting "where" and "how" is the key. Ports change at each server restart, so they must be local information. Hosts are global information, so they belong in a directory. This is the same idea as naming in chapter 04: a name must be resolved into an address.

Q6Exercise

Lightweight RPC: why do the slides say "1 parameter copy instead of 4"? When is it used?

Model answer

It is used when client and server are on the same machine. A normal RPC would use TCP/UDP, which is useless there.

Normal RPC, 4 copies: client stub → kernel, kernel → server stub (request); server stub → kernel, kernel → client stub (reply). That is 2 × (stub→kernel + kernel→stub).

Lightweight RPC, 1 copy: client and server share a private memory region (a shared stack). The client stub copies the parameters onto the shared stack once and makes a system call. The kernel does a context switch and runs the procedure in the server. Results go on the same stack, then another system call and context switch return to the client.

Other advantage: fewer threads, because no process must listen on a channel. Similar ideas exist in DCOM and .NET.

Why

You want the same programming primitive for local and remote calls (transparency). But you do not want to pay the network cost locally. Shared memory removes the copies through the kernel. The context switch is the only cost left.

Q7Scenario

A mobile app calls a server through RPC. The phone often loses connectivity, and many calls (e.g. "log this event") return no result. Which variants of RPC help? Describe them and their semantics.

Model answer

  • Asynchronous RPC with ack: the call returns when the server acknowledges the request. Good for calls with no result.
  • One-way RPC: returns at once, no ack. Risk: "maybe" semantics; the call can be lost.
  • Callback: the server later calls the client back with the result.
  • Deferred synchronous (promise/future): the call returns a promise at once. The client polls or waits on it later.
  • Batched RPC (Sun): calls with no result are buffered on the client. They go together with the next non-batched call or at a timeout. Fewer messages, which is good for "log event".
  • Queued RPC (MIT Rover): made for mobility. If the phone disconnects between request and reply, the server retries the reply later. Requests and replies can use different channels. A network scheduler can batch, compress, or reorder by priority. The client uses promises.

For this app: batch the "log" calls, and use queued RPC with promises for the calls that need a result.

Why

Synchronous RPC wastes the client's time and fails when the link is down. Each variant removes part of the waiting. The price is weaker semantics: with one-way calls you do not know if the call ran. Queued RPC adds persistence, so it moves RPC towards message queuing.

§3

Remote method invocation

Core idea. RMI applies RPC to objects. The interface lives on one host and the implementation on another. The big new feature: remote object references can be passed around. The big new problem: passing objects by copy means passing code.

§4

Message-oriented communication

Core idea. RPC is synchronous, point-to-point and tightly coupled. Message-oriented communication uses one-way messages. It is usually asynchronous, often persistent and multi-point, so components are more decoupled. Four models: sockets and MPI (message passing), message queuing, publish-subscribe.

Q9CompareRelated: middleware exam 2013

Compare stream sockets and datagram sockets. What is IP multicast, and how is it different from broadcast?

Model answer

Stream sockets (TCP): connection-oriented, reliable, ordered byte stream. The server listens and accepts connections on a port; the client connects. A connected socket is identified by 4 numbers: server IP, server port, client IP, client port.

Datagram sockets (UDP): no connection, best-effort. Client and server do the same: create a socket, bind it to a port, then sendto/recvfrom. One socket can talk to many hosts.

IP multicast: delivers UDP datagrams efficiently to a group. Groups use class D addresses (224.0.0.0 – 239.255.255.255). Receivers must join the group (setsockopt). Groups are open: senders do not need to be members. Most routers do not route multicast outside the LAN.

Difference from broadcast: broadcast reaches every host on the network, and every host must process the packet. Multicast reaches only the hosts that joined, so it costs less with many hosts and high traffic.

Why

Sockets are the common abstraction for the transport layer. Every higher model (RPC, MPI, queues) is built on them. Multicast shows the limit of the network layer: it is efficient, but routers often do not support it on the Internet. This is why middleware builds multicast in overlays (see queue relays and pub-sub brokers).

Q10Describe

Why was MPI introduced? Describe its model and its main limitation.

Model answer

Sockets are low level and protocol independent, so they are awkward to use. High-performance networks (clusters) need higher-level primitives for asynchronous, transient communication, with more services than read and write. MPI is the platform-independent answer.

Model: communication happens in a known group of processes. Each process has a local id in the group. The pair (groupID, processID) is the address. There are collective operations: MPI_Bcast, MPI_Reduce, MPI_Scatter, MPI_Gather. There are many send variants with different synchronization.

Limitation: no fault tolerance. A crash is fatal for the whole computation.

Why

MPI targets a cluster: a fixed set of reliable machines on a fast network, running one parallel program. In that setting fault tolerance costs more than it gives. On a wide-area network this assumption fails, so MPI fits clusters, not general distributed systems.

Q11Describe

Describe message queuing: primitives, client-server with queues, and the architecture (queue managers, relays, brokers).

Model answer

Point-to-point, persistent, asynchronous communication. Usually the only guarantee is the eventual insertion of the message in the recipient's queue. Decoupled in time and space: a generalization of e-mail. Each component has an input and an output queue. Products: IBM MQ, MSMQ, JMS.

PrimitiveMeaning
putAppend a message to a queue
getBlock until the queue is not empty, then remove the first message
pollCheck the queue and remove the first message; never block
notifyInstall a handler called when a message is put in the queue

Client-server with queues: clients put requests in the server's queue; the server takes them, processes them and puts results in the clients' queues. Clients do not need to stay connected. Many servers can share one queue: automatic load balancing.

Architecture:

  • Queues have symbolic names, so a lookup service maps them to network addresses (often a static, pre-deployed topology).
  • Queue managers handle queues, locally or remotely. Some act as relays (application-level routers) in an overlay network. Relays improve fault tolerance and give multi-point delivery without IP multicast.
  • Message brokers are application-level gateways that convert message formats, to integrate different subsystems.

Why

Persistence is the key. Because the queue stores the message, the receiver can be offline. This gives decoupling in time, which RPC and sockets cannot give. Shared queues give load balancing with no extra protocol.

Q13CompareExam 5 Sep 2013

Distinguish subject-based and content-based publish-subscribe. What is the trade-off?

Model answer

Subject-based (topic-based): the set of subjects is fixed in advance. A subscriber selects a subject, e.g. "Distributed Systems". It is similar to multicast groups.

Content-based: subscriptions are filters on the content of the event, e.g. course = "Distributed Systems" ∧ date > 16.11.2004 ∧ room = "D04". The set of filters is defined by the subscribers. One event can match many subscriptions. The two can be combined.

Trade-off: more expressiveness → more complex and slower implementation (matching filters is costly, routing is hard). But expressiveness also gives more filtering: fewer useless events reach the subscribers.

Why

With subjects, routing is simple: one subject = one group. With content, each broker must evaluate filters on each event. This is why content-based systems need special routing (next questions) and why a DHT supports only subjects.

Q14Exercise

Four brokers form an acyclic overlay: B1–B2, B2–B3, B2–B4. Subscriber S1 on B3 subscribes to fire*. Subscriber S2 on B4 subscribes to temp*. Publisher P on B1 publishes fire alarm. Describe what happens with (a) message forwarding and (b) subscription forwarding. Count the broker-to-broker messages for the subscriptions and for the event.

Model answer

(a) Message forwarding. Each broker stores only the subscriptions of its own clients. Subscriptions: 0 broker messages (B3 keeps fire*, B4 keeps temp*). The event is flooded on the tree: B1→B2, B2→B3, B2→B4 = 3 messages. B3 delivers to S1. B4 drops the event.

(b) Subscription forwarding. Each subscription is propagated to all brokers, never twice on the same link. fire*: B3→B2, B2→B1, B2→B4 = 3. temp*: B4→B2, B2→B1, B2→B3 = 3. Total 6 messages. Now each broker knows on which link each subscription came. The event follows the reverse path of fire*: B1→B2 (B1 got fire* from B2), B2→B3 (B2 got fire* from B3). Total 2 messages. B4 gets nothing.

With coverage optimizations, a broker does not forward a subscription that is covered by one it already forwarded (e.g. "Distributed *" covers "Distributed systems").

Why

Message forwarding makes subscriptions free and events expensive. Subscription forwarding makes subscriptions expensive and events cheap. So the choice depends on the ratio. Many events and stable subscriptions → subscription forwarding. Few events and frequent subscription changes → message forwarding. Hierarchical forwarding is in between: on a rooted tree, subscriptions and messages go up to the root; messages go down only along branches where a matching subscription came from.

Q15DescribeExam 17 Jan 2024 · 5 Sep 2013

Explain how a generic DHT can be used to implement a distributed publish-subscribe dispatcher. Which is the main limitation of this approach?

Model answer

A DHT routes efficiently to the successor of any id: the node with the smallest id ≥ that id.

  • Subscribe to subject S: compute HS = hash(S). Route a subscribe message towards succ(HS). On each node along the path, leave routing information that points back to the subscriber.
  • Publish on subject S: compute HS and route the event towards succ(HS). When the event meets a path left by subscriptions (at the latest at succ(HS)), follow those paths back to the subscribers.

succ(HS) is the rendezvous node for subject S. The DHT overlay can have cycles; the DHT gives the routing.

Main limitation: it works only for subject-based pub-sub. The hash needs an exact key. A content-based filter like "temp > 40" has no single key, so you cannot hash it to one node. A second problem: the rendezvous node of a popular subject becomes a hot spot.

Why

Hashing is the trick: publishers and subscribers do not know each other, but they both compute the same node from the subject. A hash destroys order and ranges. So "temp > 40" and "temp = 41" go to unrelated nodes. Content-based routing needs other strategies (next question).

Q16Describe

For content-based routing on cyclic topologies, describe per-source forwarding (PSF), improved PSF (iPSF) and per-receiver forwarding (PRF). How are the paths built?

Model answer

  • PSF: each source defines a shortest path tree (SPT). The forwarding table is organized per source: for each source v, the children of this node in the SPT of v; for each child u, a predicate that joins the predicates of all nodes reachable through u.
  • iPSF: like PSF, but it merges indistinguishable sources. Two sources A and B are indistinguishable at node n if n has the same children in T(A) and T(B), and reaches the same nodes through them. Result: smaller tables that are easier to build.
  • PRF: the source computes the set of receivers and puts it in the message header. At each hop the set is partitioned among the next hops. Two tables: a unicast routing table, and a table with the predicate of each node.

Path building: Distance Vector builds minimum-latency SPTs with config / config-response packets; each node knows only its neighbors in the SPT. Link-State floods link-state packets; each node knows the whole topology and computes the SPTs locally; any metric is possible.

Why

In a cyclic graph, a message can reach a node twice. A tree per source removes the cycles. The difference is where the routing information lives: in the tables (PSF, iPSF) or in the message header (PRF).

Q17Describe

What does complex event processing (CEP) add to publish-subscribe? Which issues remain open?

Model answer

CEP adds rules that describe how to build composite events from primitive (or composite) events. Example: "smoke on floor 2 and temperature > 50 on floor 2 within 1 minute → fire on floor 2". Pub-sub looks at one event at a time; CEP looks at patterns of events.

Open issues:

  • Rule language: balance expressiveness with processing complexity.
  • Processing engine: how to match incoming events efficiently to build composite events.
  • Distribution: how to distribute processing, in a cluster or over a network.

Why

It is the same trade-off as subject vs content filtering, one step higher. More powerful rules filter better, but they cost more to evaluate and to distribute.

§5

Stream-oriented communication

Core idea. Usually time affects only performance. For streams such as live video, time affects correctness: a frame that arrives too late is useless. IP is best effort, so the application must create the quality of service (QoS) itself.

Q18Describe

Define the asynchronous, synchronous and isochronous transmission modes. Which QoS parameters describe a stream?

Model answer

  • Asynchronous: data units go one after the other, with only an ordering constraint.
  • Synchronous: each unit has a maximum end-to-end delay.
  • Isochronous: each unit has a maximum and a minimum end-to-end delay: the jitter is bounded.

Streams can be simple, or complex (made of substreams, e.g. audio + video).

QoS parameters: required bit rate; maximum delay to set up the session; maximum end-to-end delay; maximum variance of the delay (jitter).

Why

Playback needs regular spacing, not only speed. A video at 25 fps needs a frame every 40 ms. Frames that arrive fast but irregularly still break playback. That is why isochronous transmission bounds the jitter.

Q19ScenarioExam 18 Nov 2023 · 18 Jun 2024

You want to implement your own streaming library for a video service (or an Internet radio). (a) List the requirements of this service that do not fit the characteristics of IP. (b) Describe the mechanisms you could use to address those limitations.

Model answer

(a) Requirements vs IP. IP is best effort: no guarantee on bandwidth, delay, jitter, loss or order. The service needs:

  • a minimum, constant bit rate;
  • a bounded end-to-end delay (critical for live content);
  • bounded jitter for smooth playback;
  • few losses, and a short session setup time;
  • synchronization of substreams (audio and video: lip sync).

TCP fixes loss and order with retransmissions, but retransmissions add delay and jitter. So streaming often uses UDP and handles losses itself.

(b) Mechanisms.

  • DiffServ: mark packets in the IP header (DSCP, e.g. Expedited Forwarding). But Internet routers do not necessarily support it.
  • Buffering at the receiver: start playback later, then absorb the jitter. You trade setup time for jitter.
  • Forward error correction: send redundant data, so the receiver rebuilds lost packets without retransmission.
  • Interleaving: spread consecutive frames over different packets. A lost packet then causes many small gaps instead of one long gap.
  • Stream synchronization at the sender (merge substreams) or at the receiver.

For the radio (one sender, many listeners), add one-to-many distribution: IP multicast inside a LAN, or relay servers in an overlay, because Internet routers do not route multicast.

Why

The exam asks for a mapping: each requirement → why IP fails it → which mechanism fixes it. Keep that structure. Note that most mechanisms work at the application layer, because the network layer gives no guarantees.

Q20Exercise

An audio server sends one packet every 20 ms. The network delay of each packet is between 40 ms and 160 ms. How long must the client wait after the first packet arrives before it starts playback, to never stop? How many packets must the buffer hold?

Model answer

Worst case: the first packet is the fastest (40 ms) and a later packet is the slowest (160 ms). Jitter = max − min = 160 − 40 = 120 ms.

Wait 120 ms after the first arrival. Then playback of packet i is at 20·i + 40 + 120 = 20·i + 160. Packet i arrives at most at 20·i + 160. So it is always ready in time.

Buffer: in 120 ms, 120 / 20 = 6 more packets arrive in the best case. So the buffer holds about 6–7 packets.

Why

This is the slide sentence "control max jitter by sacrificing session setup time", with numbers. The buffer converts variable delay into a fixed delay equal to the maximum. Same reasoning as the Pepperland charge in chapter 02: the uncertainty is max − min.

Q21Exercise

A stream has 16 frames. Each packet carries 4 frames. Packet 2 is lost. Which frames are lost without and with interleaving? Why is interleaving better?

Model answer

Without interleaving: packet 1 = frames 1–4, packet 2 = 5–8, … Losing packet 2 loses frames 5, 6, 7, 8: one gap of 4 consecutive frames.

With interleaving: packet j carries frames j, j+4, j+8, j+12. Packet 2 = frames 2, 6, 10, 14. Four separate gaps of one frame each.

A one-frame gap is easy to hide (repeat or interpolate the neighbors). A long gap is very visible or audible.

Why

Interleaving does not lower the loss. It spreads the loss so that it is less harmful. The cost: the receiver must wait for more packets before it can play a sequence, so the delay increases.

Q22Exercise

Why is stream synchronization hard? Give the maximum jitter for (a) left and right channels of CD-quality audio and (b) lip sync of a 30 fps video.

Model answer

  1. CD audio: 44,100 samples per second. Each sample must stay in sync: 1 / 44,100 s ≈ 23 μs.
  2. Lip sync at 30 fps: each audio interval must stay with its frame: 1 / 30 s ≈ 33 ms.

Synchronization can happen at the sender (merge the streams into one) or at the receiver. It can happen in the application or in the middleware.

Why

"Synchronized" depends on the data unit. The limit is one unit of the finest stream. Audio samples are very short, so stereo channels need a very tight bound. That is why they usually travel merged in the same stream.
