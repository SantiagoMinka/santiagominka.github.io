§1

Atomic commit and two-phase commit

Core idea. Atomic commit gives the "A" of ACID when a transaction updates data on several nodes: either all nodes commit or all abort. Every node votes; the outcome is commit only if all vote commit. 2PC has a voting phase and a decision phase. It is always safe, but a coordinator crash can block the participants.

Q1Compare

Compare atomic commit and consensus. For each one, say who proposes what, what the nodes agree on, and how many failures it tolerates.

Model answer

ConsensusAtomic commit
InputOne or more nodes propose a valueEvery node votes commit or abort
OutcomeNodes agree on one of the proposed valuesCommit if and only if all nodes vote commit; abort otherwise
FailuresTolerated, as long as a majority of nodes is availableAny crash leads to an abort
Typical useReplicated state machines (Raft, Paxos)Distributed transactions in a partitioned (sharded) DBMS

Atomic commit guarantees atomicity: if the transaction commits, its effects are durable; if it aborts, it has no side effects. Consistency (preserving invariants) relies on this atomicity.

Why

In consensus any proposed value is acceptable, so the majority can choose without the missing nodes. In atomic commit every node holds a different part of the data. A node that does not answer may be unable to apply its part, so the only safe answer is abort. The common trap is to say "2PC is a consensus protocol with a majority": it is not, it needs all the votes.

Q2Describe

Describe two-phase commit (messages, coordinator and participant states). Analyze what happens when a participant or the coordinator fails. Why is 2PC called a blocking protocol?

Model answer

Messages. The client sends commit T to the coordinator (transaction manager). Phase 1 (voting): the coordinator sends prepare; each participant (resource manager) answers vote-commit or vote-abort. Phase 2 (decision): if all votes are commit, the coordinator sends global-commit, else global-abort. Participants answer with ack.

NodeStateEvent → next state
CoordinatorInitrcv commit T, send prepare → Wait
CoordinatorWaitrcv all vote-commit, send global-commit → Commit; rcv a vote-abort (or timeout), send global-abort → Abort
ParticipantInitrcv prepare, send vote-commit → Ready; rcv prepare, send vote-abort → Abort
ParticipantReadyrcv global-commit, send ack → Commit; rcv global-abort, send ack → Abort

Participant fails: the coordinator waits in Wait; after a timeout it decides abort.

Coordinator fails:

  • Participant in Init (waits for prepare): it can decide abort. No participant can have received global-commit.
  • Participant in Ready (waits for the decision): it cannot decide alone. It can wait for the coordinator to recover, or send a decision-request to the other participants. If one of them received the decision, it follows that decision. If one is in Init, the coordinator crashed before the end of the prepare phase, so it assumes abort. If all are in Ready, nothing can be decided until the coordinator recovers: the protocol blocks.

Why

A participant in Ready promised to commit if asked, so it cannot abort. It does not know the decision, so it cannot commit. 2PC is always safe, but it is vulnerable to a single-node failure (the coordinator). If the restore is slow (for example a manual procedure), the system stays unavailable and the locks stay held.

Q3Describe

In the 2PC pseudocode, list what the coordinator and a participant write to their local log, and where they use a timeout. Why must a node write to the log before it sends the message? How does a node use the log when it restarts after a crash?

Model answer

The log is on durable storage: it survives crashes.

NodeLog writes (in order)Timeouts
Coordinatorstart_2PC, then global-commit or global-abortWhile it collects votes. On timeout: write global-abort, multicast global-abort, exit.
Participantinit, then vote-commit or vote-abort, then the global decision(1) While it waits for prepare: on timeout, write vote-abort and exit. (2) After vote-commit, while it waits for the decision: on timeout, multicast decision-request to the other participants and remain blocked until a decision arrives.

Log before send. Suppose the coordinator sends global-commit and crashes before it logs it. At restart it finds no decision and could abort, while some participant already committed. Suppose a participant sends vote-commit and crashes before it logs it. At restart it could abort, while the coordinator decided commit. Writing first makes every promise survive the crash.

Restart.

  • Participant with only init: it never voted commit, so it aborts.
  • Participant with vote-commit and no decision: it is in Ready. It must ask the coordinator or the other participants.
  • Participant with a decision: it applies the decision again.
  • Coordinator with only start_2PC: no decision exists anywhere, so it can safely decide abort.
  • Coordinator with a decision: it sends the decision again.

Why

The log turns "what I said" into "what I will still say after a crash". The timeouts are asymmetric. Before the vote, a timeout can end in abort, because the node did not promise anything. After vote-commit, a timeout cannot end in a decision: the participant can only ask and wait. This is the exact place where 2PC blocks.

Q4Exercise

Coordinator C, participants P1, P2, P3. All participants vote commit. C writes global-commit to its log, sends global-commit to P1, then crashes before it sends to P2 and P3. (a) What does each participant do? Does anybody block? (b) Same case, but P1 also crashes right after it commits. (c) What does C do when it restarts?

Model answer

  1. P1 receives global-commit, logs it, commits, sends ack. P2 and P3 are in Ready. Their timeout expires; they multicast decision-request. P1 answers "commit". P2 and P3 log global-commit and commit. Nobody blocks.
  2. P2 and P3 are in Ready. They can only reach each other, and both are in Ready. They cannot decide: they block until C or P1 restarts. The decision (commit) exists, but nobody who knows it is reachable.
  3. C finds global-commit in its log. It sends global-commit again to all participants. P2 and P3 commit. P1 ignores the duplicate (it already committed).

Why

Case (b) is the interesting one. P2 and P3 cannot abort, because P1 may have committed. They cannot commit, because C may have decided abort. From their point of view the two worlds look the same. Blocking does not mean "no decision was taken"; it means "the survivors cannot know it".

Q5Exercise

Coordinator C, participants P1, P2, P3. C writes start_2PC and starts to multicast prepare. Only P1 receives it; then C crashes. P1 votes commit. Trace what P1, P2, P3 and the restarted C do. What is the outcome?

Model answer

  1. P1 writes vote-commit, sends it (C is down), and is in Ready.
  2. P2 and P3 are in Init. Their timeout for prepare expires. Each writes vote-abort and exits: they abort.
  3. P1's timeout for the decision expires. It multicasts decision-request. P2 (or P3) answers that it is in Init or Abort.
  4. P1 concludes that C crashed before the end of the prepare phase. It assumes abort.
  5. C restarts. Its log has only start_2PC, with no decision. It decides abort and sends global-abort.

Outcome: all nodes abort. Nobody blocks.

Why

A participant in Init (or one that voted abort) proves that C could not have decided commit: commit needs all votes. So one such answer is enough to abort safely. The blocking case needs all reachable participants in Ready.

Q7Exercise

Coordinator C, participants P1, P2, P3. All three vote commit. C receives all votes and crashes before it writes any decision. (a) What do P1, P2, P3 do? (b) Why can they not abort, even if they know that C wrote no decision? (c) What changes if P3 had voted abort?

Model answer

  1. All three are in Ready. They time out and send decision-request. Every answer is "I am in Ready". They block until C restarts. Their locks stay held.
  2. They do not know it. From their point of view, this case is identical to "C wrote global-commit and crashed before it sent it". In that second case C commits at restart. If they aborted, the result would be inconsistent.
  3. P3 is in Abort. It answers "abort" to the decision-request. P1 and P2 abort. Nobody blocks.

Why

This is the textbook blocking case: every participant voted commit and the only node that knows the outcome is down. Safety is kept, liveness is lost. 3PC was designed to remove exactly this case.

§2

Three-phase commit, FLP and CAP

Core idea. 3PC adds a Pre-commit phase: first tell everybody the outcome, then commit. Survivors can then decide without the coordinator, so locks are released. The quorum version is always safe, but partitions can still stop it. FLP says this trade-off is unavoidable in an asynchronous system. CAP states the same tension for replicated data: during a partition, choose consistency or availability.

Q9Compare

How does three-phase commit avoid blocking? List the recovery rules of a participant when the coordinator fails, and compare 3PC with 2PC.

Model answer

3PC splits the decision phase in two. The coordinator collects the votes. If all are commit, it sends prepare-commit; participants go to Pre-commit and answer ready-commit. Then the coordinator sends global-commit; participants commit and ack.

Single participant fails. Coordinator in Wait: it can decide abort (no participant can be in Pre-commit). Coordinator in Pre-commit: it can safely commit, and tells the failed participant to commit when it recovers.

Coordinator fails. A participant in Init can decide abort. A participant in Ready contacts the others:

  • at least one in Abort → abort; at least one in Init → abort;
  • at least one in Commit → commit;
  • at least one in Pre-commit, and #Pre-commit + #Ready form a majority → commit;
  • a majority in Ready, nobody in Pre-commit → abort.

No two participants can be one in Pre-commit and the other in Init.

2PC3PC (quorum version)
Phases23, always
Coordinator crashMay block; locks stay heldSurvivors decide; locks released
PartitionsSafe, may blockSafe, may lose liveness
Use in practiceWidely usedRarely used (cost)

Why

Pre-commit is a "decision announced" state. If a survivor saw it, nobody voted abort, so commit is safe. If nobody in a majority saw it, nobody can have committed, so abort is safe. Both 2PC and 3PC still need a failover mechanism to recover failed nodes. The real gain of 3PC is that resources are unlocked even when the coordinator crashes.

Q10Describe

State the two conditions that make a commit protocol non-blocking (Skeen and Stonebraker). Show which state of the 2PC participant violates them, and how 3PC satisfies them.

Model answer

A protocol is non-blocking if and only if:

  1. No state leads directly to both commit and abort.
  2. No state where the final decision is impossible to determine can lead to commit.

2PC. The participant state Ready leads directly to Commit and to Abort: it violates condition 1. Ready is also a state where the decision cannot be determined (the coordinator is down and everybody is in Ready), and it leads to Commit: it violates condition 2.

3PC. Ready leads to Abort or to Pre-commit, never directly to Commit. Pre-commit leads only to Commit. In Pre-commit the decision is known: every participant voted commit. The same holds for the coordinator: Wait → Abort or Pre-commit; Pre-commit → Commit.

Why

The idea is to put a buffer state between "uncertain" and "committed". A node can commit only from a state where everybody already knows the outcome. So a node that is still uncertain knows that nobody has committed yet.

Q12Exercise

Find the impossible combinations. After a coordinator crash, a student reports these pairs of participant states. For each pair, say if it is possible and why. (a) 3PC: P1 Pre-commit, P2 Init. (b) 2PC or 3PC: P1 Commit, P2 Abort. (c) 2PC: P1 Commit, P2 Init. (d) 3PC: P1 Commit, P2 Pre-commit. (e) 2PC: P1 Ready, P2 Abort.

Model answer

  1. Impossible. The coordinator sends prepare-commit only after all participants voted commit, so nobody is still in Init.
  2. Impossible. This violates atomicity, which both protocols guarantee (safety).
  3. Impossible. global-commit is sent only after all votes are commit; P2 left Init when it voted.
  4. Possible. The coordinator sent global-commit to P1 and crashed before it reached P2.
  5. Possible. P2 voted abort (it goes directly to Abort), or global-abort reached P2 but not P1.

Why

Reason about which messages must already exist. A state that the coordinator reaches only after all votes excludes Init everywhere. Case (a) is exactly the property the slides state for 3PC, and it is why "someone in Init" safely means abort.

Q14Describe

What does 3PC guarantee? Distinguish the original protocol and the quorum-based version with respect to network partitions. What is the real advantage of 3PC over 2PC, and what is its cost?

Model answer

  • Original 3PC: non-blocking with crash failures. With network partitions it can violate safety: the two sides can decide differently.
  • Quorum-based 3PC (the version in the slides): safety is always guaranteed. Network partitions can still violate liveness: a side without a majority cannot decide.
  • Real advantage: in 2PC resources (for example database rows or columns) stay locked while the decision is unknown. In 3PC they can be unlocked even if the coordinator crashes. In both protocols a failover mechanism is still necessary to recover the failed nodes.
  • Cost: three phases of communication, always. It is not frequently used in practice.

Why

Without quorums, each side of a partition sees only part of the states, and each side can apply a different rule (one side sees Pre-commit, the other only Ready). Majorities fix this, because only one side can have a majority. The price is that the minority side must wait.

Q15Describe

State the FLP result. Use it to summarize the commit protocols: what does 2PC sacrifice, what does 3PC sacrifice, and what does Raft do?

Model answer

FLP (Fischer, Lynch, Paterson, 1985, "Impossibility of distributed consensus with one faulty process"): in an asynchronous system, no deterministic protocol can guarantee both safety and liveness if even one process can fail. In the words of the slides: you cannot have both liveness and safety in presence of network partitions in an asynchronous system.

  • 2PC: keeps safety, sacrifices liveness (it blocks on a coordinator crash).
  • 3PC: more robust and more expensive; in theory it can still sacrifice liveness with network partitions.
  • Raft: safety always; liveness is not guaranteed in theory, but it holds in practice under typical conditions, thanks to randomized timeouts.

Why

In an asynchronous system a slow process and a crashed process look the same. A protocol that waits may wait forever; a protocol that stops waiting may act without information that exists somewhere. Every practical protocol picks "never wrong" and accepts "sometimes stuck".

Q16Describe

State the CAP theorem and explain its practical meaning for modern data systems.

Model answer

A distributed system where nodes store some replicated or partitioned data can have at most two of these three properties: Consistency (equivalent to a single up-to-date copy of the data), Availability of the data for reads and updates (liveness), tolerance to network Partitions.

Partitions can always happen, so the real choice is: during a partition, stay consistent (refuse some requests) or stay available (accept requests and risk divergence). Modern data systems choose a suitable balance for the application at hand, often with weaker definitions of consistency (chapter "replication and consistency").

Why

During a partition, a replica that accepts a write cannot tell the other side. Either it answers (available but inconsistent) or it waits (consistent but unavailable). There is no third option. Without partitions, a system can have both C and A.

§3

Replicated state machines and Raft overview

Core idea. A replicated state machine: identical copies apply the same commands in the same order, so clients see one fault-tolerant machine. A replicated log fixes the order. Raft builds this log with a leader. It is equivalent to multi-Paxos, but designed to be understandable: log replication, leader election, safety. With 2f + 1 servers it tolerates f crashes.

Q18Describe

What is a state machine, and what is a replicated state machine? Explain the role of the replicated log with the example of a storage system.

Model answer

A state machine manages an internal state and responds to external requests (commands). Example: a storage system; the state is a set of variables, the commands are read and write operations.

A replicated state machine is a collection of servers that work as a coherent group. They operate on identical copies of the same state, offer a continuous service even if some servers fail, and clients see them as a single fault-tolerant machine.

Each server has a log and a consensus module. The consensus modules make all logs equal, for example w(x)1, w(y)2, w(x)8 on every server. Each state machine executes the log in order, so all reach x = 8, y = 2. The client that sent w(x)8 gets ok.

Why

A deterministic state machine that starts from the same state and executes the same commands in the same order ends in the same state. So the hard problem reduces to one thing: agree on the order of the log. That is what consensus gives.

Q19DescribeExam 18 Nov 2023 · 6 Sep 2024

Consider the Raft consensus protocol. Which problem does it solve? Under which assumptions? Does it guarantee safety (it is always correct) and liveness (it always makes progress)? Motivate your answers.

Model answer

Problem. Consensus on a sequence of commands for a replicated state machine: all non-failing machines execute the same commands in the same order.

Assumptions. Asynchronous, unreliable communication: messages can take arbitrarily long, be duplicated, be lost. Processes fail by stopping and may restart; they record their state on durable storage. No Byzantine failures.

How (short). Followers, candidates, leader. Time is divided into terms. A follower that hears no heartbeat within a randomized timeout (150–300 ms) becomes a candidate, increments the term, votes for itself and sends RequestVote. A majority of votes makes it leader (one vote per server per term). The leader appends client commands to its log and sends AppendEntries; an entry replicated on a majority is committed and executed.

Safety: yes, always.

  • At most one leader per term (one vote per term, majority needed).
  • Log matching: AppendEntries carries the index and term of the previous entry; a follower rejects mismatches, and the leader retries with lower indexes. So equal index and term mean identical logs up to that point.
  • Leader completeness: a candidate includes its last index and term; voters refuse candidates with less up-to-date logs. So every new leader has all committed entries.

Liveness: not guaranteed in theory (FLP). Split votes can in principle repeat forever. In practice, randomized timeouts make this very unlikely. The system makes progress whenever a majority is up and can communicate, if timeouts are much longer than the communication time.

Why

Raft puts safety in the rules on terms, votes and logs, which never depend on timing. Timing is used only for liveness (timeouts). This is the standard way around FLP: never be wrong, and be fast most of the time.

Exam tip

Answer the four parts in order with a label each: problem, assumptions, safety, liveness. For liveness, name FLP and the randomized timeouts; this is what the grader looks for.

Decomposition.

  1. Log replication (normal operation): the leader accepts client commands, appends them to its log, and replicates its log to the other servers.
  2. Leader election: select one server as leader; detect crashes and choose a new leader.
  3. Safety: keep the logs consistent; only servers with up-to-date logs can become leader.

Why

Raft does not solve a different problem: it solves the same problem in a way people can reason about. A strong leader makes the data flow one-way (leader → followers), which removes most special cases.

§4

Leader election, terms and partitions

Core idea. Servers are follower, candidate or leader. A follower that hears nothing for a randomized timeout (150–300 ms) starts an election in a new term. Each server gives one vote per term, and a majority is needed, so there is at most one leader per term (safety). Random timeouts make split votes rare (liveness in practice). Terms identify obsolete information: a stale leader steps down when it sees a higher term.

  1. Term 5 < 7: the message is obsolete. It rejects it and replies with term 7, so the old leader learns it must step down.
  2. Term 9 > 7: it sets its term to 9 and becomes a follower (if it was leader or candidate). It grants the vote if it has not voted in term 9 and the candidate's log is at least as up-to-date as its own.
  3. Another server won the election of term 7. It becomes a follower of that leader.

Why

The term is exchanged in every message and works like a logical clock for leadership. The rule is simple: a lower term is ignored, a higher term is adopted at once. With this rule, an old leader can never overrule a newer one.

Q25Exercise

5 servers S1–S5. S1 is the leader of term 3. At t = 0 all followers receive a heartbeat; then S1 crashes. The election timeouts are S2 = 250 ms, S3 = 180 ms, S4 = 290 ms, S5 = 210 ms. Every message takes 5 ms. All logs are equal. Trace the election: who becomes candidate, in which term, who votes for whom, who wins and when.

Model answer

  1. t = 180: S3 times out first. It becomes candidate, sets currentTerm = 4, votes for itself, sends RequestVote(term 4) to all.
  2. t = 185: S2, S4, S5 receive it. They are still followers (their timeouts are later). They have not voted in term 4, and S3's log is as up-to-date as theirs. They set term 4 and vote for S3. S1 is down.
  3. t = 190: S3 has 4 votes (itself, S2, S4, S5) ≥ majority 3. S3 becomes leader of term 4 and sends heartbeats.
  4. t = 195: the heartbeats reach the others before their timeouts (the earliest is S5 at 210). No other election starts.

Why

The majority is computed on all 5 servers of the cluster, crashed ones included: 3 votes. With randomized timeouts, one server usually times out first and wins before the others time out. This works because the timeout (hundreds of ms) is much longer than the message time (5 ms).

Q26Exercise

5 servers; the leader S1 crashed. S2 times out at t = 200 ms and S4 at t = 201 ms; both start term 4. Message delays: S2→S3 5 ms, S2→S5 12 ms, S4→S5 4 ms, S4→S3 11 ms. (a) Who wins term 4? (b) The new random timeouts of the candidates are S2 = 160 ms and S4 = 270 ms, counted from the start of their election. S3 and S5 time out later than both. All logs are equal. What happens next?

Model answer

  1. S3 receives S2's request at 205 and votes S2; S4's request arrives at 212, but S3 already voted in term 4 → denied. S5 receives S4's request at 205 and votes S4; S2's request arrives at 212 → denied. S2 and S4 voted for themselves, so they deny each other. Votes: S2 = 2 (S2, S3), S4 = 2 (S4, S5). Nobody has 3: split vote, no leader in term 4.
  2. S2 times out at 200 + 160 = 360 ms, before S4 (201 + 270 = 471 ms). S2 starts term 5 and sends RequestVote(term 5). S3, S4, S5 see term 5 > 4, adopt term 5 (S4 stops being a candidate) and vote S2, because nobody voted in term 5. S2 wins term 5 with 4 votes.

Why

Split votes happen when two servers time out at almost the same time. The fix is a new randomized timeout: it is unlikely that the same two servers collide again. Each failed attempt still costs one term number, so a term can have no leader at all. The safety rule is "at most one leader per term", not "exactly one".

Q27Exercise

5 nodes A–E; A is the leader of term 4. A partition separates {A, B} from {C, D, E}. Describe what happens in both sides, and after the partition heals.

Model answer

  1. A and B still think A is leader of term 4. C, D, E stop receiving heartbeats.
  2. One of C, D, E times out first, say D: it becomes candidate for term 5 and gets votes from C and E (3 of 5): D is leader of term 5.
  3. Clients that write to A: A appends to its log but cannot reach a majority, so nothing commits and clients get no success.
  4. Clients that write to D: D replicates on C, E and commits.
  5. When the partition heals, A receives a message with term 5 > 4: it learns it is not up to date and steps down to follower. Its uncommitted entries (and B's) are overwritten by D's log through the consistency check.

Why

Two leaders can exist at the same time, but in different terms, and only the one with a majority can commit. Terms identify obsolete information, so the old leader is harmless: it cannot commit anything.

Q28Exercise

5 nodes A–E; A is the leader of term 4. (a) A partition separates {A, B, C} from {D, E}. What happens on each side? When the partition heals, D has term 7. What happens, and who can become the next leader? (b) Instead, the network splits into {A, B}, {C, D}, {E}. What happens?

Model answer

  1. During the partition. A keeps its majority (A, B, C = 3) and keeps committing client commands. D and E time out again and again: they become candidates in terms 5, 6, 7, but they get at most 2 votes and never win. Clients that reach only D or E get no service.
    After healing. A receives a message with term 7 > 4. It adopts term 7 and steps down. D's log lacks the entries committed during the partition, so A, B and C deny their votes to D. D and E cannot win. One of A, B, C times out, starts term 8 and wins with the votes of the others. The consistency check then repairs the logs of D and E. No committed entry is lost.
  2. No group has 3 nodes. A cannot commit (only 2 of 5). No election can succeed anywhere. The system is safe but stops until the network heals.

Why

In (a) the high term of D forces a leader change, but the up-to-date rule stops D from becoming leader. So the extra election costs time, never correctness. Case (b) is FLP and CAP in practice: Raft keeps consistency and gives up availability when no majority can communicate.

§5

Log replication, safety and clients

Core idea. Each log entry has an index, a term and a command, and is stored on disk. An entry is committed when the leader of its term has replicated it on a majority. The consistency check in AppendEntries guarantees the log matching property. The vote rule (deny a candidate with a less up-to-date log: last term first, then length) guarantees leader completeness. Clients talk to the leader and attach request ids, so retries do not execute twice.

Q30Exercise

State the log matching property. Then apply the consistency check. The leader's log is 1:1 w(x)1, 2:1 w(y)2, 3:2 w(x)3, 4:3 w(y)7 (index:term command). It sends the new entry at index 4 with the previous entry ⟨3, 2⟩. Give the result for: (1) a follower with 1:1 w(x)1, 2:1 w(y)2, 3:2 w(x)3; (2) a follower with 1:1 w(x)1, 2:1 w(y)2, 3:1 w(x)5, 4:1 w(y)9. (3) After (2), what does the leader send, and what is the final log?

Model answer

Log matching property. If entries on different servers have the same index and term, they store the same command, and the logs are identical in all preceding entries. Also: if an entry is committed, all preceding entries are committed.

  1. Index 3 has term 2: match. The follower appends 4:3 w(y)7. Result: ok.
  2. Index 3 has term 1 ≠ 2: mismatch. The follower rejects; its log does not change.
  3. The leader retries with a lower index: entries 3 and 4, previous ⟨2, 1⟩. Index 2 has term 1: match. The follower replaces 3:1 w(x)5, 4:1 w(y)9 with 3:2 w(x)3, 4:3 w(y)7. Final log = leader's log.

Why

The check is an induction step. Base: empty logs match. Step: if the logs match up to the previous entry and the follower appends the same entry, they match up to the new entry. So one comparison of ⟨index, term⟩ proves the whole prefix equal. The entries w(x)5 and w(y)9 were never committed, so overwriting them is safe.

Q31Exercise

Leader log (index: term): 1:1, 2:1, 3:2, 4:3. A follower has 1:1, 2:1, 3:1, 4:1. The leader sends AppendEntries for index 4 with previous entry ⟨3, 2⟩. What happens step by step?

Model answer

  1. The follower checks its entry at index 3: term 1 ≠ 2. It rejects.
  2. The leader retries with a lower index: send entries 3–4 with previous ⟨2, 1⟩.
  3. The follower has index 2 with term 1: match. It deletes its conflicting entries 3:1 and 4:1 and appends 3:2, 4:3.
  4. Now the follower's log equals the leader's.

Why

The leader always assumes its log is correct; normal operation repairs the followers, with no special recovery code. The follower's entries 3:1 and 4:1 were never committed (otherwise this leader would have them, by leader completeness).

Q34Scenario

5 servers. The leader S1 of term 2 commits the entry at index 5 after S2 and S3 store it. Logs (terms): S1, S2, S3: 1 1 2 2 2 · S4: 1 1 2 2 · S5: 1 1 2. Then S1 crashes. (a) S4 times out first. Can it win? (b) Who can win? (c) Explain the general argument for leader completeness.

Model answer

  1. S4 has (2, 4). S2 and S3 have (2, 5): same last term, longer log, so they deny. S5 (2, 3) grants. S4 gets S4 + S5 = 2 votes < 3: it cannot win. The election times out.
  2. S2 or S3. For example S3 gets votes from S2 (equal log), S4 and S5: 4 votes. The new leader has entry 5.
  3. Leader completeness: once an entry is committed, all future leaders store it. The entry is on a majority M1. A winner needs votes from a majority M2. M1 and M2 intersect in at least one server. That server has the entry, and denies its vote to a candidate whose log is less up-to-date. So the winner's log is at least as up-to-date, and contains the entry.

Why

Raft never moves entries from followers to the leader. So the only way to keep committed entries is to elect a leader that already has them. The vote denial does exactly this, using the same majority intersection as the commit rule.

Q35Scenario

A client of a Raft key-value store sends "increment x" with request id 17. The leader commits the entry and crashes before it replies. (a) How does the client find the leader at the start and after the crash? (b) The client times out and resends request 17 to the new leader. Without extra mechanisms, what goes wrong? (c) How does Raft avoid it, and which semantics does it guarantee?

Model answer

  1. Clients always interact with the leader. At start the client connects to a random server, which tells it the leader of the current term. If the leader crashes, the request times out, and the client asks again.
  2. The entry is committed, so the new leader has it (leader completeness). A second "increment x" would add a second entry: x is incremented twice for one client request.
  3. The client attaches a sequential request id. Servers store the last id of each client as part of the log (so all replicas have it). The new leader sees id 17 already executed, discards the duplicate and returns the result. Raft guarantees linearizable semantics: every operation behaves as if executed once and only once on a single copy.

Why

Retrying is necessary (the reply may be lost) but dangerous for non-idempotent commands. Storing the ids in the replicated log, not in the memory of one server, is the key point: the filter survives the leader change.

Q36Describe

The slides refer to the extended Raft paper for log compaction and membership change. What problem does each one address, and what is the main risk?

Model answer

  • Log compaction. The log grows forever and takes space; a restarted server would replay all of it. Question: when is it safe to delete old entries? Committed entries that are already applied can be replaced by a snapshot of the state machine. Risk: deleting entries that are not committed, or that a slow follower still needs (the leader must then send the snapshot).
  • Membership change. Add or remove servers from the group consistently. Risk: if servers switch from the old to the new configuration at different times, an old majority and a new majority can be disjoint, and two leaders can be elected in the same term. The paper uses a special procedure (a transitional configuration) to prevent this.

Why

Both mechanisms touch the two things safety depends on: the log content and the definition of "majority". This is why they need extra care, and why the course mentions them without details.

§6

Distributed DBMS and Byzantine conditions

Core idea. Modern distributed databases (e.g. Spanner) use two layers: Raft or Paxos per partition so that a partition does not fail, and 2PC across partitions for atomic commit. With Byzantine processes, BFT replication needs 3f + 1 nodes. Permissionless blockchains (Bitcoin) are replicated state machines with unknown membership: proof of work orders the blocks, and the guarantees are only probabilistic.

Q37Describe

How do modern distributed databases (e.g. Spanner) combine replicated state machines and 2PC?

Model answer

The database is partitioned; inter-partition transactions need atomic commit. Each partition is replicated with Paxos/Raft, so all replicas process the same sequence of operations, and a partition behaves like one machine that does not fail (5 replicas survive 2 simultaneous crashes). Across partitions, 2PC gives atomic commit. The coordinator (transaction manager) and the participants (partitions) are assumed not to fail, because they are replicated. Channels are assumed reliable: it is sufficient that a majority of nodes in each partition is reachable.

Why

2PC is blocking only because a single node can fail. Replace each node with a replicated state machine and the weak point is gone. The two layers solve two different problems: consensus inside a partition, atomic commit across partitions.

Q38Exercise

A database has partitions PA and PB, each replicated on 5 servers with Raft. A transaction updates both; PA's group is the 2PC coordinator. What happens in each case? (a) 2 servers of PB crash during the vote. (b) 3 servers of PB crash after PB voted commit. (c) The leader of PA crashes right after "global-commit" is committed in PA's log, before it is sent.

Model answer

  1. PB still has 3 of 5 servers, a majority. Its leader (or a new one) continues. 2PC is not affected.
  2. PB has only 2 of 5 servers: it cannot commit new log entries, so it is unavailable. Its vote and its Ready state are in its replicated log, so they are not lost. The transaction cannot finish on PB until a majority of PB is back. This is a loss of liveness, not of safety.
  3. PA elects a new leader. By leader completeness, the new leader has the committed "global-commit" entry. It sends global-commit to PB. No blocking.

Why

"The coordinator writes to its log" now means "the coordinator group commits an entry in its Raft log". The decision survives the crash of any minority, so the blocking case of 2PC needs a majority failure of a group. That is much rarer than one crashed machine.

Q40Describe

Explain how a proof-of-work blockchain acts as a replicated state machine in a Byzantine environment. What are its assumptions and guarantees? What is double spending?

Model answer

State: the current balance of each user. Log: the ledger of all transactions since the beginning, grouped in blocks and replicated by all nodes. Transactions are digitally signed: if the private key is lost, the bitcoins are lost too.

Miners collect pending transactions in a block and search a proof of work over the existing chain + the new block. This links the block to the chain. The proof is hard to find (brute force, on average one every 10 minutes, difficulty adapted to the computing power) and easy to verify. The winner broadcasts the block and earns bitcoins. The others verify it and start on the next block: global agreement on the order of blocks. If two chains appear, the one that grows faster (more blocks) survives; with the same length, a deterministic choice.

Assumptions: very many nodes; the set of nodes is unknown upfront; no single entity owns the majority of compute resources. Guarantees: no provable safety, only with high probability; a longer chain that you do not know may always exist.

Double spending: a misbehaving user with enough computing power and 1 bitcoin builds two concurrent chains, one paying A (shown to A) and one paying B (shown to B). A and B can never be 100% sure that a conflicting chain does not exist.

Why

With unknown membership you cannot count votes: anyone could create many identities. Proof of work makes a "vote" cost computing power, so the majority of power decides, not the majority of identities.

Q41Exercise

The chain ends with block 100. Miner M1 finds block 101a (transactions T1, T2) and miner M2 finds block 101b (T2, T3) at almost the same time. Half of the network receives 101a first, the other half 101b. Then a miner that builds on 101b finds block 102b. (a) What does each node do at each step? (b) What happens to T1, T2, T3? (c) A shop accepted T1 as soon as it saw 101a. What risk did it take?

Model answer

  1. Each node keeps the first valid block it receives and mines on top of it: there is a fork, two chains of equal length. When 102b arrives, the chain 100–101b–102b is longer. All nodes switch to it and mine on 102b. Block 101a is discarded.
  2. T2 and T3 are in the surviving chain. T1 was only in 101a: it goes back to the pending transactions and will be included in a later block (if still valid).
  3. Its payment disappeared from the accepted chain for a while. If the payer had sent a conflicting transaction in the other branch, the shop would lose the money. One block is weak evidence; the more blocks follow, the less likely it is that a longer conflicting chain exists.

Why

Simultaneous proofs are unlikely because the proof is very hard, but they are possible. The longest-chain rule resolves them, but only after the fact. This is why the guarantee is probabilistic: no node can be 100% sure of a given sequence.

Q42Scenario

Someone proposes to replace proof of work in an open cryptocurrency with Raft: "every node votes, the majority decides". Explain why this does not work. Then explain what an attacker needs for a double-spending attack on a proof-of-work chain, and how a merchant reduces the risk.

Model answer

  • Raft does not fit. Raft assumes a known set of servers (to compute a majority) and no Byzantine behavior. In an open system the set of nodes is unknown upfront, and an attacker can create many fake nodes and win any vote. Nodes can also lie, which Raft does not tolerate.
  • Double spending. The attacker needs enough computing power to build a second chain, in which the same bitcoin pays someone else, and make it grow faster than the honest chain. This is why the assumption "no single entity owns the majority of compute resources" is essential.
  • Merchant. It waits until several blocks follow the block with its payment. Each extra block makes a longer conflicting chain less likely. It can never reach 100% certainty.

Why

Raft counts identities; proof of work counts computing power. Identities are free to create, computing power is not. The trade-off is the guarantee: Raft gives proven safety in a closed system, a blockchain gives only high-probability safety in an open one.
