Chord lookup and query flooding

The Chord exercise appears in almost every exam: build the finger tables, then route a lookup. Load an exam preset or enter your own peers. The second tab shows Gnutella-style flooding with hops-to-live.

Preset

Finger tables

Row i: start = n + 2i mod 2m; interval = [starti, starti+1); succ = first peer ≥ start (wrap around 0). The highlighted row is the one the current node uses.

Routing rule (slides of both professors). A node that receives a query for key k first checks if it stores k (k is in (predecessor, node]). If not, it forwards the query to the succ of the row whose interval contains k. This is the same as "the largest start that does not exceed k", counted clockwise from the node.

Exam method. (1) Write which keys each peer stores. (2) Build the tables, careful with the wrap-around. (3) For each hop, name the row you use. (4) The reply goes back to the requester.

Flooding. Each peer forwards the query to all its neighbors except the one it came from. Each hop decrements hops-to-live (HTL); at 0 the query stops. A peer drops a query it has already seen (same query id). A hit is sent back along the reverse path (or directly to the requester). With C neighbors on average and HTL D, one search can cost up to CD messages, and it can miss items beyond D hops.
